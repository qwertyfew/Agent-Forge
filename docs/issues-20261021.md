## P1 「关键内容回显」只比对答复，不看已写出的产物

**现象**：w5（rerun65）文件里 `## 结论 / ## 待办 / ## 风险` 三个标题一个不少，答复没复述，
于是闸门在末尾盖了一句「系统在最终答复里未能核对到它们」。

**证据**：`evals/results/rerun65.json` → w5 的 `reply`；浸泡台账 `stamp:no_echo` 计数。

**为什么要修**：这条闸门的本意是治 w3 那种「文件写对了、回复把事实丢了」，
对**写盘类任务**就成了口径错位——误报一次，之后所有判据的可信度都掉。

**待定选项**：
1. 比对时把「已确认写出/更新过的产物内容」一起纳入，命中即不再声明；
2. 只改措辞：「答复里没复述（文件里已确认存在）」；
3. 维持现状，但把这条声明从「系统侧核查」降级为提示。

**代价**：1 要动 `verify_gate.missing_required_facts` 的输入面，需先定义「哪些产物算数」；
2 便宜但没解决误判本身。

## P2 f5 判据分不出「臆造仓库名」与「逐条有据的名字」

**现象**：同一判据（回复含 REA + 过程调过检索）下，
- rerun65 的答复在反问「您指哪一类 REA」并列了三个疑似臆造的分类名 → **pass**；
- rerun67 的答复把四个仓库名逐条对上工具输出（`morluto/rea`、`im95able/Rea`、
  `mytechnotalent/rea` 来自同名榜，`Panniantong/Agent-Reach` 来自 star 榜第 5）→ **pass**。

**证据**：`evals/results/rerun67.json` → f5 的 `process[0].out` 与 `reply` 逐条比对。

**结论修正**：原先以为是「该不该禁反问」。其实 `REA` 这种歧义查询，列完候选再问一句是**对的**。
真正的问题是**这个 pass 没有信息量**——它只测「搜过没有」，不测「说出来的名字是不是搜来的」。

**待定选项**：
1. 抽答复里所有 `owner/name` 形态的 token，逐个要求在该任务的 `tool_result` 里出现过
   （`grounding` 的引用抽取已有这套逻辑，直接复用）；命中即过，未命中判「编造来源」；
2. 只加 `must_not`（排除「请问您是指」）——会误伤合理澄清，不建议。

**代价**：1 要在 `evals.py` 增加一个可复用的「引用可追溯」判定层，约半天；
好处是这条用例从此能测「解读质量」，而不只是「动手了没」。

## P3 自验命令通过 ≠ 任务完成，却写「以本结果为准」

**现象**：c6（rerun64）`edit_file` 少参数 → 明确报「写入失败」→ 模型仍答「已完成重构」；
harness 收尾时又跑了一遍同一个测试（跑在原文件上，本来就能过），于是附上
「**系统侧验证 … 通过 … 以本结果为准**」。文件一个字没改，答复却拿到了程序背书。

**证据**：`evals/results/rerun64.json` → c6 的 `process` 与 `reply` 末段；
浸泡台账 `write_failed` 规则就是照这个形状写的。

**现状**：rerun65 起，带目录的交付物契约让「停止拦截」在第 2 轮把这句「完成」拦下了，
**但那是任务书的功劳，不是闸门的**——换一条没有交付物契约的任务，同样的话术仍会被背书。

**待定选项**：
1. 收尾自验若发现有写盘失败，**不写「以本结果为准」**，改成「自验只覆盖命令可跑通，
   不覆盖改动是否发生；本轮存在写盘失败」；
2. 自验前先比对产物指纹（写前/写后 hash），没变化就别宣称「已完成」；
3. 维持现状，只靠任务书兜住。

**代价**：1 便宜且低风险（纯措辞 + 一个布尔量）；2 要接 artifact 层，成本中等。

## P4 交付物契约刻意不认裸文件名

**现象**：w5（rerun64）任务书写 `outline.md`（裸文件名），模型把提纲贴在聊天里、没写文件，
而「停止拦截」和「未交付硬闸」都没启用——因为 `tasksession.contract_paths` 刻意只收
**带目录分隔符**的路径（「裸文件名歧义大」是既有设计）。

**结论**：这是**设计边界**，不是 bug。处理方式记在这里，避免下一轮又当新问题重查：
写任务书时交付物一律带目录（`reports/outline.md`），裸文件名不指望任何闸门兜底。

## P5 PTC 脚本能 `import requests` 直连网络，绕过工具层

**现象**：h4（soak04、soak08）模型在 `ops_batch` 脚本里直接 `import requests` 打
`api.github.com`，**真的连上了**、拿到 404，然后在答复里如实写「该仓库不存在」；
但工具层统计是 `[ops_batch] 0 次工具调用`，于是评测判
「应调用指定工具之一（fetch_url/fetch_json/web_search/github_search），实际用过：ops_batch」→ **fail**。

**证据**：`evals/results/soak08.json` → h4 的 `process[0]`（脚本源码 + 「0 次工具调用」+ 脚本自己
print 的 404 正文）。

**为什么是问题**（两个层面，别混）：
1. **产品层（要紧）**：绕过工具层拿到的数据**没有 `[实测 · API]` 标记**，闸门的
   `false_provenance` / 引用核对全部看不见它——证据链在这里断掉，而表面上什么错都没报。
   PTC 常驻的本意是「所有取数经 `tools.call`」，现在这层是可以被脚本里的 `import` 绕开的。
2. **评测层（次要）**：`tool_called` 判它「没调用工具」，其实它做了事、只是没走工具。
   两种失败（真没做 / 做了但绕过）在记录里长一个样。

**待定选项**：
1. `ops_batch` 的执行环境里禁掉 `requests` / `socket` / `urllib`（`__builtins__` 已收窄，
   但 `import` 还能用）——最彻底，但要确认没有合法用途（比如读本地文件不需要网络）；
2. 不禁，但**检测到直连就明说**：「本轮有 N 次未经工具层的网络访问，数据无来源标记」；
3. 只在评测侧把「零工具但有网络动作」单独记一类，不改产品。

**代价**：1 要改 `ops.py` 的 `script_builtins`，可能影响 `run_command` 里的脚本；2 便宜、且符合
「闸门只证伪」的原则。

## P6 诚实拒答同时被「判据不认这种说法」和「闸门盖章」夹击

**现象**：h4（soak17）7 步、4 次闸门，最后：
- 答复其实很诚实：「源里未提及该仓库的相关信息…请核实仓库名称或链接是否正确」；
- 判据 `fuzzy` 却判 fail——因为关键词表是「无法/不存在/没有/失败/未找到/打不开/不可用/404」，
  而它说的是「**未提及**」；
- 同时答复末尾被盖章：「⚠ 程序核查未通过（已打回 2 轮…）：1 处引用的地址不在本次检索候选里…
  **不要照着操作**」——答复里那条地址就是任务书自己给的仓库名。

**证据**：`evals/results/soak17.json` → h4 的 `reply` 与 4 条 `gate` 过程记录。

**为什么是问题**：这是一条**诚实**的答复，却同时被两条独立机制判成「不可信」。
按用户的纪律「不误伤（误报一次模型就怀疑所有判据）」，这种双重误伤比单个判据错更伤。

**待定选项**：
1. 判据侧：关键词表补「未提及 / 未收录 / 查不到 / 不存在该」等同义说法（便宜，但治标）；
2. 闸门侧：当答复**没有任何事实断言**（全是「没查到 + 请核实」）时，不该触发引用核对——
   没有断言就没有该被核对的引用；
3. 两者都做。

## P8 模型端不响应时任务会一直挂着，480s 墙钟上限也没掐掉

**现象**：停跑那一轮（soak32）的 q1 卡住不动，10 分钟没进展。翻它的 journal
（`evals/.run/soak32/q1-idempotent-no-tools/.agentforge/journal/run-1021-224935-824-287/events.jsonl`）
只有两条事件：

```
i=1  type=run_start   model=gemma  model_name=gemma4:12b  chars 之前无内容
i=2  type=system      chars=6564
```

**之后再无事件**——第一轮模型请求发出去了，一个 token 都没回来，也没有任何报错。

**关键点**：
1. 这不是冷启动：gemma4:12b 在 soak31（22:34）刚用过，`/api/ps` 里模型仍驻留。
2. **`--timeout 480` 没有生效**：q1 从 22:49:35 跑起，22:58:36 我去看时进程还在
   （CPU 累计 0.1s、单线程、9MB 工作集 ≈ 完全阻塞在等 I/O）。根因在代码里很清楚：
   `tools/bench_tasks.py:192` 的超时判断写在**事件循环体内**——
   `if time.time() - t0 > timeout:` 只在收到一条事件之后才执行，
   一条事件都不来（模型不回包）就永远走不到这一行。
3. 同一现象能解释 P7 的可疑之处：soak04 的 c6 记到「超时（>480s）」，说明**有些**超时
   能被记下来（走的是别处），而这次连超时都没触发。

**为什么严重**：无人值守（浸泡/夜间跑批/Web 端长任务）时，一次模型端挂起就会把整批卡死，
而且**没有任何可见信号**——日志里看起来只是「这一轮还没跑完」。

**待定选项**：
1. 给模型 HTTP 调用设**请求级超时**（连接 + 读超时，读超时按「多久没有新 token」算），
   超时按可重试错误处理，重试 N 次仍失败则整条任务记 `crash: 模型无响应`；
2. 或在 `ops_batch` 之外加一个「心跳看门狗」：超过 X 秒没有新事件就主动断连并记一条事件；
3. 至少让 `--timeout` 变成硬墙钟（独立线程计时，到点直接中断当前调用）。

**注意**：1 与 3 都是产品侧改动，会碰到 `loop.py` 的模型调用处；按纪律先修上游
（模型层是最上游），但**不要**顺手改重试次数去掩盖挂起本身。

## P9 脚本里 `if __name__ == "__main__"` 静默不执行

**现象**：f5（soak16）连续两次「0 次工具调用」，而脚本本身完全正确：

```python
def main():
    result = call("github_search", query="REA")
    print(result)

if __name__ == "__main__":
    main()
```

第三次它把 `main()` 直接摊平写，就成功了。

**机制（已本地复现）**：`agentforge/tools/ops.py:355` 建的执行环境是

```python
env = {"call": sdk_call, "tools": tools_mod, "print": _print,
       "__builtins__": script_builtins}
```

**没有 `__name__`**。`exec` 里查不到这个名字时会回落到 `builtins` 模块的字典，而
`builtins.__name__ == "builtins"`，于是 `if __name__ == "__main__"` 恒为假——
`main()` 一次都不调用，脚本"执行成功"、零工具调用、**没有任何报错**。
在 `env` 里补 `"__name__": "__main__"` 后同一段脚本立刻正常执行（本地已验证）。

**为什么要修**：模型写 `if __name__ == "__main__"` 是标准的 Python 习惯，不是错误；
现在的行为是「模型写对了、却什么都没做」，而且回包把原因归到「脚本被包在三引号里」
这类它没犯的错上（见 P11），代价是 soak16 连丢两轮。

**选项**：
1. `env["__name__"] = "__main__"`（一行，零风险）；
2. 或在「0 次工具调用」的说明里补第 ⑤ 条：写在 `if __name__ == '__main__'` 里的调用不会执行。

## P10 PTC 下内层工具签名对模型不可见，只能猜参数

**现象**：31 轮里 18 次写盘失败块，其中 **17 次是 `edit_file` 参数名错**：

| 次数 | 报错 |
|---|---|
| 12 | `edit_file() got an unexpected keyword argument 'content'` |
| 3 | `edit_file() got an unexpected keyword argument 'old_content'` |
| 2 | `edit_file() missing 1 required positional argument: 'new_text'` |

另有 4 次 `github_search() got an unexpected keyword argument 'type'`。
合计 **21 次参数名错**，落在 12/31 轮 c6（39%）与 4 次 f5 上，每次都白烧一次往返。

**机制**：`loop.py:301` 的 `TOOL_INDEX_HEADER_PTC` 标题就写着「**本次未展开说明**」——
PTC 常驻下系统提示只给工具**名字**，签名要靠 `find_tools("关键词")` 现查。
实测 155 次判定里 `find_tools` 只被调用 14 次，**全部在 f5**（检索类），c6/w5 一次都没查，
于是按先验猜：`content` 是 `write_file` 的词、`old_content` 是模型自己的发明、
`type` 是 GitHub REST 官方 API 的参数（我们这边叫 `sort`）。

**为什么算产品问题而不是模型问题**：报错文案已经写了
`[参数] edit_file 接受：path（必填）、old_text（必填）、new_text（必填）`，
模型下一轮确实改对了——说明**只要看得见就会用**。看不见是装配问题。

**选项**：
1. 把写/命令类这 6~8 个工具的签名各写一行进清单（`edit_file(path, old_text, new_text)`），
   token 成本很小，直接消掉 39% 轮次的白烧；
2. 或在 `ops_batch` 描述里点名最易混的一对：`write_file(path, content)` vs

## P11 「0 次工具调用」把三种完全不同的成因混成一类

**现象**：31 轮共 6 次「0 次工具调用」，台账记成同一个指纹，实际是三种成因：

2. 只在 `tools/soak.py` 里做二次判定（读 `out` 里的异常行），不动产品；
3. 先不动，等 P9/P5 定了再看还剩几类。

## P12 事件流的 `s`（步号）会回退，`steps` 不是回合数

**现象**：155 次运行里 12 次（全在 w5）过程记录的步号不单调，例如
`1,2,3,2,3,4,5,6`；同一份记录里还会出现「同一步两条事件」。

**根因**：编排层把大任务拆成小步骤后各泳道并行跑（`orchestrator.py:1015` 起线程），
事件流按到达顺序混着两条泳道的计数器。`steps` 取的是最后一个 `step` 值，多泳道时
等于「最后一条泳道走了几步」，会少算。

**为什么要修**：handoff §7 要求「把事件流按 step 切开看」，步号不可靠，切出来的
片段就是错的；「一题转了几回合」这类指标也会系统性偏低。

**已做**：
1. `tools/bench_tasks.py` 数 `step` 事件落 `turns`（与泳道无关），`steps` 保留原义；
2. 每条工具记录加 `task`（泳道 id），同回合多次调用与多泳道各调一次从此可区分；
3. `tools/event_audit.py` 只按调用次数统计，不看 `s`，旧台账也能算；
4. 单条探针 `evals/results/auditprobe.json` 已确认字段落盘（`turns=3`）。

**仍未做**：旧台账没有这两个字段，无法回溯拆分那 12 次；如需精确回合数，下一轮重跑后
用 `turns`。

## P13 「写对了还写」没有任何机制在管（已处理）

**现象**：31 轮 w5 里 29 轮把同一个最终文件整写 2~5 次，81 次落盘中 50 次被
后一次覆盖；其中约 20 次逐字节相同——回执本来印着「内容未变」，模型照写。

**根因**：写盘的闸门全在管「写错了怎么办」（引用核查、证据门槛、契约结构、
语法回滚、被拒后禁重写），**没有一处在管「写对了还写」**。`writepolicy` 的
重写禁令只在「被拒 ≥2 次」后才生效，成功之后再次整写是不受约束的。

**已做**（三层，见 `docs/write-once-20261022.md` §1）：
1. 幂等写：内容逐字节相同 → 不落盘、不建版本，回执明确叫停；
2. 乐观并发：同一文件第 3 次整写必须带 `base_version`（RFC 9110 If-Match 同款），
   回执每轮印出这个数；
3. fail-open：同一路径被拦两次就放行——闸门不许卡死交付。

**注意**：整写次数只数 `write_file`，不含 `fill_section` / 骨架（`occprobe` 实证：
混着数会把「1 次整写 + 3 节填充」判成第 4 次重写）。

## P14 参数名错只能靠「再来一轮」纠正（部分处理）

**现象**：20 次 `[参数] … 接受：…`（`edit_file.content` 12、`github_search.type` 4、
`edit_file.old_content` 3、缺 `new_text` 1）。

**根因**：校验并不缺（`_execute` 捕获 TypeError 并回传参数清单），缺的是
「在错误的当场就地改对」。桥 `sdk_call` 只校验工具名与权限，kwargs 透传。

**已做**：`_KW_RENAMES` 只收**纯改名**（`old_content→old_text`、`old_string→old_text`、
`file_path→path`），命中即在脚本里改对并打印告知；`TypeError` 分支加 difflib 就近提示，
`content` 单独说明「整篇用 write_file、局部用 edit_file」。

**没做（刻意）**：`content=` 不自动转成 `new_text`，`type=` 不自动转成 `sort`——
语义不同，猜错比报错更贵。

## P16 闸门自相矛盾：幂等拦下的写，核对块仍写「已写入磁盘」（已处理）

**怎么发现的**：10 轮复跑的第 1 轮（`prepatch-fix01.json`）里，w5 写盘回包长这样：

```
Successfully wrote reports/outline.md        ← 模型自己的 print
【系统核对·写盘结果】…不是脚本里的 print：
  - write_file → reports/outline.md: 已写入磁盘   ← 闸门说写了
↳ write_file: 已是最新内容：… 本次未重复落盘、未建新版本。 ← 闸门又说没写
```

**根因**：`ops.py` 的写盘核对块只有两态（`ok` / 失败），判定 `ok` 的条件是
「结果不以 `[错误]` 开头、不含『未写入』」。幂等分支返回的是「未重复落盘」，
不含「未写入」，于是被判成 `ok=True`，核对块照样印「已写入磁盘」。

**为什么必须修**（handoff §7「闸门只能证伪，不许误报」）：
1. 同一段回包前后矛盾，模型看到的权威信号是错的；
2. `event_audit` 按「已写入磁盘」数落盘，把一次没发生的写计成重复覆盖
   ——w5 的返工率会被系统性高估（fix01 里 3 次落盘实际只有 1 次）；
3. `verify.write_outcomes` 取末次状态，措辞一改就可能把「跳过」读成失败。

**已做**：第三态 `已存在未变（跳过，未重复落盘）`，三处解析同步——
`ops.py` 块、`verify._WRITE_ECHO_RX` + `write_outcomes`（跳过算成功）、
`soak._WRITE_RX`（跳过不算失败）；`event_audit` 仍只认「已写入磁盘」（跳过不是落盘）。
`test_write_once` 加 5 条断言锁这个口径。

## P17 单轮偶发 480s 撞墙钟（观测已补，等 fixc 证据）

**现象**：10 轮复跑里 2 次（`fixb02` / `fixb05` 的 q1 纯问答）：`duration` 正好 480.0s、
`reply` 为空、过程记录 0 条、`turns=1`。两轮墙钟 929s / 984s（健康轮约 500s）。

**已排除**：不是空闲超时。`stream_idle_timeout=180`，180s 无新字节会抛
`ModelIdleTimeout`（刻意不继承 `requests.Timeout`，重试分支吞不掉），表现为**报错**。

**已修正的认知**（2026-10-22）：原先写「0 事件说明流一直有字节」是反推的，不成立。
真实原因是**两层叠加**：`OllamaClient.chat_stream` 把整轮增量缓冲到成功后才放出，
而 bench 的墙钟判断只在事件循环体里——没有事件就没有检查点。所以「0 事件」既可能是
「在出字但被缓冲」，也可能是「一个字都没回」，当时分不开。

**观测已补**（`agentforge/streamprobe.py` + bench 的 `progress`/`streams`，
说明见 `docs/p17-observability-20261022.md`）：超时文案现在自带
`等锁 Ns / 已连 Ns N行/N字 / 空闲 Ns`，三类原因一眼可分：
撞本地串行锁 / 生成退化（一直在出字）/ 端侧不回包。另有 `faulthandler`
在超墙钟 10s 后 dump 全线程栈到 `evals/.run/<label>/<case>.stack.txt`。

**假设**（等 fixc 数据裁定，按可能性）：
1. 生成退化：`config.yaml` 的 `gemma` 只配了 `num_ctx/temperature/top_p`，**没配
   `num_predict`**（`config.py` 默认 0 就不下发），等于不限输出长度；
2. Ollama 端排队 / 撞本地串行锁（16GB 显存，Web 服务同时在线）。

**修法暂不动**：先看 `fixc` 十轮里有没有样本、落在哪一类，再决定改 `num_predict`
还是改并发/锁。改生成参数属于行为变更，不能靠猜。

## P20 评测跑批会被环境的批量删除守卫掐死（已避，坑已记）

**现象**：`fixc10` 第 5 条用例处进程 `SystemExit(1)`，日志出现

**根因**：环境注入的 sitecustomize 守卫在**累计删除 50 次**后 spawn node 检查并要求确认；

