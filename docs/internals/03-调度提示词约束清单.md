# 03 · 调度提示词（DISPATCH_SYSTEM）约束清单与化简分析

> 对象：第一次调用（任务拆分+分配）的 system 提示词，`agentforge/dispatcher.py:35`。
> 现状 2248 字符（模板）→ 渲染后 2310 字符 ≈825 tokens。
> **本文只是分析，未改动任何代码；化简方案待用户拍板后才实施。**

## 一、约束逐条清单

## 二、真正可能影响输出的风险点（按危害排序）

### 1. #6「宁可多拆也不错配」没有对冲——成本放大器

这是唯一一条**单向天平**式约束：鼓励拆的收益（各配最强模型）写明了，
拆的代价（每个子任务独立烧一遍系统提示+任务书+执行轮，子任务间历史不共享）
只字未提。那条 624K token 的任务里调度器拆出 3 个子任务、且全部指派给
**同一个**模型——「各配最强」的收益为零，成本却是三份。约束文本与模型池
状态脱节，是结构性的误导源。

### 2. #3 在单模型池下仍然强制「必须拆成不同任务」

候选目录只有一行 DeepSeek 时，「不同类型拆给不同最强模型」没有兑现对象，
但「**必须**拆」的语气仍在——模型会为遵守形式而硬拆（本次 3 任务正是如此）。
可加一句条件化：「候选模型同质（或仅一个）时，按交接清晰度决定拆分，不必为
分配而拆」，但这改行为，需拍板。

### 3. #7+#8 叠加导致 goal 整段抄原文

「自包含」+「绝不缩小范围」都没有说「可以引用而不必复制」。实测子任务
goal 里出现了用户原文的大段复制（每个子任务各带一份），执行轮每轮重发时
这部分被放大 N 轮 × N 任务。改法是教它「goal 只写本任务做什么+点名交付物，
共享背景用一句『原文见交接』」——但这会动保真语义，需谨慎评测。

### 4. #10 的长示例是死重量

逐字节比对的 python 单行命令示例 185 字符，只在复制/备份任务有用。
程序侧 `_augment_copy_checks` 本来就会给这类 goal 自动补写同款声明
（f4 教训的兜底），所以提示词里只需保留「复制类任务要写明用复制命令、
禁止 read+write 重写」一句，示例可删。

## 三、化简方案（分层，未实施）

**第一层：纯压缩，语义零变化（预计 2248 → ~1500 字符，≈省 250 tokens/次）**

1. #4 两个示例压成一个（保留 REA 三任务例，删「分析→报告=2 任务」子例）；
2. #15 两条防自派合并成一句；
3. #10 删长示例，留一句约束（程序兜底已有）；
4. #11 三句压一句；
5. #5 并进 #2/#3 的表述。

**第二层：改语义，需单独评测验证（各自独立拍板）**

6. #6 加对冲句：「拆分也有交接成本；候选模型不足以兑现『各配最强』时，
   优先少拆」；
7. #3 加单池条件（同上二.2）；
8. #7/#8 加「引用而非复制」的 goal 写法指引。

**收益说明（如实）**：第一次调用本身只 ≈1200 tokens，第一层化简省的是
每次调用约 250 tokens + 更清晰的约束面；真正的大头在执行轮（见 02 篇），
化简调度提示词的主要价值是**防错误约束误导输出**，不是省钱。

## 四、历史沿革备注

- 「宁可多拆也不错配」「按能力类型分层」是第 42 步按用户口述规则反转写入的
  （原为「宁可少拆」）——第二层的任何松动都涉及这条用户决策，必须由用户拍板。
- #9/#10 的保真条款来自第 29 步闸门前移与 f4 复制教训，有评测背书，不建议删。
