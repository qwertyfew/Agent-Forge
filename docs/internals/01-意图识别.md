# 01 · 意图识别：纯规则，不用 LLM

> 结论：**意图识别（要不要走多 agent 调度）全程零 API 调用**。
> 这是对照 Anthropic《Building Effective Agents》后有意的设计——Routing 模式的
> 分类器可以是确定性规则，省钱且零延迟。第 29 步补记（evolution.md）里用户已确认过。

## 判定链（2026-10-17 核实）

入口在 `agentforge/orchestrator.py` 的 run_flow 末段（约 1140 行）：

```python
if (auto_plan and not pinned                      # 用户没手动钉模型
        and getattr(agent.cfg, "dispatcher_enabled", False)
        and _worth_dispatch(message, len(entries))):
    # → 走多 agent 调度（决策模型拆解+指派）
```

`_worth_dispatch`（orchestrator.py:195）：

```python
def _worth_dispatch(message: str, pool_size: int) -> bool:
    """是否值得动用决策模型拆解：包含多个动作，或请求本身较长。"""
    return needs_plan(message, pool_size) or len((message or "").strip()) >= 60
```

`needs_plan`（planner.py:280）：

```python
def needs_plan(text: str, pool_size: int) -> bool:
    if pool_size < 2:
        return False
    return len(split_task(text)) >= 2
```

`split_task`（planner.py:162）是纯文本规则，依次尝试三种切法：

1. 编号列表（`NUMBER_RX`）切成段；
2. 连接词（`SPLIT_RX`，如「然后」「再」「接着」类）切；
3. 多行请求按行切。
   都切不开就返回单段 → `needs_plan` 判 False。

## 对那条 REA 分析任务实际发生的事

原文 1098 字符 ≥ 60 → **命中「较长」分支**，直接判定走多 agent 调度。
一次模型调用都没花在「判断这是个复杂任务」上。

## 未走调度时的退化路径

`_worth_dispatch` 不过时不是直接单模型裸跑：若 `needs_plan` 为真
（多动作但池子/长度不够调度），仍走**计划循环**（make_plan，同样规则切分），
每步一个子任务书；单动作请求才真正单模型直答。

## 为什么不用 LLM 做意图识别

- 判定的输出只是二值（调度 vs 不调度），规则的错误成本很低：判轻了走计划循环，
  判重了多花一次拆解调用，都不破坏任务本身；
- Anthropic 五模式中 Routing 的分类器明确可以是确定性规则；
- 每省一次调用就省一次「系统提示 + 全文重发」的固定开销。

（后续若任务形态复杂到规则判不准，可考虑用最便宜的本地模型做分类，但那是
成本换准确率的主动选择，不是现在的实现。）
