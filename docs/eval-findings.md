## 1. 失败只有六层，先归层再动手

评测里每次「答错」都能落到下面某一层。**修错层是最贵的错误**——在闸门上加判据去修
「抓取失败」，只会让闸门判得更准、模型更没材料。

| 层 | 典型症状 | 确定性判据（能自动拦吗） | 归属模块 |
|---|---|---|---|
| **L1 取数** | 搜回来的东西跟查询无关；网页抓不到；抓到的是导航壳 | 能：与查询零词面交集 → 丢弃并明说 | `tools/web.py` |
| **L2 上下文** | 抓到了但后面几轮「忘了」；压缩后依据消失；上下文越压越大 | 能：证据消息是否仍在、压缩前后字数 | `context.py`、`loop.py` |
| **L3 组装** | 脚本语法错、三引号整段变字符串、控制标记混入 | 能：能不能编译、有没有真调用 | `tools/ops.py` |
| **L4 闸门** | 判得对但用户看不见；判错冤枉模型；判了也不说为什么 | 能：事件是否到达流、误报样例 | `grounding.py`、`webui.py` |
| **L5 模型** | 凭先验写包名；源对读对但推理错；谄媚式收尾 | 部分：只能证伪（命令无据/引用未准入/谎称已核实） | 提示词 + 证据准入 |
| **L6 评测** | 你的复现脚本本身在骗你 | 能：先按 step 切事件流再下结论 | `scripts/dispatch_task.py` |

一句话总结这十几跑的收益分布：**L1/L2（取数与上下文）的修法收益最大，L4 只能避免误伤与漏报，
L5 只能压概率，L6 决定你会不会修错地方。**

### 2.1 rerun62 之后才被发现的三件事（都在 L2）

1. **压缩不累积**：`60640 → 6087` 之后下一轮又是 `63703`。原因是压缩只改了「本轮请求的副本」，
   `ctx` 一直是原始历史 → 每轮从 6 万字重摘一遍，摘要白做、快照翻倍、还多花一次摘要调用。
   修：模型侧上下文单列 `model_ctx`，压缩结果写回它；展示用 `history` 不动。
2. **越压越长**：日志里 30 条 `truncate 3872→3878`。每轮都给已压缩的消息再盖一次
   `[已压缩] `（正好 6 字），压 30 轮一个字没省。修：已压缩的不再动；没变短就不替换；
   一条都没动就返回原列表（调用方据此不再报「压缩」）。
3. **一条退化调用占 5 万字**：某轮 `ops_batch` 的参数 50,228 字，其中 50k 是
   `<|channel>thought` 连吐。它此后每轮重发，直接把上下文撑爆。
   修：参数入历史前先洗（剥控制标记 → 折叠连续重复行 → 走同一套 `sanitize_script` → 超长掐中段），
   实测 50,228 → 247 字。

## 3. 判据清单（闸门到底能拦什么、不能拦什么）

**能拦（确定性，误报率低于可接受线）**

- 命令/目录/包名在本次工具输出里找不到（`reply_grounding_issues`）
- 答复引用的 URL / owner-repo 不在本次检索候选池里（`evidence_admission_issues`）
- 声称「已从官方源提取 / 已验证」但本次**零篇**一手正文（`false_provenance`）
- 结构性问题：脚本零调用、参数退化、成块重复、代码块里的命令无据

**拦不了（只能压概率）**

- 源对、读对、推理错（例：从 marp-cli README 推出「Marp 依赖 Pandoc」）
- 措辞谄媚、结论过度自信、该说「不确定」时不说
- 选错源但那个源确实存在于候选池（准入只保证「不是自己拼的」，不保证「是最优的」）

**闸门的三条铁律**（都来自被用户当场纠正的教训）

1. **不给答案**：诊断只说「你犯了什么错 + 确定性依据 + 下一步往哪走」，绝不写「改成 XXX 就对了」。
   给了答案，模型会照抄提示蒙过去，闸门就退化成答案生成器。
2. **不误伤**：误报一次，模型就会开始怀疑所有判据。引用抽取必须先排除命令行里的镜像名、
   缩写并列（`CI/CD`）、`src/components` 这类路径。
3. **必须可见**：`yield` 了不等于到了用户眼前——事件类型没有前端分支就会被静默丢弃（rerun16、58 各一次）。

## 4. 复跑规程（每次都要照做，省下的是排查时间）

```bash
# 1) 改完先自证：相关套件全绿（不要只看一个）

  s=$(curl -s -o /dev/null -w "%{http_code}" --max-time 3 http://127.0.0.1:8787/api/health)
  [ "$s" = "200" ] && break; sleep 4
done

# 3) 派发（tag 会进任务标题：[rerun63] …，并落 .run/rerun63.meta.json 身份卡）
C:/Users/admin/.workbuddy/binaries/python/versions/3.13.12/python.exe .run/launch_rerun63.py

# 4) 判读：先看时间线，再看上下文构成，最后才看答复
.venv/Scripts/python.exe scripts/ctx_report.py --list 3
```

**判读顺序**（顺序反了就会误诊）：

1. `.run/<tag>.events.jsonl` 的 `tool_result` —— 它到底拿到了什么材料
2. `scripts/ctx_report.py` —— 材料到它眼前时还剩多少（压缩吃了吗）
3. 闸门事件（`grounding_gate`） —— 判了什么、依据是什么
4. 答复 —— 最后才看，而且要问「这句话背后有哪条工具输出」
