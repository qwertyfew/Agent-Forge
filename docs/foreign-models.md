# 国外（非中国厂商）本地模型调研

> 调研时间：2026-10-11 ｜ 目标硬件：RTX 5060 Ti **16GB** + Windows ｜ 用途：本地 Agent（需**工具调用**）+ 编码 + 推理
> **本报告只做调研，未下载任何模型。**

---

## 0. 先说一个容易被忽略的事实

你现在的 `gemma4:12b` **本身就是国外模型**——Google 出品（Gemma 系列），
不是国产。你的池子里真正的国产品牌只有 `qwen3.5:4b`（阿里）。

所以「只有国产模型」这个判断，实际只对了一半。不过 Gemma 之外确实还有几个
值得看的国外选择，尤其是 OpenAI 开源权重的那款。

## 3. 几条必须说清楚的取舍

**① 24B 那一档在 16GB 上是"看得见吃不着"。**
`mistral-small3.2:24b` 和 `devstral:24b` 纸面都很强（后者 SWE-bench Verified
约 68%，是 16GB 级别里最高的 agentic 编码分），但它们实际占 ~19GB，
在 16GB 卡上会被迫 **18%/82% CPU/GPU 分割**，速度从 50+ 掉到 **约 18 tok/s**。
你这个 256K 窗口的 gemma4 已经占了 13.8GB —— 同时常驻会打架。

**② 你已有的 `gemma4:12b` 其实排位很高。**
有评测把它列为「16GB 档最佳 agent 倾向选择」，理由是原生工具调用 + 输出格式
稳定 + 256K 上下文。**能压过它的本地选择并不多**，而且 gpt-oss:20b 属于
"互补"而不是"替代"——看官方数据：

| 指标（high 档） | gemma4:12b | gpt-oss:20b | 谁赢 |
|---|---|---|---|
| GPQA Diamond | **78.8** | 71.5 | gemma4 |
| HLE | — | 10.9（偏低） | gemma4 |
| Tau-Bench（工具调用） | **tau2 68+** | 54.8 / 38.0 | gemma4 |
| AIME 2025 | 77.5 | **91.7** | gpt-oss |
| MMLU | 77.2（Pro） | **85.3** | gpt-oss |
| 长文推理（AA-LCR） | — | 14%（明显弱） | gemma4 |
| 生成速度 | ~84 tok/s | **~140 tok/s** | gpt-oss |
| 上下文 | 256K | 128K | gemma4 |
| 多模态 | 图+文 | 纯文本 | gemma4 |

结论：**gpt-oss:20b 赢在速度和竞赛数学，gemma4 赢在工具调用可靠性、长文推理
与上下文长度**。做 agent 任务时前者未必更稳，别指望"换了就变强"。
两者同时常驻也很合适——按维度路由正好各取所长。

**③ 中文能力是要付代价的。**
这是国外模型最现实的短板。综合多方评测：
- Gemma 4：**优秀**（140+ 语言，多语言是它的招牌）
- Llama 3.x / Gemma 3：**中等偏良好**
- Mistral / Phi / Command-R：**中等或偏弱**

也就是说，从国产模型换到国外模型，中文对话与中文写作的体验**大概率会下降**。
如果你大量用中文写长文，建议**保留 gemma4 作为中文主力**，把国外模型放在
编码、英文资料、速度敏感的场景。

## 4. 如果只试一个

```bash
ollama pull gpt-oss:20b
```

理由：唯一一个"既明显强于现状、又能在你这张 16GB 卡上满速跑"的国外模型。
MoE 架构让它以 3.6B 的算力成本生成——**本机实测预填充 1779 tok/s，是 gemma4:12b
的 4 倍**，生成 89 tok/s 也快于 gemma4（76），且原生支持工具调用与 thinking，
适合作为 agent 的第二主力。

想再稳一手就先拉 `llama3.1:8b`（6–8GB）试试水，成本最低。

> 原生上下文长度并写好配置，你在设置页勾选即可用。
>
> 而且本报告的数据已经进了评分库（`agentforge/scores.py` 的 `gpt-oss:20b` 条目），
> 路由会按上表的真实强弱分配任务——不用你再手填维度分。

## 5. 本机实测（2026-10-11，gpt-oss:20b 已部署）

硬件：RTX 5060 Ti **16GB** + Windows。测量工具：`tools/bench.py`（读 Ollama 的
`load_duration` / `prompt_eval` / `eval` 计时字段，非掐秒表，跨模型可比）。
**统一 `num_ctx=8192`** 保证是同一条件的横向对比：

| 模型 | 加载 | 提示处理 | 生成 | 显存 |
|---|---|---|---|---|
| `qwen3.5:4b` | 5.1 s | 327 tok/s | **103.0 tok/s** | 100% GPU |
| `gpt-oss:20b` | 6.3 s | **1779 tok/s** | 89.1 tok/s | 100% GPU |
| `gemma4:12b` | 12.2 s | 443 tok/s | 76.0 tok/s | 100% GPU |

### 由此得到的三条结论

1. **预填充差距是量级级的。** gpt-oss:20b 靠 MoE（只激活约 3.6B）把提示处理做到
   1779 tok/s，是 gemma4:12b 的 **4 倍**。长任务里多步接力每步都要重发上下文，
   这一项直接决定"等多久才开始出字"。
2. **生成速度的公开数据要打折。** 调研阶段引用的社区数字约 140 tok/s，
   本机实测只有 **89 tok/s**（换成 gemma4 是 76，仍更快，但没到"碾压"）。
   体积更大的模型在消费级卡上很难复现评测站点的吞吐。
3. **64K 窗口不会掉到 CPU。** 自动配置给 gpt-oss:20b 的窗口是 65536
   （原生 131072 按 65536 上限封顶），实测该窗口下仍是 **100% GPU**、
   生成 89 tok/s 与 8K 时几乎一致，说明 16GB 卡扛得住，
   "部署完勾选即用"这条路径是通的。

## 6. 信息可靠性说明

- 本报告前四节基于 2026-10 的公开评测与厂商资料整理（含 ollama.com/library 的
  tag/体积/上下文）；**第 5 节是本机实测**，口径与方法已注明。
- 标「未确认」的字段表示公开资料中没有可信来源，未做猜测填充。
- 实际体积、上下文与速度会随量化档位、Ollama 版本、KV cache 设置而变；
  拉取前建议在 ollama.com/library 上核对一次当前 tag。
- 表中混有个别社区评测口径的数据（如 SWE-bench Verified 分数），
  不同来源的测试脚手架不同，**只宜横向比较量级，不宜当精确值用**。
- 第 1~4 节的分数/排名未在本机复测；第 5 节的实测数字**只对本机配置成立**，
  换硬件需重跑 `python tools/bench.py`。
