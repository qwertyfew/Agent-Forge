# 模块入门指南：Journal 与 WritePolicy (rerun49)

本指南旨在帮助新加入维护团队的成员快速理解 `journal.py` 和 `writepolicy.py` 的设计初衷、核心逻辑以及它们在 AgentForge 工作流中的关键位置。

## 1. 模块职责与背景

### agentforge/journal.py (运行日志)
**解决的问题：** 解决“模型可见即已记录”的追溯难题。
在复杂的 Agent 执行过程中，模型可能会因为压缩策略（Compressor）或长上下文处理导致输入内容发生变化。如果没有 `journal`，当评测发现模型输出异常时，我们无法准确还原模型在某一特定轮次看到的真实 Prompt（是原始文本还是被压缩后的摘要）。

**核心设计：**
- **Append-only 语义**：日志只增不减，确保历史可追溯。
- **关键快照**：不仅记录消息，还记录 `compact` 事件（包含压缩前后的完整路径），确保即使内容变了，也能找到原始证据。
- **容错性**：作为旁路系统，任何 IO 失败都会被吞掉，绝不阻塞主任务流程。

### agentforge/writepolicy.py (写前策略)
**解决的问题：** 防止模型在重复失败时陷入“无效重写”的死循环。
模型在处理复杂文件（如长文档或表格）时，往往会因为一次小的错误而尝试重写整个文件。如果重写依然失败，模型可能会不断尝试全量重写，浪费大量 Token 且无法修复局部问题。

**核心设计：**
- **证据门槛**：识别“引用密集型”文档（如包含大量路径或代码片段的文件），对这类文件实施更严格的写入限制。
- **草稿机制**：当全量重写被拒绝时，系统强制模型将内容暂存在 `draft/` 目录中，引导模型转向使用 `edit_file` 进行局部修复。

## 2. 关键入口与职责

### Journal 模块
- `journal.new_sid(prefix)`：生成唯一的会话标识符，确保日志隔离。
- `Journal.log_event(sid, event_type, data)`：核心记录函数。支持 `run_start`（初始输入）、`system`（提示词变化）、`message`（消息流）和 `compact`（压缩快照）。
- `MAX_CHARS (200,000)`：日志单条截断阈值，防止单次读取撑爆内存。

### WritePolicy 模块
- `reject_count(path)`：跨 Run 记录同一路径的失败次数。
- `write_policy.check_write(path, content)`：核心守门员。它根据文件类型、历史失败次数和内容变化，决定是允许 `write_file`、强制进入草稿模式还是要求 `edit_file`。
- `_key(path)`：生成路径的唯一标识，用于在不同 Run 之间共享失败计数。

## 3. 模块交互与接续逻辑

这两个模块并非孤立存在，它们深度嵌入到 AgentForge 的执行链条中：

- **Loop 与 Journal**：`loop.py` 在每一轮迭代中都会调用 `journal`。每当模型接收到新消息或触发压缩策略时，`loop.py` 负责将这些状态“推”入日志。这是保证 Agent 行为可观测性的基础。
- **Tools (fs.py) 与 WritePolicy**：这是最关键的拦截点。当 Agent 尝试调用 `write_file` 工具时，工具内部会先请求 `writepolicy` 进行合规检查。
    - 如果 `writepolicy` 返回拒绝，工具不会执行写入，而是返回错误信息给模型，告知模型：“全量重写已被禁用，请修改草稿或使用 `edit_file`”。
    - 这种机制强制将“全量重写”作为最后的手段，而将“局部编辑”作为首选修复路径。

## 4. 新维护者避坑指南

在修改这两个模块时，请务必注意以下几点：

- **不要破坏 Journal 的顺序性**：`journal.py` 的核心价值在于时间线。任何改变事件排序或非原子化追加的操作都会破坏重放逻辑。
- **WritePolicy 的计数逻辑**：`reject_count` 是跨 Run 持久化的。如果你修改了路径生成的 `_key` 算法，会导致模型“忘记”之前的失败记录，从而导致它在同一个文件上反复尝试全量重写。
- **草稿目录的隔离**：`writepolicy.py` 中定义的草稿目录（`draft/`）是专门用于中间状态的，**绝对不能**将其内容作为最终产物提交。
- **性能敏感度**：由于 `writepolicy` 在几乎所有的文件写入操作中都会被调用，任何复杂的正则匹配或耗时的 IO 操作都可能显著拖慢 Agent 的响应速度。
