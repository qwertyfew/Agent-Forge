# 目录布局：一次任务 = 一个案卷（2026-10-20）

## 为什么改

之前一次任务的文件散在三处：证据记录在 `history/<任务>/_records/`、中间文件
直接摊在 `history/<任务>/` 根上、交付物按任务书路径留在 `evals/` 等目录里。
复盘时要来回翻，而且分不清一个文件是「harness 记的」还是「模型写的」。

现在按「过程 / 产物」两类归位，一次任务的全部文件都在 `history/<任务>/` 里。
这与 dsh 的 session 目录同思路：过程（事件、日志、快照）与表面（可见产物）分开，
且都落在同一个可整体归档的目录下。

```
history/<任务>/
  record/                 过程记录（harness 写，不由模型写）
    evidence.jsonl        读过哪些文件的哪些行；每次写盘落成哪个版本
    citations.jsonl       每次写盘的引用核查结论（refs / with_line / inside_read / outside_read）
    versions/<扁平路径>/  每次成功写盘的全文快照（多版本并存，谁都不覆盖谁）
    work/                 模型写的中间/过渡文件（草稿、提取片段、临时脚本），保留子目录
    run/                  这一轮怎么跑起来的：prompt.txt / dispatch.py /
                          events.jsonl（SSE 全部事件）/ raw.log / reply.txt / tools.txt
  output/                 最终产出：收尾时按声明路径镜像一份（可含子目录）
```

`output/` 只在**真有交付物**时存在：停掉或失败的任务（rerun30/32/33）不会凭空多一个空目录，
它们留下的半成品在 `record/work/` 里——「没交出来」本身就是要能一眼看出来的事实。

交付物本身仍留在任务书写的位置——代码类任务改的就是仓库里的文件，搬走会把工程
改坏。`output/` 是**案卷副本**，用来回答「这次任务产出的东西对不对」。

## 根目录逐个说明

| 目录 | 作用 | 属于 |
|---|---|---|
| `agentforge/` | 后端核心：主循环、编排、闸门、工具、记录、骨架、证据 | 代码 |
| `web/` | 前端单页（由 `webui.py` 提供） | 代码 |
| `webui.py` | HTTP 服务：SSE 事件流、任务台账、静态页面、重启/停止接口 | 代码 |
| `service.py` | 看门狗：守护 webui 进程，读 `.run/restart.flag` 自动重启 | 代码 |
| `run.py`、`start.bat`、`stop.bat` | 启动入口 | 代码 |
| `skills/` | 内置 skill（每个一个目录，含 `SKILL.md`） | 配置 |
| `tools/` | 测试脚本（`test_*.py`）与工具壳（`ops.py` 等） | 代码 + 测试 |
| `scripts/` | 运维脚本：`start.sh`、`dispatch_task.py`（派发一轮并归档运行日志）、`check_deliverable.py`（交付物核查）、`migrate_task_layout.py`、`migrate_run_logs.py` | 代码 |
| `docs/` | 设计文档、对照报告（**人写的**，不是任务产出） | 文档 |
| `evals/` | 评测：`tasks.yaml` 任务集、`reports/` 分析报告、`runs/` 历次交付物样本、`results/` 结果 JSON（不入库）、`.run/` 任务集保存前的旧版备份 | 评测 |
| `external/` | 收编的第三方仓库（mini-swe-agent、learn-claude-code），不入库 | 只读素材 |
| `examples/` | 示例配置与脚本 | 文档 |
| `debug/` | 开发期一次性脚本（probe、rea_task3 等）；`debug/archive/` 放历史事件日志与截图（可整体删） | 开发期 |
| `history/` | **任务案卷**：每个任务一个目录，`record/`（含 `run/`、`work/`、`versions/`）+ `output/`；`_archive/` 收历史运行日志与一次性草稿 | 运行产物 |
| `.run/` | 服务运行期目录：`service.pid`/`web.pid`、`restart.lock`、`service.log`/`web.log`/`ollama.log`、`dispatcher_failures/`。一轮跑完的日志会自动归进案卷 | 运行期 |
| `.agentforge/` | 运行期状态：`skeletons/`（骨架档案）、任务笔记、`memory.md` | 运行期 |
| `.drafts/` | 被核查拒绝的内容暂存（供局部修正，不是交付物） | 运行期 |
| `.sessions/` | 会话记录 | 运行期 |
| `config.yaml` / `config.lanrun.yaml` | 通用配置 / 本机配置（后者不入库） | 配置 |
| `models*.json` | 模型注册表（`models.json` 含密钥，不入库） | 配置 |
| `Dockerfile` / `docker-compose.yml` | 容器化 | 部署 |

## 闸门只看文件（dsh 式）

改完之后，每一道判定都能指到具体文件，出问题能立刻分清是「产出不对」还是「审核异常」：

| 判定 | 读的文件 |
|---|---|
| 引用是否编造（路径 / 行号） | `record/evidence.jsonl` 里的读区间 + 源文件本身 |
| 骨架填完没有 | `output/`（或声明路径）的正文 + `.agentforge/skeletons/` 的建档 |
| 任务书必填项写全没有 | 交付物正文 vs `skeleton.required_items(任务书)` |
| 本轮是否真写过 | `record/evidence.jsonl` 的 write 行（不再只靠内存里的 file_log） |
| 任务产出了哪些文件 | `record/evidence.jsonl` + 收尾镜像的 `output/` |

一句话：**内存只是缓存，磁盘才是事实**。所以判错时可以逐层对照——
「模型写了什么」看 `record/versions/`，「模型读到什么」看 `record/evidence.jsonl`，
「最后交出来什么」看 `output/`，「判定为什么这么下」看闸门读的是哪一份。

## `.run/` 与案卷的分工

`.run/` 是**运行期工作区**，不是存档：`service.pid`、`web.pid`、`restart.lock`、
`service.log`、`web.log`、`ollama.log`（ollama 子进程的日志，服务停着时才能轮转）、
`dispatcher_failures/`（调度失败样本）。一次跑完，它的运行日志就该进案卷：

| 文件 | 去处 |
|---|---|
| `<run>.events.jsonl` / `.raw.log` / `.reply.txt` / `.tools.txt` / `.prompt.txt` | `history/<任务>/record/run/` |
| `dispatch_<run>.py` | 同上，改名 `dispatch.py` |
| 找不到对应任务目录（历史目录已清） | `history/_archive/run-logs/<run>/`、`_archive/run-scripts/` |
| 一次性草稿（commit_msg、gptoss 原始输出） | `history/_archive/notes/` |

自动归位：`scripts/dispatch_task.py` 跑完调 `layout.record_run_dir`（按台账里
【本轮编号：X】→ created_at → 目录名）。历史遗留用
`python scripts/migrate_run_logs.py --apply` 一次性搬完（可重复执行）。

## 迁移

`python scripts/migrate_task_layout.py --apply`：把历史任务的 `_records/` 改名 `record/`，
根上散落的报告移进 `output/`、临时文件移进 `record/work/`。脚本可重复执行。

`python scripts/migrate_run_logs.py --apply`：把 `.run/` 里的历次运行日志按轮次编号
归进对应案卷的 `record/run/`。两个脚本都是「预览 → 加 `--apply` 才动手」。

老任务（`20261017-*`、`20261018-*`）只有 `output/` 没有 `record/`，因为记录机制是
20261019 之后才上线的——这些任务的过程数据本来就不存在，不补空目录充数。
