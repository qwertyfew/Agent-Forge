# PTC 常驻 + 能力缺口台账诊断（2026-10-19）

## 一、能力缺口台账诊断结论

`能力缺口`栏（`.agentforge/gaps.json`）此前累计 75 条事件 / 6 个不同条目。逐条归因：

| 条目 | 次数 | 性质 | 是否架构缺陷 |
|------|------|------|--------------|
| `write_file` 引用核查未通过 | 34 | evidence 闸门**正确拦截**伪造引用（模型引用了没读过/不存在的文件）。是功能生效，不是 bug。 | 否 |
| `read_file` 文件不存在 | 25 | 模型逆向分析 `external/` 仓库时**路径幻觉**（如 `learn_claude_code` 实际是 `learn_claude_code`）。工具正确报错。 | 否 |
| `list_dir` 路径不存在 | 12 | 同上，路径幻觉（含 `agentforge/web` 这种拼错）。 | 否 |
| `edit_file` 未找到待替换文本 | 1 | 模型 old_string 写错。 | 否 |
| `tool_missing · git.clone` | 2 | 模型用 `git.clone`（点号），注册表是 `git_clone`（下划线）——**分隔符不匹配**，被误判为「工具缺失」。 | **是（已修）** |
| `tool_missing · this??...?` | 1 | 工具调用名是任务原文泄漏的乱码——**解析健壮性边缘问题**，污染了台账。 | **是（已修）** |

**结论**：绝大多数不是当前架构的真实缺陷，而是「旧架构逐次直接调用」放大了模型路径幻觉的噪声面（每多一次直接调用就多一次记 gap 的机会）。让 PTC 常驻会自然收敛这类噪声（脚本内工具失败不再逐条记台账）。其中**两个是真实可修的架构问题**，已修复（见下）。

## 二、真实修复（已落地）

1. **工具名分隔符归一化**（`loop.py::_execute`）：调用前先把 `. - 空格` 归一成 `_` 再查一次。
   `git.clone` → `git_clone` 自动命中，不再误报 `tool_missing`。
2. **乱码工具名格式校验**（`loop.py::_is_malformed_tool_name`）：名字含空白 / CJK / `?!` 等特殊符号 / 超长，判定为「任务原文泄漏 / 乱码」，**不记台账**，直接退回格式错误。合法的大小写 / 点号差异不当作乱码（交由归一化 / 选择器建议处理）。

旧台账已备份至 `gaps.json.archive-2026-10-19` 并清空，使栏位反映新架构状态下的真实缺口。

## 三、PTC 常驻（程序化工具调用）

`config.ptc_resident` 默认 `True`。行为变化：

- **模型直接拿到的工具 schema 只剩「脚本面」**：`ops_batch` + `ask_user` + `find_tools`。
  其余所有工具只在系统提示的「可编入脚本的工具」索引里列名字，模型必须在脚本里用
  `tools.call("工具名", ...)` 调用。
- **顶层硬闸**（`loop.py` 工具调用循环）：常驻模式下，模型若直接发非脚本面工具调用，
  被拦截并提示改走 ops_batch——防止绕过系统提示。关闭 `ptc_resident` 则回到原行为。
- `ask_user` 仍可直接调用（脚本线程里弹窗必死锁，是唯一例外）；`find_tools` 保留以便脚本前查参数。
- 脚本内 `tools.call` 仍走 `Agent._execute` 同一条管道：审批 / 证据台账 / file_log / 越界权限全部继承；
  write/command 类工具仍需运行是完全访问权限。
- 不再需要逐工具的中间结果回传（符合预期），脚本 `print` 的内容即唯一回传。

配套测试：`tools/test_ptc_resident.py`（16 项，全过）。`test_toolselect.py` / `test_contract_gate.py`
因验证的是「非常驻」路径，已显式 `cfg.ptc_resident = False`。
