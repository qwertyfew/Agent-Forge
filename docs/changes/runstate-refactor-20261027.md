# 有界重构（一）：运行状态唯一事实源 + 界面单一渲染入口

（2026-10-27，起因是一次「停止后『执行中』角标不灭」）

## 一、为什么动结构，而不是继续打补丁

同一天里连续出了三个 bug，表面无关，其实是同一件事的三种表现：

| 现象 | 表象原因 | 真实原因 |
|---|---|---|
| 停止后「执行中」呼吸灯不灭 | `syncTopRun()` 没在轮询里被调用 | 界面刷新函数散落在各事件分支，没有统一入口，漏一个就不同步 |
| 追问被新建成另一条任务 | `send()` 里 `if(viewingHistory) resetChat()` | 与「追问续接」语义直接冲突的一行，一直没人发现 |
| 停止点了像没反应 | 事件流断了没人收尾 | 界面没有「停止中 → 已停止」的中间状态可表达 |

共同点：**同一件事有多份状态、且没有单一的更新入口**。继续在原地打补丁只会不断重复这类问题，所以做一次有界重构——只动「运行状态」这一层，不动任务编排、工具、闸门等其余部分。

## 二、服务端：`agentforge/runstate.py`

运行期状态的唯一事实源，取代原先分散在三处的实现（停止标志字典、thread-local
当前任务、台账 status 各说各话）。

- 生命周期状态机：`queued → running → stopping → (stopped | done | error)`；
- `stopping` 是新增的**中间态**：表达「已请求停止、运行侧还没退出」，让「点了停止
  但还没退出」有明确说法，而不是让界面去猜；
- 停止标志与状态同处一把锁下，派生查询只有一个口径（`running_ids()` 与旧
  `runcontrol` 保持一致：已进 stopping 的不算「在跑」）；
- `runcontrol.py` 退化为门面，保留原有函数名与语义，所有调用方零改动。

分工：**run_state 管「现在到底在干嘛」，TaskStore 管「历史与展示」**，任务收尾时
以 run_state 的终态为准落盘，两边不再各自判断。

## 三、前端：`renderRunUI()` 单一渲染入口

原先 `syncTopRun` / `syncComposer` / `renderRunBar` 被 27 处代码零散调用，谁漏了
谁不同步。现在：

- 三个函数只被 `renderRunUI()` 调用；
- 任何状态变更（发起、接管、轮询、收尾、停止、切视图）一律调 `renderRunUI()`；
- 用静态断言把这条不变量钉住（见下）。

## 四、护栏

`tools/test_runstate.py` 共 28 条断言，覆盖：

1. 状态机语义（登记/排队/停止/终态不被改写/重复登记换新标志/release）；
2. 当前任务的线程隔离；
3. `runcontrol` 门面与底层行为一致（保护所有老调用方）；
4. **静态检查**：三个渲染函数只允许在 `renderRunUI` 内被调用；
5. **静态检查**：续接不允许再出现「回看即清空线程」，且 `contOf` 不得依赖
   `taskData`（刷新后竞态）。

前四条防「再犯」，后两条把当天修掉的两个 bug 钉死。

## 五、后续

这一步只覆盖了「运行状态」。仍待收敛的（按优先级）：

1. 前端其余 60+ 个顶层全局状态收成一个 store，`renderRunUI` 的模式推广到
   侧栏任务列表、上下文计量、模型池提示；
2. 服务端把算力闸门（`_COMPUTE_GATE`）与 `runstate` 合并，排队/放行也走同一状态机；
3. `orchestrator.py`（1228 行）与 `loop.py`（1971 行）按职责再切分。
