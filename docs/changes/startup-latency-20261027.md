# 开局耗时解剖：为什么一句「你好。我叫张三」要 16 秒

（2026-10-27，依据本机 Ollama + `gpt-oss:20b`、16GB 显卡的实测时间线）

## 一、问题现象

Web 界面上发一句「你好。我叫张三」，16 秒才出第一个字。用户的两个直觉都没错：

- 一个任务只用一个模型，为什么要去加载别的模型？
- 界面早就打开了，为什么还在加载模型？

## 二、实测解剖（CLI 路径，逐事件时间戳）

```
[ 0.67s] CLI 就绪
[ 2.05s] 预热扫描完成 → 健康门禁开始
[15.77s] gemma4:12b  探活通过    ← 加载 13.7s
[22.95s] gpt-oss:20b 探活通过    ← 把 gemma 挤掉，加载 7.2s
[35.31s] qwen3.5:4b  探活通过    ← 又把 gpt-oss 挤掉，加载 12.4s
[35.31s] 这时才「选模型」——结果派给了线上 DeepSeek V4-Pro，然后报错
```

三处结构性浪费：

1. **门禁时机错位**：`ollama_health_gate` 放在「选模型」之前，拿的是**整个模型池**，
   于是对每个本地模型挨个做真实生成探活。探活 = 一次权重加载 = 12~20B 模型各 5~14 秒，
   而且后一个必然把前一个挤出显存——用户白等 33 秒，最后任务要用的那个模型还是要重新加载。
2. **探活参数与真实调用不一致**：探活不带 `num_ctx`（Ollama 默认 4K），真实调用是 32K。
   Ollama 按「模型 + 影响加载的参数」缓存 runner，两者参数不同就是两个 runner，
   于是「刚加载完又加载」。这正是「我已经打开了，怎么还在加载」的直接原因。
3. **种子复制走全树**：`layout.seed_output` 用 `base.rglob("*")` 遍历整个工作区，
   `.venv` / `node_modules` / `history` 动辄几万个文件全走一遍才判断要不要拷。
   实测 1.3~4.1 秒，全花在走目录上，真正拷进去的只有几百个。

附带发现一个模型池 bug：`models.json` 里启用项写的是 `local:gpt-oss:20b`（模型名），
而模型目录里的 id 是 `local:gpt-oss`（配置 key），两边对不上 → 勾选整体失效 →
任务池退化成「所有能跑的模型」按能力分排序 → 一句「你好」被派给线上旗舰模型。

## 三、四处修复（都在流程本身，不加任何按关键词分叉的特殊路径）

### 1. 门禁只探本次任务真正要用的模型（`orchestrator.py`）

- `ollama_health_gate` 的调用点从「选模型之前」挪到「计划确定之后」；
- 探活对象由 `_local_model_keys(entries, agent)`（整池）改为 `_plan_local_keys(plan, agent)`
  （计划里出现过的模型，去重、只留本地）。
- 门禁的语义因此变得严格正确：它回答的是「**我这次要用的**模型能不能生成」，
  而不是「给整张模型清单体检」。

### 2. 探活本身变便宜（`llm.py`）

- `warmup(model, options)` 接收模型加载参数，探活请求带上与真实调用**完全相同**的
  `options`（含 `num_ctx`）——这次探活**就是**那次加载，不再是两个 runner；
- 加 `num_predict=1` + `think=false`：只验证「能吐 token」，不等它把「hi」答完，
  也不让思考型模型先烧几百个思考 token；
- 成功判定放宽到「正文 / 思考 / eval_count 任一非空」——单 token 预算下，
  思考型模型这一个 token 可能落在 `thinking` 里；
- 4xx 时退回最保守的 payload 再问一次（旧版 Ollama 不认 `think`），别把参数问题误报成「模型不可用」；
- **不做结果缓存**：探活是对「此刻」的判定，模型是否还驻留由 Ollama 的 `keep_alive` 管，
  缓存会把「已经被卸载」误判成「还活着」。实测模型驻留时一次探活 0.2~0.5 秒，不值得为它引入状态。

### 3. 服务启动后台预热（`ollamaguard.py` + `webui.py`）

- 新增 `pick_prewarm_entry()` / `prewarm()` / `warm_state()`：挑「第一条任务最可能用到的
  本地模型」（路由默认模型优先，否则池内能力分最高者），用与真实调用一致的参数加载一次；
- `serve()` 拉起 HTTP 服务后，在 daemon 线程里做这件事，**界面不等它**；
- 只预热**一个**模型：显存只够常驻一个大模型，同时预热多个等于让它们互相挤出去；
- 在线/付费模型不预热（没有加载成本，预热只是多一次请求）；
- `/api/health` 增加 `ollama_warm` 字段（`{ok, model, seconds, detail}`），
  界面可据此提示「默认模型正在加载」而不是让人以为卡住。

配置开关（`config.yaml`）：

```yaml
ollama:
  prewarm: true      # 服务启动时后台预热默认本地模型；false = 首个任务现加载
```

### 4. 种子复制剪枝（`layout.py`）

- `rglob` 换成 `os.walk` + 原地剪枝（排除目录既不进也不产生 stat）；
- 新增 64MB 总字节上限（原来只限量 500 个文件，单个最大 5MB，最坏能拷几个 GB）；
- 语义不变：仍然只拷工作区种子，拷不全的部分由读侧镜像的「根回退」兜底。

### 5. 启用匹配容忍别名（`modelstore.py`）

启用判定从「只比 id」改为「比 id 或模型名」（`local:gpt-oss:20b` 与 `local:gpt-oss`
都算命中）。历史版本/前端可能把模型名写进启用列表，只比 id 会让勾选静默失效。

## 四、验证数据

同一句「你好。我叫张三」，走同一条 `run_task` 路径：

| 指标 | 修改前 | 修改后 |
|------|--------|--------|
| 开局到首字（CLI 冷启） | 35.3s | 8.7s（其中 4.9s 是唯一一次加载）/ 已驻留 4.3s |
| 模型加载次数 | 3 次（13.7 + 7.2 + 12.4s） | 1 次 |
| 工作区种子复制 | 1.3~4.1s | 0.8s |
| 实际使用的模型 | 线上 DeepSeek V4-Pro（并报错） | 本地 `gpt-oss:20b` |
| 服务启动 `serve()` 返回 | — | 0.37s（不等预热） |
| 启动后台预热 | — | 5.1~6.2s 完成 |
| 首条消息（预热后） | 16s | 3.4~4.0s |
| 单次探活（模型驻留） | 0.6~2s（还会触发重新加载） | 0.20~0.51s |

探活期间 `/api/ps` 全程稳定在 `gpt-oss:20b`、11GB 显存、`context_length=32768`——
没有任何重复加载。

## 五、遗留与下一步

- **模型思考长度才是剩下的波动来源**：同一句问候，`gpt-oss:20b` 的事件数在 44 / 84 / 252
  之间跳，对应 3.5s 与 15.4s。这是模型自身行为（`think: true` + 两万多 token 上下文），
  流程侧已无可削之处；要再快只能动思考预算（`num_predict` / 关闭 think）或换小模型。
- 若长时间不开界面（超过 `keep_alive` 15m）后又想首条消息不等待，可把 `keep_alive` 调大，
  代价是模型长期占着显存。
