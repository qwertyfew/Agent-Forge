# Token 经济诊断与架构演进：从「多角色仪式」到「极简闭环 + PTC」

（2026-10-19，依据 rerun14 全量事件日志 + dsh-ops 调研）

## 一、rerun14 的 token 解剖（实测）

一个任务（逆向分析 + 产出差距清单）消耗：

| 指标 | 数值 |
|------|------|
| 模型调用轮次 | ~130 轮 |
| 每轮 prompt | 8k → 35k，随工具结果累积线性增长 |
| 每轮 completion | 30–600 token（多数是几十 token 的一个工具调用） |
| prompt : completion | ≈ 20 : 1 |
| worker 固定开销 | 每次员工启动 ~7–9k（系统提示+工具定义+任务书+warmup）× 11 次 |
| leader 判定轮 | 6 轮，每轮 15–34k prompt |

**结论：token 大头不是「干活的输出」，而是「每轮工具往返都重发整个上下文」。**
模型读一个 2 万 token 的文件后，这个文件在后续每一轮 prompt 里都被重发一遍——
O(n²) 行为。130 轮里 90% 的轮次模型只说「调 read_file/search_code」，决策 token
几十个，运输成本上万。

## 二、三个 token 黑洞（按杠杆排序）

1. **工具往返 × 全上下文重发**（占绝对大头）：「读 10 个文件、grep 5 次、
   汇总」= 15+ 轮，每轮重发全量历史。PTC（程序化工具调用）把它压成 1 轮：
   模型写一段脚本，脚本在沙箱里循环调工具，只有最终紧凑结果回给模型。
   dsh-ops 实测省 65–97% token（自报口径，DeepSeek V4.1 Flash）。
2. **多角色消息传递**：任务书转写、worker_brief 注入、leader 每轮重读计划+摘要
   再写裁决、汇总重写。小任务被拆成 11 步 + 6 轮 leader 判定，仪式性开销显著。
   「为了多 LLM 而多 LLM」的批评在这一半是成立的。
3. **固定开销 ×N**：系统提示 + 工具定义每次员工启动全量进 prompt；warmup
   注入每个员工一份。

## 三、演进方案（吸收 DSH 形态，不推倒重来）

### T1 · PTC 工具层（最大杠杆，先做）

新增 `ops_batch` 类工具：模型写 Python 脚本 → 沙箱内执行 → 脚本通过
agentforge 工具 SDK（read_file/search_code/list_dir/run_command…）自由组合循环
→ **只有最终紧凑结果（结构化 Outcome）回给模型**。

- 走现有 registry/Guard：权限、审计台账（evidence ledger、file_log）全部继承，
  read 硬闸不受影响——脚本里的读也记账。
- 结果预算：单脚本返回 ≤400 token 摘要 + 按需引用（文件落盘，模型要用再读）。
- 预期：分析型步骤的轮次降 60–80%。

### T2 · 极简单循环成为默认路径（DSH 形态）

单任务、无并行需求 → 不再走 leader 拆步：一个 agent、一条循环、tasksession
做现场记录。leader/worker 编排只保留给**真并行的批量任务**（泳道已有）。
router 保留（选模型不是仪式，是刚需）。

### T3 · 每轮只带关键信息（上下文预算）

- 工具结果老化替换：超过 K 轮的旧工具输出压成一行摘要（summary_replace 事件，
  日志不动、视图替换）——Surface 思想用到 worker 自己的上下文上。
- 任务书/系统提示瘦身：固定开销从 7–9k 压到 3k 内；warmup 只进 tasksession
  Surface，不再整段注入每个员工。

### T4 · 契约闸门与诚实层原样保留

收工对账、引用硬闸、产物核查与 token 优化正交——极简架构更需要它们
（单循环没有 leader 兜底，程序核查就是唯一防线）。

## 四、明说不做的

- 不引入 Rust 工具核心（dsh-ops 的做法）：Python 单机场景收益不抵复杂度。
- 不做 Cordis 式微内核插件化：当前规模不需要。
- 不删评测/闸门体系：那是从 rerun12/14 事故里长出来的，是资产不是负担。

## 五、预期收益（以 rerun14 为基准）

轮次 130 → ~40；prompt 总量按每轮均值同步下降；本地跑任务的 GPU 时长
（29 分钟）预计降到 8–12 分钟；云端计费口径下同比例省钱。
