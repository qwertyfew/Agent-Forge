# PTC 常驻验证（rerun20）诊断报告

PTC 常驻（`ptc_resident=True` + 修复 import/tools 冲突 + 去重/回显修复）在**本任务（长报告 + 弱执行模型 gemma4:12b）上是负收益**：

## 二、根因链条

### 1. PTC 红利被模型行为抵消（token 不降反升）
- 模型在脚本里 `print(call("read_file", ...))` **全量回传**文件正文（4 次 ops_batch 的 result 达 2447 字符），而非「提炼后只回结论」。
- PTC 本应压缩的上下文，被模型的「全量 print」抵消；叠加 O(n²) 逐轮重发，总 token 翻倍。

### 2. 引用核查 × 弱模型 = 死循环（交付物未落盘）
- ops_batch #6 首次 `write_file` 被引用核查拒绝（交付物里大量编造引用：`README.md L28`、`src/agents.py（推测核心逻辑）` 这类复现不到）。
- gemma4:12b 看到拒绝后**不会删改编造引用**，而是「重读 16 文件 + 重写完全相同 content」——#8/#10/#12/#13 的 code 均为 3035 字符的同一份 content，#11/#14 各重读 16 文件后再写同 content。
- 死循环到 22 轮上限，交付物始终未写入。

### 3. 真实架构缺口：T4 契约闸门在 PTC 路径下失效（新增）
- T4 契约闸门（`loop.py` 顶层 tool_calls 拦截）只拦**顶层**调用；PTC 常驻后 write_file 发生在 ops_batch 脚本**内部**，顶层看不到。
- 结果：rerun20 全程 **0 次**契约闸门事件，之前 T4 建立的「收尾诚信核查 / 虚报拦截 / 逼模型补写」在 PTC 路径下完全失效。这正是 rerun17 能逼出真实落盘、rerun20 不能的根本原因。

## 三、已确认的非问题
- 修复 #2（写类工具结果强制回显）**生效**：`↳ write_file: [错误] 引用核查未通过` 已正确回显，模型确实看到了拒绝原因。
- 修复 #1（ops_batch 不去重）**生效**：写脚本重试不再被「重复调用」误拦。
- `import tools` 冲突修复**生效**：rerun20 无 `has no attribute 'call'` 错误。
- 台账 0 条是「引用核查在脚本内拦截，未走到顶层 gap 记录」所致，非 bug 消失。

## 四、建议（待用户拍板，未擅自改动）
1. **补 T4 延伸到 PTC（修复真实回退）**：ops_batch 执行后，若脚本内调了写类工具，把脚本内 write_file 的落盘情况纳入收尾对账；或拦截「脚本结束但契约交付物未落盘」。
2. **缓解 token**：引导模型在脚本里「只 print 结论不 print 全文」；或对脚本内 print 施加更激进的 budget 截断。
3. **印证此前判断——分模型策略**：PTC 常驻只适合强推理模型（规划层）；弱执行模型做长报告应回到「直接调用 + T4 契约闸门」。即退回混合模式 / 自适应触发，而非强制常驻。

## 五、验证序列
- rerun18：import tools 冲突，ops_batch 全失败（假干净）。→ 修复 `call()` 主 API。
- rerun19：去重守卫误拦写脚本 + 写结果回传丢弃，交付物未落盘。→ 修复去重排除 + 写结果回显（commit ab2be7a）。
- rerun20：修复后验证，暴露 PTC 在弱模型+长报告上是负收益 + T4 被绕过。
