# 修复两处架构缺口：压缩可重放 + 写前策略

（2026-10-20。对应 `docs/agentforge-vs-dsh-20261020.md` 第九节差距 2 与差距 4。）

## 一、压缩破坏了「模型可见即已记录」

### 根因

`Agent._compact()` 每轮调用 `context.Compressor.compact()`，压缩结果**只替换内存里的
messages**。日志侧只有两种东西：leader 路径的 `TaskSession`（单任务路径根本没有），
以及评测派发脚本落盘的 SSE 事件流。两者都看不到压缩——压缩后「模型到底看到原文还是
摘要」只能靠猜，评测归因（rerun22–26 的 token/耗时分析）因此缺一环。

### 修复

新增 `agentforge/journal.py`，一次 run 一份 append-only 事件日志：

| 事件 | 内容 |
|---|---|
| `run_start` | 模型、任务原文、历史条数、relay 与否、契约路径 |
| `system` | 系统提示**变化时**记全文（warmup / skill 注入 / 权限模式都会让它变） |
| `message` | 逐条模型可见消息（原样存，含 `tool_calls`），回灌消息标 `_source=system` |
| `compact` | 策略、前后字符数、**前后快照路径**、消息条数 |

- 快照单独落 JSON（`.agentforge/journal/<sid>/step-NNN-{before,after}.json`），
  事件里只放路径与统计——日志体积与上下文长度解耦。
- `journal.replay(path)` 折叠事件还原上下文：遇到 `compact` 就用 after 快照整体替换，
  与 dsh 的 Surface replacement 同义（原文仍完整留在之前的 `message` 事件里）。
- 系统提示不进快照，只由 `system` 事件表达，避免重放时被当成普通消息。
- 记账是旁路：开不出文件就退化为 `None`；`cfg.journal=False` 可整体关掉。
- 每次 append 开后即关，不在 run 期间常驻句柄（生成器可能被提前放弃，Windows 上会挡住清理）。

`webui.py` 增加 `compact` 分支：播报「上下文压缩（strategy）：A → B 字符」，
事件同时下发前端，评测事件流里也留痕。

### 验证

`tools/test_compact_journal.py`（18 项）：压缩触发、快照完整性、
「重放 == 模型实际收到的历史」、压缩后的新消息接在快照之后、回灌消息归属、开关关闭不落盘。

## 二、只有写后核查，没有写前策略

### 根因

内容核查（引用、语义、语法）全在 `write_file` 内部——**模型把整篇生成完之后**才被打回。
被拒 = 整篇重写：rerun23 里引用核查连拒 4 次，每次三千字从头再来；同一轮 7 次宣称已写入
而文件不存在。dsh 的对应机制是 `fs/write-intent`：写之前先问策略。

### 修复

新增 `agentforge/writepolicy.py`，三层，全部在落盘之前：

1. **证据门槛**（`intent_gate`）：内容含 ≥3 处带目录的项目引用（引用密集型文档），
   而本任务 `read_file` 次数为 0 → 直接拒收。返回「先读这些文件」的清单（最多 6 个，
   只列存在且未读的）。引用只能来自读过的代码——这是 rerun22「路径全对、结论全错」的根因。
2. **草稿暂存**（`reject_message`）：任何拒绝（引用 / 语义 / 语法）都先把内容写进
   `.drafts/<消毒路径>`，回传草稿路径 + 逐条定位「草稿第 N 行」+ 局部修正指令
   （`edit_file` 改点到的行，再 cp 到位）。被拒不再等于丢掉重来。
3. **重复拒绝升级**：同一路径第二次被拒，明确「禁止重写全文，只允许基于草稿做局部替换」。

出口统一：三种拒绝共用 `reject_message`，措辞与定位格式一致；`.drafts/` 已加进
`.gitignore`，不参与交付核查。系统提示新增一节「写文件的两条硬规则（架构层真的会拦）」，
把规则在生产前就说清楚，而不是等它写完再打回。

PTC 常驻下所有写盘仍走 `fs.write_file`（脚本里的 `call('write_file', ...)` 也是），
所以两层天然覆盖顶层与脚本两条路径，不需要在 `ops_batch` 再加一套。

### 验证

`tools/test_prewrite.py`（19 项）：零读拒收并给必读清单、读过即放行、普通文件不设门槛、
拒绝时草稿落盘且内容一致、定位到草稿行号、第二次升级措辞、语义拒绝同出口、
开关关闭不拦、`draft_ready` 查询。

## 三、行为变化与代价

| 变化 | 代价 |
|---|---|
| 每次 run 多一个 journal 目录（只在有内容时写） | 磁盘占用与工具输出量同阶；单条上限 200K 字符，超出标 truncated |
| 引用密集型文档在零读时直接写不进去 | 可能多一轮 read_file——但省掉的是整篇重写 |
| 拒绝后多出 `.drafts/` 文件 | 需定期清理；已 gitignore |
| 系统提示多出一节规则 | ~200 字符固定开销 |

## 四、仍然没做（与 dsh 的剩余差距）

- **Follow-up 通道**：同会话追加仍是新任务，turn 状态与闸门计数归零。
- **Inject 队列化**：守卫回灌仍直接 `_push`，不排队、不合并。
- **写意图再前移**：证据门槛仍在「内容生成之后」，真正的生成前约束只有系统提示那一节。
  下一步可考虑「骨架先行」——先写目录结构（小内容），核查通过再分段填充，把单次
  生成成本压到最小。
