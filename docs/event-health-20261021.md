# 事件流体检：31 轮 / 155 次运行有没有在正确步骤上

2026-10-21。数据源 `evals/results/soak01..31.json` 的过程记录，工具 `tools/event_audit.py`
（`python tools/event_audit.py` 可随时复算）。

## 一句话结论

**判定 96.1% 通过，但「一次设备都没白动」的只有 60.6%。** 返工几乎不吃掉判定——靠
签名提示、写盘核对、verify 重跑，harness 自己把错兜住了；它吃掉的是时间：325 次工具
调用里 98 次（30%）是重复动作，其中 w5 一道题就占 50 次。

> 口径修正（2026-10-22 00:4x）：初版把这 50 次和 `fill_section` 的分节填充混在
> 一起算成 86 次「重写」。`fill_section` 是**增量**填充，同一文件写 6 次正是它的
> 用法（soak04 等 6 轮就是这么干的），算重写属于误伤。剔除后 w5 的白写是 50 次。

分任务看，健康度差别很大：

| 任务 | 均耗时 | 回合/次 | 零错误返工 | 主要问题 |
|---|---:|---:|---:|---|
| q1 纯问答不动手 | 81s | 1.0 | 31/31 | 无——零工具是正确行为 |

| w5 长文 | 174s | 4.7 | 30/31 | **无错，但 23/31 轮整文件写 2~5 次（50 次白写）** |

## 口径

- `turns` = 模型回合数，`calls` = 工具调用事件数，`calls/turn` 越接近 1 说明每一步都在动手。
- 返工分两层：
  - **错误类**：这一步必须重做（空脚本 / 脚本异常 / 签名错 / 定位失败 / 写盘失败）。
  - **冗余类**：不算错，但同一个文件被整写多次，前面的版本直接作废。
- 一次调用只归一类，优先级 空脚本 > 脚本异常 > 签名错 > 定位失败 > 写盘失败。
  理由：soak31 的 c6 有一步既报「参数不对」又报「写入失败」，那是同一个错误的两句话，
  记两次会把返工量直接吹高一倍。
- 写没写进磁盘，只认 `【系统核对·写盘结果】` 里那行「已写入磁盘」。脚本里写了
  `write_file` 不算——soak27 的 w5 就有一次脚本被判空跑，按脚本数会记成重复写。

## 逐任务：哪里是健康的，哪里不是

### q1：31/31 零调用，最健康的一题

纯问答类，31 轮没有一次伸手。`calls=0`、`turns=1`，`tool_must_not` 从没被碰过。
这说明「不该动手时不动手」这条判断是稳定的，不是运气。

### h4：404 是题面要求的，真浪费的是脚本写法

24/31 轮零错误。剩下的 8 次不是判断错，是写脚本写崩了：6 次 `AttributeError: 'str'
object has no attribute 'get'` 和 `NameError`（拿到 404 文本后当成 dict 去 `.get()`），
2 次脚本被判空跑。`fetch_json` 的 404 出现 15 次，那是这题的目的（仓库不存在），
不算返工。

同一份数据里还有个好消息：h4 的 grounding gate 在 soak14 起命中过几次，说明闸门在工作，
且都是「先瞎报再被拦回」，不是误伤。

### c6：12 次签名错，一次错换一个回合

12 次 `param_err` 全是同一类：模型用 `edit_file(path, content=...)`，而工具要的是
`(path, old_text, new_text)`。另有 6 次 `edit_miss`——`old_text` 写了但没对上，
或者「找到 3 处匹配，存在歧义」。

健康形态是 `read_file → write_file → verify`（12/31 轮）或
`read_file → write_file → run_command → verify`（4 轮），合计 16 轮一步不错。返工形态是
`read_file → edit_file(报错) → write_file(兜底)`——**每一轮都靠回包里的
「[参数] edit_file 接受：…」自愈**，自愈成功率 100%，代价是每题多一个回合（约 24s）。

这正是 P10 要治的：签名看不见。已加常驻签名块；2026-10-21 23:5x 的单条探针
（`evals/results/auditprobe.json`）第一次就跑成 `read_file → edit_file → verify` 一把过，
但 n=1，不能当结论。

### f5：14 次先打听工具名

12/31 轮零错误，最差的一题。14 次 `find_tools(query="github_search")` / `("github search")`
——模型不知道该用什么工具，先花一回合查。另有 4 次 `github_search(type=...)` 签名错。

`find_tools` 本身是合法工具，但在这套固定 5 题、工具集不变的场景里，每次运行都要查一遍
说明**工具名没有稳定地出现在模型眼前**，和 c6 的签名错是同一个病。

### w5：一次错误都没有，却是最贵的一题

30/31 轮零错误——**它的问题是另一种**：23/31 轮把 `reports/outline.md` **整文件**写了
2~5 次（`write_file` 成功 81 次，其中 50 次被后一次覆盖），占该题 146 次工具调用的 34%。

先把「写的是什么文件」说清楚：**31 轮里所有写入都指向最终交付物 `reports/outline.md`
一个路径**，没有中间文件、没有草稿文件。81 次 `write_file` + 36 次 `fill_section`，
路径统计里只有这一个值。

两种写法高下立现：

| 写法 | 轮次 | 结果 |
|---|---:|---|
| `write_file` 一次 + `fill_section` ×6 | 6 轮 | 零返工，一节一节填，被拒也只丢一节 |
| `write_file` 只写一次 | 2 轮 | 零返工 |
| `write_file` 整写 2~5 次 | 23 轮 | 50 次里前 N-1 次被覆盖 |

其中约 20 次是**逐字节相同**的重写（soak05 是 400→400、soak14 是 346×3）。回执里其实
已经写着「（内容未变）」，模型看得到但没据此停手。其余约 30 次是改几个字再整写，
soak12 就是 471→471→478。

这一题 4.7 回合/次、174s/次，是五题里最慢的；一个回合平均 37s（主要是把 6000+ token
上下文重算一遍）。砍掉这 50 次白写（1.6 次/轮），单题约从 174s 降到 115s。

## 返工对总时长的账（估算，非实测）

单轮五题合计约 506s（72+108+174+81+71），31 轮约 4.3 小时。

| 抓手 | 白做的次数 | 折算回合 | 单轮省 | 占比 |
|---|---:|---:|---:|---:|
| w5 整文件重写 | 50（1.6/轮） | 1.6 | ~59s | ~12% |
| 签名错 + 打听工具名 | 30（1.0/轮） | 1.0 | ~30s | ~6% |

## 可信边界：`steps` 与 `s` 不能用来切步骤

排查时发现，155 次里有 12 次（全在 w5）事件流的 `s` 会回退，例如
`1,2,3,2,3,4,5,6`。根因是编排层把大任务拆成多个小步骤时各泳道并行推进
（`orchestrator.py:1015` 起线程），事件流里混着两条泳道的计数器。

后果两个，都已处理：

1. **`steps` 不是回合数**，它是「最后一条泳道的计数器」，多泳道时会少算。
   已在 `tools/bench_tasks.py` 里改成数 `step` 事件落 `turns`，并给每条工具记录加
   `task`（泳道 id），下次跑就能把「同一回合连调两次」和「两条泳道各调一次」分开。
   `evals/results/auditprobe.json` 已验证字段落盘（`turns=3`、`steps=3`）。
2. 旧台账没有这两个字段，所以本文一律用**调用次数**统计（与泳道无关，可靠），
   回合数只用来说「一题转了几轮」的概数。

## 回答提问

**大部分情况下是健康的**，但「健康」要分两层说：

- **判断层健康**：31 轮里没有一次未读先写，没有一次碰禁用工具，判定 96.1% 通过。
  **步骤的顺序是对的。** 6 次空脚本（2 次被 `__main__` 判掉、2 次 NameError、
  2 次绕过工具层直连）是写法与环境问题（P9/P5/P11），不是「判断成不该动手」。
- **执行层不健康**：30% 的工具调用是重复动作，集中在三件具体的事上——看不见工具签名
  （16 次）、看不见工具名（14 次）、整文件反复写（50 次）。这三件都不是「想错了」，
  是「看不见 / 收不住」。

所以返工不伤结果，只伤时间；时间正好可以从这三处挤。

## 附：四个追问的代码级取证（2026-10-22）

### 1. 被反复写的是哪个文件？「最终文件只生成一次」这个机制存在吗？

**写的就是最终交付物**，没有中间文件、没有过渡文件。31 轮 w5 的写入路径统计只有
`reports/outline.md` 一个值：`write_file` 81 次、`fill_section` 36 次，全部落在它上面。

**「只生成一次」这个机制不存在。** 现在的逻辑（`agentforge/tools/fs.py` 的 `write_file`）：

1. 算落点（产出目录规则，相对路径强制进产出目录）；
2. 过内容闸：引用核查、表格证据列、契约表头；不通过就**拒收**并把内容存进 `.drafts/`；
3. 落盘；`.py` / `.json` 落盘后跑语法检查，报错就**回滚到原内容**；
4. 每次成功写盘留一个全文版本（`versions/<name>/NNNN-*.py`），回执里写「+x/-y 行」
   或「**内容未变**」；
5. `writepolicy` 只在**被拒**时升级：同一路径第二次被拒就禁止重写全文，只许基于草稿改。
   写成功之后再次整写，没有任何限制。

所以「写 3 次」不是被允许的，而是**没有被禁止**——闸门都在管「写错了怎么办」，
没有一处在管「写对了还写」。

三种写法的实测对比（同一题）：

| 写法 | 轮次 | 结果 |
|---|---:|---|
| `write_skeleton` + `fill_section` ×6 | 6 轮 | 每节单独核查，被拒只丢一节 |
| `write_file` 一次 | 2 轮 | 最省，但整篇被拒就全丢 |
| `write_file` 2~5 次 | 23 轮 | 50 次里前 N-1 次进版本库后作废 |

结论：返工发生在**同一个最终文件**上，是「整写」这个动作被重复，不是「分阶段生成中间稿」。

### 2. `edit_file` 的签名错 / 定位失败，是程序化调用出错吗？

**不是 harness 调错，是模型在脚本里把参数名写错了。** 桥（`ops.py` 的 `sdk_call`）只校验
「工具名存不存在」「权限够不够」，**不校验参数名**——kwargs 原样透传给真函数，
Python 的参数绑定就是校验点，所以错误必然发生在调用那一行：

```python
# 模型写的脚本（soak02 c6）
from tools import edit_file, run_command
new_content = """def _discount(total): ..."""
edit_file(path="src/pricing.py", content=new_content)   # ← 工具没有 content 这个参数
```
```
TypeError: build_fs_tools.<locals>.edit_file() got an unexpected keyword argument 'content'
[参数] edit_file 接受：path（必填）、old_text（必填）、new_text（必填）
```

四次错法：`content=`（8 次）、`old_content=/new_content=`（3 次）、缺 `new_text`（1 次）、
加上 4 次 `github_search(type=)`。全是「按先验猜参数名」——桥和脚本都对，错在名字。

**定位失败是另一类，跟签名无关**，是 `old_text` 与文件不逐字节相等：

```python
# soak05 第二次尝试（参数已经改对了，仍然失败）
old_text="""def member_price(total):
    return round(total * 0.85, 2)

def vip_price(total):           # ← 文件里这里有两个空行
```
真实文件是「三个函数之间各两个空行」，模型只留了一个。`read_file` 的回显带行号栏
（` 1| def member_price...`），模型是**照着回显重打**的，重打时丢了空行。另有 4 次
`old_text` 太短，「找到 3 处匹配，存在歧义」。

这两类的修复方向不同：签名错靠**把签名摊开**（P10，已做）；定位失败靠**别重打、
用能锚定的范围**（按行号区间改，或在失败时用 difflib 给出「最接近的是第 1-10 行」）。

### 3. `find_tools` 打听工具名：放进预热阶段合适吗？

**不合适，放进去没有任何提前量。** 查了实现：

- 预热块（`warmup.py`）只放**项目地图**：目录结构、源码模块清单、外部仓库清单、
  README 摘要、与任务相关的证据候选文件。它和工具索引**在同一份 system prompt 里**，
  每轮重贴（`system_messages()`），同一时刻到达模型；预热还按任务文本缓存 600s，
  搬过去只会更不新鲜。
- 工具可见性三层（`toolselect.py`）：`DEFAULT_CORE` 18 个常驻 → 关键词/能力族命中
  → 剩下的只在索引里列**名字**。PTC 常驻下模型能直接调的只有
  `ops_batch / ask_user / find_tools`，其余在脚本里 `call()`。

所以 `find_tools("github_search")` 的成因不是「说得太晚」，是**只给了名字、没给签名**：
模型知道「有这么个东西」，但不知道参数，于是花一跳去换。P10 的签名块正是补这一跳。

查成熟项目的做法（2026 年的两类主流方案）：

| 方案 | 代表 | 代价 | 对我们的适用性 |
|---|---|---|---|
| 全量 defer + `tool_search` | Anthropic Tool Search Tool（`defer_loading: true`） | 每次检索多一跳；官方明确说「少于约 10 个工具时**全量下发更快**」 | 不划算：我们只有 43 个工具，签名块 710 字符 |
| 核心常驻 + 名字索引 + 按需展开 | Claude Code（内置工具常驻，MCP 工具 defer） | 需要维护核心集 | 就是现状，缺的是「名字旁边那句用途」 |

两个被引用的数字支撑这个判断：工具数超过 **30~50** 选择准确率明显下降（Anthropic），
超过 **~20** 就开始掉（Agent Patterns Catalog 的 Tool Explosion）；反过来，工具定义
占上下文 **<10%** 时上游（Claude Code SDK）默认**不启用** tool search，直接全量下发。
我们现在 43 个工具、常驻 18 个、签名 10 个——**在「全量更划算」的一侧**。

### 4. 脚本异常 / 空脚本：是 PTC 脚本吗？是模型的问题吗？

**是模型写的 PTC 脚本，是模型的问题，但不是「随机手抖」——是可复现的类型假设错误。**

6 次 `script_exc` 全在 h4，脚本长这样：

```python
data = fetch_json(url="https://api.github.com/repos/agentforge-xyz/no-such-repo-9f3a2b")
print(f"Description: {data.get('description')}")   # ← data 是字符串
```

`fetch_json` 的返回**永远是 str**（`web.py:680` 起：404 走 `return "[错误] 请求失败: ..."`，
`raise_for_status()` 的异常被吃掉转成字符串）。模型按「JSON 接口应该回 dict」的先验
写 `.get()`，于是 `AttributeError: 'str' object has no attribute 'get'`。
soak07 第二次更典型：它已经意识到「可能是 str」，写了 `try: data = json.loads(...) except: print(...)`，
但 `except` 分支里没给 `data` 赋值，于是 `NameError`。

6 次 `noop_script`（`[ops_batch] 0 次工具调用`）是另一类：脚本语法合法但没调到工具
（`__main__` 守卫跳过、变量没定义导致提前抛、绕过工具层直连）。P9/P5/P11 已处理。

**可改的一处**：签名块只写了参数、没写返回类型，等于「说了怎么做，没说回什么」。
已在签名块补一行「返回值一律是字符串，不是 dict，不要 `.get()`」，并在 `fetch_json`
那一行点名「404 也返回字符串、不抛异常」。
