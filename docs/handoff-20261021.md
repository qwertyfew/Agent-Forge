## 3. 怎么再跑一跑评测（自己会报编号）

评测跑次从 **rerun64** 起。派发脚本一行就够，`tag` 会自动进任务标题：`[rerun64] …`，
并落 `.run/rerun64.meta.json`（编号 / 任务书 / 耗时 / 工具序列 / 是否声明未核实）。

```bash
cd /d/AI_develop/project/agent-forge
cat > .run/prompt_rerun64.txt <<'EOF'
用 ops_batch 脚本读一下工作区 README.md 的前 20 行，然后用三句话告诉我：
这个项目是什么、它最核心的一条设计原则是什么。不要编造 README 里没有的内容。
EOF

cat > .run/launch_rerun64.py <<'EOF'
import runpy, sys
tag = "rerun64"
sys.argv = ["dispatch_task.py", tag, open(".run/prompt_rerun64.txt", encoding="utf-8").read()]
runpy.run_path("scripts/dispatch_task.py", run_name="__main__")
EOF

C:/Users/admin/.workbuddy/binaries/python/versions/3.13.12/python.exe .run/launch_rerun64.py
```

落盘四个文件，**判读顺序不能反**（反了就会误诊）：

1. `.run/<tag>.events.jsonl` 的 `tool_result` —— 它到底拿到了什么材料
2. `.venv/Scripts/python.exe scripts/ctx_report.py --list 3` —— 材料到它眼前还剩多少（压缩吃了吗）
3. `grounding_gate` 事件 —— 闸门判了什么、依据是什么
4. `.run/<tag>.reply.txt` —— **最后**才看答复，而且每句话都要问「背后有哪条工具输出」

## 4. 这轮修完了什么（**不要重做**，重做等于把已验证的东西再赌一遍）

### 4.1 上下文层（L2，收益最大）

| 病灶 | 修法 | 落点 |
|---|---|---|
| 压缩不累积：`60640→6087` 后下一轮又 `63703` | 模型侧上下文单列 `model_ctx`，压缩结果写回它；展示用 `history` 不动 | `loop.py` `_compact` |
| 越压越长：每轮给已压缩消息再盖 `[已压缩] `（+6 字/轮 ×30） | 已压缩的不再动；没变短就不替换；一条没动就返回原列表（不刷假压缩事件） | `context.py` `truncate_tool_results` |
| 一条退化调用占 5 万字（`<|channel>thought` 连吐） | 入历史前洗：剥控制标记 → 折叠重复行 → 走同一套 `sanitize_script` → 超长掐中段（50,228→247） | `loop.py` `tidy_tool_args` |
| 刚抓的 README 被下一轮摘要吃掉 | 证据保护：`_is_evidence` / `pin_evidence(budget=1400)`，留抬头+前段+全部命令行；摘要后补「任务原文」「已抓源里的命令行」两段 | `context.py` |

### 4.2 取数层（L1）

- `results_look_generic` / `rows_relevant_count`：结果与查询**零词面交集** → 丢弃并明说
  「不是没搜到，是搜回来的不是这个词」，下一步指向 `github_search` / `npm` / `exact_repo_lookup`。
  （rerun59 同一句查询原样重发 28 次，就是这个闸门缺位的代价）
- `tighten_query`：查询全是泛词时不假装收紧，如实说「这句话里没有可精确匹配的名字」。
- `fetch_url`：GitHub 仓库首页优先走 `/repos/{owner}/{repo}/readme`（`Accept: application/vnd.github.raw`），
  HTML 抓不到也兜底；此前 6000 字预算全被导航壳吃掉。

### 4.3 闸门层（L4）

- 闸门升级为**证伪诊断**：只说「犯了什么错 + 确定性依据 + 下一步往哪走」，**永不写「改成 XXX」**。
- 引用抽取两道过滤：`_cli_line_spans`（命令行内 token 归命令核查）、≤4 字全大写斜杠对视为缩写（`CI/CD`）；
  修掉「`docker run … marpteam/marp-cli` 镜像名被当仓库」的误伤。
- `false_provenance`：`provenance_claims` + `fetched_pages(history)`（只认 `[实测 · 网页]`/`[实测 · API]` + 真 URL），
  专治「谎称已从官方源提取/验证通过」却零正文。
- 打回两轮仍不合格 → `render_unverified_note` 由程序盖章，不再让模型自己说「我没核实」。
- `webui.py` 补 `grounding_gate` 事件分支（此前 `yield` 了但前端静默丢弃，rerun16 同款事故）。

### 4.4 评测与文档（L6）

- `dispatch_task.py`：`step` 事件上 `deltas.clear()`（全轮累加会造出「三连刷」假故障）；传 `label`；

- 新增 `scripts/ctx_report.py`：从 journal 重算**系统提示分节 / 工具 schema / 历史按角色与工具 / 压缩记录**。
- 新增三份文档：`eval-findings.md`（六层病灶 + rerun50–62 逐跑 + 判据清单 + 复跑规程 + 残留）、

## 5. 四条预存失败：是测试陈旧，不是功能坏了

| 套件 | 报错 | 真因 | 怎么修 |
|---|---|---|---|

## 7. 用户的工作纪律（照做，别重新论证）

- **先修上游，再加闸门**：检索/组装/上下文没修好时，闸门只会判得更准、模型更没材料。
- **闸门只许证伪，不许给答案**；**不误伤**（误报一次模型就怀疑所有判据）；**必须可见**（`yield` ≠ 到用户眼前）。
- **PTC 常驻不要动**：`web_search` 直连是禁用的，工具一律经 `ops_batch` 脚本内 `tools.call(...)`；
  43 个 schema 只下发 3 个，省 89% 上下文——这是上一轮推翻「工具太多导致压缩频繁」的关键实测。
- **评测脚本和被测系统一样需要证据**：它的数字是证词不是事实；下结论前先按 `step` 切开事件流。
- **每次改完自证**：相关套件全绿 → 重启服务 → 连续 health=200 → 派发 → **自报 rerun 编号**。
- 不要碰 `skills/`、记忆文件、工作区之外的文件；不要删 `.git` 等版本库目录。
- 结论性内容写 `docs/`，不要只写在会话里（换账号就没了）。
