# n3（第三轮占空比）失败归因：机制侧问题清单

- 日期：2026-10-25
- 数据：n1037–n1066（30 批 / 300 次判定，通过 251，83.7%）
- 方法：逐类翻原始结果 + journal 事件流 + 沙盒现场；以 `evals/results/*.json` 为准
  （rounds.jsonl 的用例判定列有旧口径残留，f3 实际 0 失败，勿引用）。

## 一、机制侧（harness）确认 3 处，全部在 ops_batch 链路

### M1 sanitize_script 静默截脚本，丢弃写文件调用（ops.py:151-182）

- 实证：n1064/c5-fib。模型提交的脚本 `call("write_file", path="fib.py",
  content="def fib():\n（裸换行）...")` ——content 字符串里带裸换行，Python 语法非法，
  整段不编译。逐行抢救逻辑最终只保留**最后一行** `print(call("run_command"…))`，
  write_file 被无声丢掉；回执却印「已剥离控制标记与混入的思考文本」（诊断错误）。
- 后果链：write 调用丢失 → run_command 找不到文件 exit=2 → 写盘核对谎报成功
  （见 M2）→ 模型连试 6 次全部空转 → 宣称成功 → 停止拦截预算（2 次）耗尽放行。
- 修法：抢救结果必须与源码 call(...) 清单对账——源码里有写类调用而抢救产物里没有
  就**不采用**，改为明确报「第 N 行语法错误（字符串含裸换行，需转义 \n）」；
  至少在回执里列出「本次被丢弃的调用」。

### M2 写盘核对把失败的 run_command 报成「已写入磁盘 ✓」（ops.py:363-380、535-555）

- 实证：同上 n1064/c5-fib。`【系统核对·写盘结果】`块出现
  `run_command → (未给 path): 已写入磁盘` + `✓ 以上文件已确认存在于磁盘`，
  而该命令实际 exit=2、文件根本不存在。
- 根因：`_ok` 判定只认「[错误]/未写入/[已拒绝]」前缀；run_command 的失败输出
  （`[exit] 2` + stderr）不含这些标记 → ok=True。命令类工具（无 path）本就不该
  进「写盘」报告。
- 修法：writes_reports 只收真正落盘类工具（write_file/edit/fill_section 等带
  path 的）；run_command 单独报「命令执行完成/失败（exit=N）」，永不出现
  「已写入磁盘」；(未给 path) 一律不计入。

### M3 numeric 判定把路径时间戳扫成候选数字（判据口径）

- 实证：n1037/c4，found=[20261024.0, -164158.0]——来自答复里引用的
  `history/20261024-164158/output/...` 路径。本次没造成误杀（4.0 确实没说），
  但会制造噪音，且时间戳撞上期望值时会假通过。
- 修法：numeric 提取前剔除 `\d{8}-\d{6}` 时间戳与 history/ 路径片段。
