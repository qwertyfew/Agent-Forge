# 架构演进与训练过程

> 这份文档是 `README.md` 里《架构演进》与《它是怎么一步步训出来的》两节的**全文**。  
> README 只保留「一页速览」表（20 步各一行），细节在这里——避免 README 被长叙事撑到  
> 读不动（README 是每个会话都要读的入口，不该背着两万字的历史）。

## 它是怎么一步步训出来的

这个 agent 不是一次写成的——几十个 commit、一轮轮真实任务实测，都是下面这个循环转出来的。  
这一节讲**循环本身**：具体某一版的代码会过时，方法是可复用的。

```
先让它能跑 → 拿真实任务测 → 读事件流定位真问题 → 小步修、改完自证 → 把能力沉淀下来
    ↑                                                                    │
    └──────────────────────  下一轮带着沉淀再来  ──────────────────────────┘
```

### 1. 先让它能跑

不追求功能齐全，先打通一条最小闭环：本地 Ollama 优先（零 API 成本）→ 工具调用 → Skill 自动注入  
→ 零依赖单文件 Web UI。跑通了才谈得上「观察它怎么出错」——跑不起来的时候，任何设计都是空想。

### 2. 拿真实任务当测试集，从事件流里读事实

真正的提升来自**让它做真活**——整理一本小说的素材、调研一个外部项目、修一个真实的 bug——  
然后看它**到底**怎么失败的。关键动作是读它自己的事件流：编排发出的每一个事件  
（`route` / `dispatch` / `assign` / `tool_start` / `task_done` …）都进 SSE 总线，  
复盘时是**事实**而不是猜测——它有没有被派重活、哪一步空转了、文件到底写没写，看事件流就知道  
（这一层可观测性见「能力的契约」第 1 节）。

一个具体例子：同一个简单任务，修复前 **28 分钟 / 68 次工具调用**，修复后 **18 秒 / 1 次调用**  
（`t101213344526d9`）。数字来自事件流，不来自感觉。

另一个例子说明**流程绿 ≠ 结论对**：一次外部检索任务，事件流里每一步都正常（路由 → 派活 →  
检索 → 收尾，51 秒 / 3 次调用 / 全免费），但把它的产出拿去和 GitHub API 一对，  
数字差了整整一个数量级。**事件流只能证明它照流程走完了，不能证明它做对了**——  
后者得靠一手来源去核，这就是第 15 步的由来。

### 3. 小步修，改完必须自证

定位到问题后**一轮改一处**：一轮改动一个 commit，改完必须给出真实命令 + 真实输出，  
不接受「我觉得修好了」。（这条纪律本身也沉淀成了 `small-steps-iteration` 技能。）

它的价值在第八轮暴露得最彻底：一次修复任务的 3 次 `edit_file` 其实**全部失败**，  
agent 没读错误、也没重跑测试，就在总结里谎报「所有断言通过」——**轮次收敛了，但结论是编的**。  
于是有了第 12 步的三层防线：验证命令由**系统亲自跑**，模型**只有解读权、没有裁定权**。

### 4. 每轮结束，把「能力」沉淀下来

这是循环里最关键的一步，也是这个项目真正在攒的东西。跑完一轮，除了修代码，还要把这一轮学到的  
**留下来**，分四类落点：

| 落点     | 放什么                  | 落在哪                             | 机制                                         |
| ------ | -------------------- | ------------------------------- | ------------------------------------------ |
| **记忆** | 用户的长期偏好（**不含**事实与约定） | `.agentforge/memory.md`         | `memory.py`（一层，只放偏好）+ `autonote.py` 收尾自动抽取 |
| **技能** | 「这类任务该怎么做」的方法论       | `skills/*/SKILL.md`             | 任务收尾自动沉淀（`auto_learned`），或手写成常驻资产          |
| **架构** | 影响输出质量与形态的关键变动       | 本 README「架构演进」                  | 每步讲清「为什么必须这样」，不记流水账                        |
| **方法** | 怎么确认能力真在起作用、怎么不跑偏    | 「能力的契约」+ `self-verification` 技能 | 契约、不变量、自证规程                                |

沉淀要**防污染**：任务书句式不进长期记忆、本任务的具体结论不进长期记忆、方法论技能里混进  
本次任务的文件名/路径就整条作废（见「能力的契约」第 2 节）。

### 一条贯穿始终的原则：断言是常驻价值，脚本是消耗品

做测试用的一次性脚本（`_eval_*.py`、`tools/verify_*.py`）拿到结论就该退休——它们绑死了那一次  
评测的路径与任务，换台机器跑不起来，留着只会让人误以为「上次过了 = 现在也对」。所以顺序是  
**先把脚本守的断言抽成常驻的文档 / 技能 / 记忆，再让脚本退休**。这条也是测出来的：真删过几批，  
也真发现过一份「README 声称存在、实际从没入库」的测试文件。取舍判据见「能力的契约」第 5 节。

### 第 1 步：单 Agent 打磨（10-11，`a0944df`…`824e873`）

初始版本确立骨架：本地 Ollama 优先（零 API 费用）、工具调用、Skill 自动注入、零依赖单文件 Web UI。  
随后集中打磨交互——思考过程展开、回溯导航、上下文压缩入口、token 精算与圆环计量条。

### 第 2 步：上下文治理（10-11，`394124e`、`45f1471`）

35 个工具全量下发约 4.3K tokens/轮，小模型撑不住。三件套把它压到常规轮次约 1.7K：

1. **工具按需下发**——核心工具常驻（读写文件/跑命令/找文件/查记忆/记笔记/取技能用法），  
   其余按任务关键词命中才发 schema，只列名字，`find_tools` 现取用法；
2. **Skill 摘要注入**——只给开头几节；
3. **接力简报**——多步任务只传「计划 + 各步摘要 + 产出文件」，第 N 步不背负前 N−1 步的工具输出。

同时把上下文窗口提到模型上限（256K），技能目录与记忆同步瘦身。

### 第 3 步：部署与配置工程化（10-11 → 10-12，`14aad6a`…`d1675bd`）

换台电脑 clone 下来即可跑：`config.yaml` 变成不含绝对路径的纯通用模板，本机专属配置走  
`config.lanrun.yaml`（gitignore）；`models.json`（API Key）不入库，仓库放空模板；  
本地模型自动探测上下文长度并写好参数；新增 `tools/bench.py` 性能基准（读 Ollama 计时字段，横向可比）。

### 第 4 步：任务可见性（10-12，`a650029`…`5e47b97`）

**任务事件总线**：所有思考/工具/回复事件进 SSE 总线，发起连接断开任务不死，  
网页刷新后可接管续播完整过程。任务台账记录状态、耗时、token 与费用、产出文件。  
配套：用量卡悬停明细、语言漂移治理（每轮末尾中文提醒 + 严格 provider 的 system 上提合并）。

### 第 5 步：长材料规程 Skill 化（10-12，`7cc7acc`…`207e063`）

读大量素材后强制「清单 + 成文前自检」的末端提醒，从系统提示内联重构为 `long-material` skill  
（含元数据路由），系统提示不再常驻这份规程。

### 第 6 步：多 Agent 架构（Batch A–D，本批提交）

单 agent 升级为多 agent：**任务在 agent 之间接力流转**，不是「在 LLM 之间流转」。

- **`agentforge/dispatcher.py`**：本地「决策模型」把一句话请求拆成语义独立的任务、按能力维度指派  
  执行模型、维护共享进度（做过什么/产出在哪/需要什么），把前置任务的进度+产出整理成简报交接给下一个。  
  拆解与指派失败自动回退规则编排——没有调度模型也能干活。
- **护栏**：`coding/math/writing/analysis` 四类任务永不派给决策模型；点名模型比场上最强者弱 ≥8 分  
  时改派最强者并说明原因；纯闲聊（≤120 字且不含工具意图）才允许决策模型自己接，且可一键关闭。
- **并行波次**：独立任务同时跑（仅完全访问权限）；本地模型串行闸门（16GB 显存两个本地模型常驻会互挤）；  
  同文件写入串行保护（`claim_write`），不同文件互不阻塞。
- **Provider 层**：OpenAI 兼容 / Anthropic / Ollama 三家统一形状，内部历史转严格 provider 格式  
  （dict→JSON、补 `tool_call_id`、system 上提合并），支持 SSE 流式。
- **在严格 Provider 上跑通（Batch D 挖出的坑）**：本地 Ollama 对消息形状一律容忍，在线 provider  
  要么直接 400、要么静默跑歪。下面每一条都是真实跑崩后定位并修掉的，不是预防性设计：
  - **语言提醒曾以 system 贴在消息末尾** → `System message must be at the beginning` 400。  
    改为在 `_convert_messages` 里把**所有 system 收拢、合并成开头唯一一条**再发出；不改成  
    `user` 角色——实测那样模型会去「回复」这条提醒，反而打断干活。
  - **上下文压缩会重建消息**，丢掉 DeepSeek 要求原样回传的 `reasoning_content`、以及 `role=tool`  
    必须配对的 `tool_call_id` → 长任务跑到中途又 400。`context.py` 补了 `rehydrate_reasoning()`  
    （按工具调用指纹「名字+参数」回填，找不到就保持原样、绝不张冠李戴）与「重建 tool 消息只改  
    `content`、其余字段全留」。
  - **最阴的一个——SSE 中文乱码**：OpenAI 兼容流的 `Content-Type: text/event-stream` 不带 charset，  
    `requests` 于是把编码认成 ISO-8859-1，`iter_lines(decode_unicode=True)` 按 latin-1 解码 →  
    中文正文与**工具参数**（文件路径、搜索词）整段坏掉（`写作.txt` → `åä½.txt`），agent 读不到文件、  
    搜索全 miss、只能反复空转，而界面看不出任何异常。本地 Ollama 的原生 `/api/chat` 是  
    `application/x-ndjson`（走 bytes）不受影响——**本地跑绿 ≠ 在线 provider 跑绿**。改为  
    `decode_unicode=False` + `raw.decode("utf-8", "replace")`。
  - **空轮次假成功**：思考模型偶尔返回「无 tool_calls 且正文为空」的一轮，原先被当任务完成  
    （界面 `task_done files=[]`，实际零产出）。改为连续空轮次 ≤2 次时注入「上一轮没有输出」提示  
    并继续，超过 2 次报 error——不再假成功。
  - **决策模型私自缩小任务范围**：把「通读素材并覆盖写入 outline.md」改写成「仅做分析，不执行  
    文件写入」，执行者照 goal 干活就不写文件。`DISPATCH_SYSTEM` 明令「**绝不缩小任务范围**：用户  
    要求的产物（文件名/路径/格式）必须原样出现在 goal 里」。
  - 顺带一个路由口径隐患：`router.py` 的候选池 `all_avail` 取的是 catalog 里 `available` 的模型，  
    **包含没勾选的**——只要 `allow_paid_upgrade=True`，自动选型就可能挑到一个根本没勾选的付费模型。  
    已用 `allow_paid_upgrade: false` 收口（关掉后候选池会先过滤掉 `paid`），但这个口径要留意。

### 第 7 步：记忆分层与技能元数据（本批提交）

- **记忆分层**（`memory.py` 重写）：借鉴 TencentDB Agent Memory 的 L0~L3 思路做单用户本地简化——  
  L1 原子事实 / L2 项目约定 / L3 用户偏好，注入时按任务类型决定检索深度：  
  抠技术细节的任务优先 L1（路径、端口、版本这类可精确执行的信息），常规对话优先 L3/L2。  
  旧格式记忆行自动就地推断层标签，无需迁移。  
  （**这套分层后来在第 20 步被整体取消**——单用户本地场景里它没换来实际收益，见下。）
- **技能元数据与沉淀**：SKILL.md frontmatter 支持路由元数据；任务收尾自动沉淀可复用技能。

### 第 8 步：工具层升级（本批提交）

- **`impact_of` 影响路径分析**（`tools/graph.py`）：零依赖静态扫描，定义处与引用处分开列出，  
  改动前看清波及范围。
- **`task_notes` 任务草稿纸**（`tools/notes.py`）：`keep_recent_tool_results` 只保留最近几条原文，  
  40+ 轮任务里第 10 轮查到的关键信息到第 30 轮已「失忆」。任务笔记每轮从磁盘现读现注入  
  （≤2000 字尾部），压缩碰不到它——查到的发现永远在场，先查笔记再决定要不要重查。
- **联网工具的来源等级**（`tools/web.py`）：`web_search` 只用来找入口，输出头打  
  `[搜索摘要 · 转述 · 未核实]`；`fetch_url` 打 `[实测 · 网页]`；新增 `fetch_json`  
  （传 URL + `keys` 点分路径投影字段）打 `[实测 · API]`，把「打官方接口拿真实数据」变成  
  一次调用能办的事。收尾还有系统侧核查兜底，见第 15 步。

### 第 9 步：防反复迭代（本批提交）

定位到简单任务反复打转的三个根因并逐一修复：记忆断层（压缩）、无轮次预算、无重复拦截。

1. **重复调用拦截**：只读工具（SAFE）按「名字+参数」指纹判重，任务内重复出现直接回放上次结果；
2. **轮次预算**：30 轮软预算（每轮催收敛）/ 60 轮硬上限（撤工具强制交卷）；
3. **保鲜**：`keep_recent_tool_results` 6→8，压缩摘要行 160→280 字符。

实测对比：同一个简单任务，修复前 28 分钟 / 68 次工具调用，修复后 18 秒 / 1 次调用（`t101213344526d9`）。  
这些不变量原先由 `tools/verify_efficiency.py`（22 项断言）守着。它已按「`verify_*` 是一次性  
批次证据、不是回归网」的约定退休（见「能力的契约」第 5 节），断言说的就是上面这三条。

**后续实测补强**（第四~八轮真实任务）：

- 效率修复对**检索密集型长链路任务**同样生效：第六轮调研 mattpocock/skills（含用 GitHub API  
  复核 star 数据）1.7 分钟 / 10 次调用收敛（`ce9defc`）；
- 前端配合「合并呈现」：同一批工具调用在界面上合并成无框时间线组，连续调用不再刷屏  
  （`7a04ecc`，见第 10 步）；
- 第八轮暴露的「谎报验证通过」是假收敛的另一种形态——轮次收敛了但结论是编的，  
  由第 12 步的收尾验证闸门根治。

### 第 10 步：Web UI 结构性改版（本批提交）

### 第 12 步：可靠性工程——编辑护栏与收尾验证闸门（10-12，`58ae6e5`、`1d3d4e0`）

第八轮测试暴露本项目最危险的问题：修复任务的 3 次 `edit_file` 全部实际失败，  
agent 没读工具返回的错误信息、也没重跑测试，就在总结里谎报「所有断言通过」，  
最后靠人工独立复跑才当场戳穿。教训固化成三层防线：


1. **编辑护栏**（`tools/fs.py`，借鉴 Aider auto-lint）：`edit_file` / `write_file`
   保存后自动做语法检查（.py 用 `ast.parse`、.json 用 `json.loads`），
   失败自动回滚并把错误行号还给模型重试。边界很明确：**只查 `.py` / `.json`**（别的后缀不查），
   而且回滚**只针对「改已有文件」**——新建文件哪怕语法错也放行（新建的是草稿，没有「改坏」可言）；
   `edit_file` 另有两道前置闸：找不到待替换文本、或匹配到多处（有歧义），都直接报错且**一个字节都不动**；
2. **工具失败强呈现**（`loop.py`）：`[错误]` 结果自动追加系统注脚——必须先读错误修正重试、
   禁止无视失败继续、禁止未验证就声称完成；连续失败第 2 次起升级警告；
   前端工具卡新增红色「失败」态；
3. **收尾验证闸门**（`agentforge/verify.py` + `orchestrator._verify_gate`）：
   任务书里声明的验证命令（「验收：python tools/x.py」）由**系统亲自运行**
   （不经过模型工具调用），真实结果强制附进最终答复——**模型只有解读权，没有裁定权**。
   验证失败给一轮修正机会但报告照附；总结声称通过却全程没跑过命令的，
   追加「未经系统确认」声明。配套纪律：复用优先（先查证已有能力，禁止重复造轮子）。

自测 `tools/test_verify_gate.py`（73 项断言，覆盖命令提取与执行、谎报识别、产物核查、四条编排路径）。

### 第 13 步：运行期可靠性——上游守卫与常驻服务（10-13）

三件「不该让人操心的事」变成了代码：

1. **「读不到」不再冒充「没有」**。后端进程挂掉时，页面原先把请求失败静默吞掉再兜成空列表，
   于是「还没有记忆 / 还没有技能 / 还没有可清理的任务」三处一起说谎，而侧栏还列着十几条任务
   （那是上一次成功拉取的数据）。现在所有只读接口走统一的 `apiGet`，连不上/报错/非 JSON 一律
   翻成人话；记忆与技能面板显示红色「读取失败 + 重试」，侧栏顶部亮出「服务未连接，列表为上次数据」，
   轮询失败时保留原列表不清空。
2. **上游与自身都有人守**。本地模型的上游是 Ollama，长期不关机的机器上它可能被手动退出或升级时
   重启，本地模型就静默失效了——`agentforge/ollamaguard.py` 把它收成「探测 → 定位 → 拉起 → 等就绪」
   一件事，Web 启动、界面健康检查、常驻服务三处复用；`service.py` 则盯着 8787 端口，
   没人服务就补位拉起（**只补位不抢占、绝不杀进程**——杀进程会连带杀掉正在跑的任务）。
3. **常驻与自启从「手工配置」变成「仓库里的一步」**。以前「开机自启」只存在于这台机器的
   启动文件夹里——换台机器 clone 下来就没了，而启动项又无法入库（它必须写死本机的绝对路径）。
   现在由入口脚本 `start.bat` / `scripts/start.sh` 现场生成启动项，clone 完点一次就复现整套
   「随时打得开」，卸载留一条 `--remove-autostart`。

### 第 14 步：入口收敛与「不占任务栏」（10-13）

1. **四个看着重名的启动脚本收成一个**。`start-web`、`start-service`、`install-autostart`
   各有 `.bat` / `.sh` 一对，Windows 默认隐藏扩展名，于是根目录看着像四个同名文件，
   每次都要猜点哪个。现在根目录只剩 `start.bat`（Windows 双击）和挨着它的 `stop.bat`，
   Unix 侧挪到 `scripts/start.sh`（放子目录是为了不在 Windows 里跟 `.bat` 撞名）；
   开机自启不再单独一个脚本，由入口顺手登记。语义也简化成一句话：**点它，服务就一直开着**。
   `stop.bat` 是后来补的：`start.bat --stop` 没法双击使用（Windows 不能「带参数双击」），
   于是给它配了一个只做转发的同伴文件——用的是同一个道理，停的逻辑永远只有一处。
2. **服务彻底离开任务栏**。原来 `service.py` 拉 Web 服务用的是 `DETACHED_PROCESS`——
   实测它会给控制台程序**新开一个可见窗口**：一关掉 Web 服务就死，保姆又把它拉起来，
   于是任务栏里「关了又弹、关了又弹」。改用 `CREATE_NO_WINDOW` 后，服务自己没窗口，
   它拉起的任务命令继承隐藏控制台也不会弹黑框（实测父进程 `CREATE_NO_WINDOW` 时子进程
   `GetConsoleWindow()` 为 0；换成 `pythonw` 父进程反而会拿到可见窗口）。
   注意隐藏的只有 AgentForge 自己的这两个进程——任务里新开的命令行/程序照旧正常出现在任务栏。
   同一个坑也修在了 `ollamaguard._spawn`（退回 `ollama serve` 时）。

一个值得记下的坑：Windows 上不能用 `os.kill(pid, 0)` 探测进程存活——Windows 没有信号，
Python 的 `os.kill` 对非 CTRL_* 会直接调 `TerminateProcess`，「查一下你在不在」把人杀了。
已改用 `OpenProcess` + `GetExitCodeProcess`。另一个：venv 的 `python.exe` 可能只是转发器，
`Popen` 拿到的 pid 并不是真正占着端口的那个（实测 `web.pid=11500` 而监听者是 `19984`），
所以 `--stop` 走「记录 pid + 按端口扫占用者」双保险。

本轮的验证是逐条跑过、全绿的（Ollama 守卫 20 项、常驻服务 28 项、界面自动拉起 15 项），
但那些用例当时写在工作区临时目录、**没有随仓库留下**——留下的是上面这些结论本身。
仓库里可执行的自测见「能力的契约」第 5 节。

### 第 15 步：检索的来源等级——一手来源优先（10-13）

一次检索实测暴露的病：让它查 GitHub 上的 REA 项目，**流程全绿**（51 秒 / 3 次调用 / 全免费），
但结论里的数字**差一个数量级**——摘要写「Star 已达 **1w+**」，GitHub API 实测是 **17 万**；
「最近更新」写成「**2026 年 7 月**」，实际是当天。定性描述大致都对，定量与时效全错。
而它手里明明有 `fetch_url`，只搜了一次就下了结论。

根因不是工具坏，是**来源性质没有被区分**：「搜索摘要（转述）」和「一手来源（实测）」
在模型眼里长得一样。修法分三层，从「劝」到「拦」：

1. **说得清**（工具输出，`web.py`）。每个联网工具的输出头显式标注来源性质——
   `web_search` 打 `[搜索摘要 · 转述 · 未核实]`，`fetch_url` 打 `[实测 · 网页]`，
   新工具 `fetch_json` 打 `[实测 · API]`。`web_search` 的描述从「拿到结果后去读详情」这句
   **建议**升级为**硬约束**（搜到候选就必须抓至少一个一手来源再下结论），默认条数 6 → 8，
   末尾再补一句「这里的数字、版本、日期都不可直接写进回复」。
2. **给条路**（新工具）。`fetch_json` 把「打官方接口拿真实数据」变成一次调用能办的事：传 URL
   加逗号分隔的 `keys`（点分路径）就返回官方字段，不必让本地小模型自己拼 URL、自己读一大坨 JSON。
   核一个 GitHub 仓库，`https://api.github.com/repos/<owner>/<repo>` 一次调用就够。
3. **兜得住**（系统侧核查，`sources.py`）。只用过搜索、全程没抓过一手来源，而总结里又出现
   数字 / 版本 / 日期时，答复末尾由程序追加「转述 · 未经核实」声明，并逐条列出裸奔的数字——
   与收尾验证闸门同一思路：**模型只有解读权，没有裁定权**。它不改写正文、不阻塞收尾，
   只把证据等级说清楚。

方法论同时沉淀成技能 `skills/first-party-source/`（含常用官方 API 地图：GitHub / npm / PyPI），
让「先搜入口、再抓一手来源、才写结论」成为可复用的规程，而不是靠每条提示词重复叮嘱。

同轮还修了一类纯前端的「错觉」：任务结束后点开回看，界面上仍有东西在转圈 / 显示「执行中」。
顺着往下查，同一类问题一共有四处：

1. **工具组头卡在「调用中」**。回看历史的那条路径（`renderHistory`）只改了状态文本与样式，
   **从没把 `dataset.run` 清成 `0`**，而组头判定「运行中」正是看这个标志。
2. **组头自己的标志从不落定**。`toolHeadSummary` 只改文本与 class，不写 head 的 `dataset.run`——
   于是出现「文本说已调用、标志说还在跑」的自相矛盾状态。
3. **头像行永远显示「执行中 0m00s」**。头像行初始文案就是这四个字，冻结只发生在实时的
   `done` / `stopped`；回看历史不冻结，一条结束很久的回复就一直挂着「执行中
   （跟工具组头是同一类错觉）。现在回看时按任务台账里的真实耗时冻结成「完成 XmYs」。
4. **未执行的工具没有标红**。实时路径会给失败的调用加 `denied` 样式，回看路径漏了。

外加一道兜底：任何终态事件（`done` / `stopped` / `error`）之后，DOM 里仍标记为运行中的工具
一律落定为「未执行 / 中断」——任务已经结束，就不该还有东西在转圈。这四条一起锁进了前端回归
`tools/test_tool_panel.mjs`（21 项，用 jsdom 加载真实页面驱动 `renderHistory`，找不到 jsdom 会自动跳过）。

### 第 16 步：点一下就要看到窗口——绕开 Windows 的前台锁（10-13）

用户反馈：「点侧栏的工作区路径 `D:\AI_develop\project\agent-forge` 之后，还要再点一次任务栏上那个
文件资源管理器窗口才能看到它。」这种事不能靠猜，先量：写了 `EnumWindows` + `GetForegroundWindow`
探针，点击前后各看一次——

```
接口返回: {"ok": true}                                  ← 后端确实把文件夹打开了
前台窗口: [Chrome_WidgetWin_1] 'AgentForge ... Edge'   ← 点击前后都是它
资源管理器窗口: hwnd=1968236 'agent-forge - 文件资源管理器'  ← 就停在后面，一直没上来
```

所以既不是路径错、也不是没打开，是**窗口没到前台**。根因是 Windows 的**前台锁**：
后台进程不许抢焦点——否则任何程序都能用弹窗盖住你正在看的东西，钓鱼就是这么干的。
`os.startfile()` 只是「请求资源管理器打开这个目录」，窗口是开出来了，但请求来自后台进程，
Windows 不给它焦点。**「功能生效了但你看不见」也是一种坏掉**，而且最难查：日志里全是绿的。

绕法在 `agentforge/reveal.py`：`AttachThreadInput` 把自己挂到当前前台线程的输入队列上，
借它的资格再 `SetForegroundWindow`，用完立刻把资格还回去。同一探针验证有效——调用后前台窗口
从 Edge 变成了那个资源管理器窗口；换成服务进程再走一遍端到端，接口返回
`{"ok": true, "front": true}`（0.34 秒），前台窗口变成 `CabinetWClass 'agent-forge - 文件资源管理器'`。

配套的三条边界，缺一条就会变成新的毛病：

1. **只在用户点击触发的 `/api/open-folder` 里抬窗口**，不是后台随时抢焦点；
2. **只抬自己该抬的窗口**。文件夹只认 `CabinetWClass` / `ExploreWClass`，且标题开头是
   本文件夹名或完整路径——标题形如 `<名字> - 文件资源管理器`，统一按 ` - ` 切出开头段来比，
   否则 `agent-forge-backup` 会被当成 `agent-forge`；文件则要求标题里带**完整文件名**
   （`README.md` 而不是 `README`），不满足就不动，免得把恰好同名前缀的浏览器页签抬上来；
3. **找不到就退回原样**：等满 1.6 秒仍无匹配窗口就返回 `false`，行为与改动前完全一致——
   「抬窗口失败」绝不能变成「文件夹点不开」。

这一步和第 14 步是同一个主题：**桌面集成只能实测，不能推理**。第 14 步问的是「子进程的窗口
会不会弹出来」，这一步问的是「窗口会不会到前面来」，两处都是 Windows 在用你没想到的规则
替你决定结果。

### 第 17 步：一条任务只有一个入口——提问、头像、计时都从台账来（10-13）

用户反馈（已经不是第一次了）：「你发指令时，一开始回复没有显示问题，也没有头像和计时；
后续发指令，从头到尾都没有。」三条症状，一个原因。

先定位：画面上这三样东西各有各的出处——**提问气泡**只由 `addUser()` 画，
**头像行与计时**当时是 lazy 地挂在第一个 AI 元素之前的（`needAIHead` 闸门；
第 19 步把这一层也去掉了，改成提问落盘即建）。
所以问题变成：什么时候会调 `addUser`？全项目只有三处——输入框发送（`send`）、
回看历史（`renderHistory`）、以及**接管外部任务**时。第三处当时有个苛刻的前提：

```js
const pristine = view === 'chat' && !busy && !openTaskId && !viewingHistory
  && history.length === 0 && !log.childElementCount && !input.value.trim();
if(pristine){ … addUser(running.title) … }        // 只有「页面干净」才补一条
```

于是「已经看过一条任务，再发下一条」必然落空：`openTaskId` 还留着上一条的 id、
对话区还有内容，`pristine` 为假——**不补提问、也不挂流**，别人的思考/工具/回复就直接
续写在上一段对话底下。首屏干净时看着是对的，这解释了「第一次好像有、后面全没有」。

更深的根因不在渲染，在**真相来源**：提问的原文只活在发起方的内存里。
台账 `Task` 当时只有 `title`（压空白 + 截 90 字），`history` 要到任务结束才写
（`finish(history=…)`），所以任务跑到一半，别的端除了那个截断的标题**没有原文可用**。
三条路各写各的，本质是在各自弥补这个缺口。

改法是收成一个入口，并且让台账从第一秒起就有真相：

| 层 | 改动 |
|---|---|
| 台账 `taskstore.py` | `Task` 增 `prompt` 字段：`begin(message)` 时原样记下用户原话（不截断、不压空白）；`title` 降级成它的派生物 |
| 前端 `index.html` | 新增唯一入口 `enterTaskView(task, {live})`：清场 → 提问气泡（`taskPrompt`：`prompt` → `history` 首条 user → `title`） → 头像行与计时（基准 = 台账 `created_at`） → 实时就挂流、回看就 `renderHistory`。`openTask` / `adoptRunning` / `resetChat` 全部改走它 |

判据也跟着改成「**要不要显示**」而不是「**页面够不够干净**」：只要停在对话页、
自己手上没有正在流的任务（`busy`），外来任务就入场；正在回看历史**不算**妨碍——
一开始我把「回看中」也当成「别打扰」，写完才想明白它的后果：用户一直停在回看态，
轮询每次都跳过，这条任务他就**永远看不见**，正是要修的那个症状。入场每个任务只发生
一次（判据是 `liveTask.id`），想看旧任务点回去即可。

顺带修掉同一类病的一处：清空对话区（换任务 / 新对话）时，`cur` `curTool` `aiHeadEl`
这些**指向 DOM 的渲染状态**没复位，后面的事件会写进已经脱离文档的节点——流还在跑、
界面永远空着。收成一个 `resetRenderState()`，谁清场谁调用。

验证分三层，都不靠「看起来对了」：

1. `tools/test_taskstore.py`（18 项）：`begin` 之后 `prompt` 就是原话，`list` / `get`
   都带得出来，`finish` 不会冲掉它，老台账（没有这个字段）读得进来；
2. `tools/test_task_view.mjs`（34 项，jsdom）：脚本发起的任务在「页面不干净」时也要入场、
   气泡里是原话、提问之后紧跟头像行、计时基准是任务真正的开始时间；`busy` 与「停在设置页」
   不抢画面也不挂流；回看时提问不重复上屏；
3. **突变验证**（测试到底抓不抓得住）：把老的 `pristine` 条件塞回去再跑一遍，
   测试立刻红 6 项，症状与用户描述一一对应——气泡里是**上一条**任务的提问、
   没挂流、计时基准变成「现在」（`1791875325024`，而不是任务开始时间）。

最后是真机端到端（`.run/e2e_task_view.mjs`，仅供本地诊断）：脚本 `POST /api/chat` 发起任务，
jsdom 里跑真页面代码、连真服务、走真 SSE 回放。结果：

```
台账里的这条任务：id=t10131510505bdc created_at=1791875450.5
台账 prompt（前 60 字）：先列出当前工作区根目录下的文件（不要读内容）…
对话区实际结构：msg-user → ai-head → pillnote → … → divider → …
计时基准 = 台账里的任务开始时间（不是「现在」）        [PASS]
```

`msg-user → ai-head → …` 就是这一步要的结果：**先有「我问了什么」，再有头像与计时，
然后是过程**——不管这条任务是浏览器里敲的，还是脚本 / CLI 发起的。

### 第 18 步：要读现场的任务，不许写成「写作」（10-13）

第 17 步验证时顺手派了一条极简任务——「先列出当前工作区根目录下的文件（不要读内容），
然后用一句话说明你都做了什么。」结果是**25 秒、0 次工具调用，答复凭空编了一份目录清单**：

```
agent-forge.json / config.yaml / core/ / docs/ / scripts/ / start.bat /
stop.bat / tools/ / ui/ / venv/ / README.md          ← 前 5 个在工作区里都不存在
事件统计：tool_start 0 次      台账 tools=0
route: kind=writing → qwen3.5:4b     ← 「列目录」被判成了写作类
skill: self-verification 已加载       ← 加载了，但没拦住
```

三个缺口，逐个补。

**① 定性错了：`kind_of` 只因为「说明」两个字就判成写作。** 写作信号里的
「写」「说明」「介绍」「总结」太泛，几乎任何请求都会命中一两个；而"要读现场的任务"
选模型时该看的是**推理**，不是**文风**——交给一个擅长长文的模型，它就去"写"而不是"看"了。

改法：新增一类 `inspect`（检视），信号是「列出 / 有哪些 / 看一下 / 查看 / 工作区 /
根目录 / 目录结构…」；并在 `kind_of` 里加一条优先级——**检视优先于写作与通用**
（要读现场的任务，读不到就无从写起）。`inspect` 的维度取 `reasoning`。
新增一种 kind 要同步四处（`KIND_LABEL` / `KIND_DIM` / `KIND_SIGNALS` / 路由器
`_CAP_DIMS`，外加调度提示与 `NOT_SIMPLE_KINDS`），少一处就是线上 `KeyError` 或静默退化——
这份同步清单直接写成了断言，见 `tools/test_planner.py`。

**② 闸门缺了一路：外部事实有核查，本机事实没有。** 第 15 步给外部事实立了闸门
（`sources.py`：只用搜索、没抓一手来源、总结里有数字 → 附「转述」声明）。
而同一种病——**拿没查过的东西当查过的写出来**——在本机事实这一侧完全没有防线。

改法：`sources.py` 加第二路核查（配置项 `agent.local_facts_gate`），三条同时成立才出手：

1. 任务要的就是「工作区里现在有什么」（列目录 / 有哪些文件 / 看现状…），
   且**不是在让它造东西**——造东西时出现的文件名是它自己起的，不是对现状的陈述；
2. 总结里在陈述现状：有明确列举标记（根目录 / 文件列表 / 目录结构…），或 ≥2 个文件 / 目录名；
3. 整个任务**没有调用过任何能读工作区的工具**（`list_dir` / `read_file` / `find_files` /
   `search_code`…；跑过 `run_command` 也算读过）。

**③ 「技能加载了但没有硬约束」——这才是要修的那条。** 规矩当时同时写在系统提示
（`loop.py` 输出要求）和技能里，两处都是「劝」，模型不听就什么都不会发生。
把提示词写得更重不解决问题，**得让系统替它把这一步做实**：命中就先给模型
**一轮修正机会**（明确要求它 `list_dir` 看一遍再重写，并把点出的项逐条列给它），
复查仍然没读，才由程序在答复末尾追加「本机事实未经核实」声明，并在界面上标出是哪几项。
这是第 12 步「模型只有解读权、没有裁定权」在本机事实上的延伸。


顺带把技能那一侧的边界修对：`first-party-source` 原来的 `when_not_to_use` 写着
「纯本地任务（读写本项目代码…）」，等于**把本机事实排除在「一手来源」之外**——
这次改成「转述 / 一手来源」两种表现共用一条判据（外部的来源是官方站点，本机的来源
就是工作区本身），`when_to_use` 补上「列目录 / 看有哪些文件」。

验证分三层：

| 层 | 结果 |
|---|---|
| `tools/test_planner.py`（54 项） | 事故原句 → `inspect`；「读 README 并总结」→ `inspect`；纯写作 / 检索 / 编码不被误判；**新增 kind 的四件套不变量** |
| `tools/test_local_facts.py`（61 项） | 任务书判据、工具清单口径、文件名识别（含带目录前缀、绝对路径、网址不误伤）、三条件联动、修正轮与声明块、闸门接入六条路径 |
| 真机端到端（原样重发那条任务） | `assign #1 inspect → gemma4:12b`，`tool_start list_dir {"path": "."}`，答复 12 项**全部存在**（改前是 11 项里 5 项不存在） |


外加一次**真实脏数据回放**：拿历史那一跑的原始事件（零工具调用 + 编造清单）喂给新闸门，
判定「出手」，逐条点出 `agent-forge.json`、`core/` 等未经核实项——断言没有对着
理想输入写。

### 第 19 步：分清楚「硬约束」和「叮嘱」（10-13）

第 17、18 步收尾时用户提了一个更根本的质疑：

> 修复方式里有很多是**增加记忆**。对于严格限制的事情，必须通过架构解决——
> 比如有时候头像 + 计时消失，那就独立出模型的判断，让它在回复一开始就把头像加载并计时；
> 比如中途冒出复制 / 重新生成 / 朗读按钮，那就等全流程走完再生成这些按钮。
> 对于不需要模型判断的 bug，不走模型的判断，防止模型出错。

这个质疑是对的，而且指出了一个此前的**方法缺陷**：修完一个坑，我们常把结论写成一条记忆
（`.agentforge/memory.md`）或一段技能文本，下次靠模型读到它、并且愿意遵守。
可这两层都是**劝**——第 18 步已经吃过一次：`self-verification` 技能明明加载了，
编造目录清单照发不误。**「写下来了」不等于「会生效」**。

所以补一条判据，用来决定一件事该用什么方式修：

| 三问 | 都是"是" → | 否则 → |
|---|---|---|
| 1. 这件事的**正确答案**依赖模型判断吗？ | 只能留在模型侧 | **由程序定** |
| 2. 程序能不能**在出错的那一刻**发现它？ | 能 → 加程序侧核查（闸门 / 断言） | 只能靠事后复盘 |
| 3. 三个月后还会不会重犯？ | 会 → 写成 `tools/test_*.py` 常驻断言 | 记在记忆里就够 |

**不需要模型判断的事，就不该让它经过模型。** 本轮把四处这样的地方从"劝"搬到了"定"：

**① 回复的开场：头像行与计时不该等模型吐第一个 token。**
原先 `takeAIHead` 是 lazy 的——挂在 8 个渲染函数里，"谁先出现谁负责插"。
于是「头像与计时什么时候出现」被交给了「模型什么时候吐第一个 token」：
首轮跑得慢、只吐胶囊、甚至一个字都不吐，它就缺席或迟到。改成 `addUser()` 里
（即**提问落盘的那一刻**）无条件建头像行、把计时基准定为那一刻；`takeAIHead` reduced
成幂等兜底（已在就不动），8 个调用点一个都不用改也不会重复插。台账的 `created_at`
到达后（`task` 事件）再把基准校准到它上面，与侧栏口径一致。

**② 回复的收尾：也只留一个出口。** 工具条的挂载原先散在 `done` / `stopped` /
`history` / 回看四条路上，代价是：`history` 那条会在回答中途挂（已修过一次），
而 `error` 那条**什么都不做**——出错的回复永远停在「执行中」，`done` 那条则一视同仁
写「完成」，把出错的也写成完成。**结局由"最后收到哪个事件"决定**是错的。
现在收成一个 `settleReply(status)`，四条路全走它，按结局决定标签（完成/已停止/已中断）、
工具落定口径与工具条；收尾之后流程若又动起来（多步任务的后续步骤），
`unsettleReply()` 立刻把工具条撤回去——**宁可晚一点有，不要早一点有**。
再加一层兜底：`streamChat` 的 finally 里，若流读完了还没等到终态事件（进程崩、连接断），
由前端自己收尾——**收尾是"流程结束"这件事的产物，不该依赖某个事件必须到达**。

**③ 失败之后换哪条路，由程序写出来，不让模型猜工具名。**
REA 那三跑里，`fetch_url` 被代理拒之后模型去猜了个 `browser`（白烧两轮），
而正解（`fetch_json` 打 `api.github.com`）就印在它刚读过的工具说明里——
**问题不在能力，在失败那一刻没人把这条和眼前的错误连起来**。现在 `fetch_url`
的失败输出由程序按失败类型写下一步：网络层失败 → 直接给出可照抄的 `fetch_json` 调用
（URL 形态认得出来就换算好，如 `github.com/o/r` → `api.github.com/repos/o/r`）；
4xx → 先建议确认地址；5xx → 说明是站点故障。`browser_snapshot` 降为最后退路。

**④ 两道闸门都扩了面**（第 15 / 18 步那两道）：
外部事实那道原先只认「总结里有数字 / 版本 / 日期」——A 组通篇定性转述
（「10 月初走红」）一个阿拉伯数字都没有，静默放行。**「没写数字」不等于「有据」**，
所以补一路时效性措辞（最近 / 月初 / 刚发布 / 最新版…），并要求**总结确实在谈搜过的
那个东西**（从 `web_search` 的调用参数里抽实词比对）——这个附加条件是为了不让
本地任务里的「最近改的那块代码」误伤。
搜索词那道则是补在工具里：判定为泛查询（或结果清一色门户首页）时，
**程序自动补一枪收紧后的检索**（`site:` + 精确词，如 `site:github.com "REA"`），
把结果拼在同一次工具返回里且排在前面，并注明「以后这么写能省一轮」——
白烧的那一轮被程序吸收了，不再指望模型自己想到收紧。

留下的那些**只能靠叮嘱**，但也说清为什么：

| 事情 | 为什么不能架构化 |
|---|---|
| `.bat` 里要写外部命令全路径 | 这是"写代码时的约定"，没有运行时可检查的点；能做的只是把 `%SystemRoot%\System32\find.exe` 写进文件 |
| 别在自己所在的工具 shell 里启停常驻服务 | 这是**人的作业纪律**，不是程序的输入输出；能在日志里看出来的只有事后 |
| 突变验证时备份不要先删 | 同上——能强制的是"改完必须重跑全量回归"这个动作，做没做只有人知道 |

这三条留在记忆里，并明确标注它们是**作业纪律**而不是系统保证。

验证（全部由程序断言，不靠"看起来对了"）：

| 层 | 结果 |
|---|---|
| `tools/test_reply_flow.mjs`（34 项，新） | 一个事件都不喂，提问落盘后头像行与计时就在、且紧跟在气泡之后；正文在写时没有工具条，`done` 之后才有且只有一条；`done` 之后再 `delta` → 工具条撤回、计时回到「执行中」；`error` 也冻结头像行并按「已中断」写；一个字都没吐时把空头像行收掉；流读完但没 `done` 也要收尾；回看多轮时**每一行**都按台账冻结 |
| `tools/test_task_view.mjs`（38 项，+4） | 实时入场时，"头像行与计时在提问落盘时就位（没等任何 AI 事件）"、且只有一个（后到的 AI 元素不会又插一个） |
| `tools/test_sources_gate.py`（49 项，+11） | 旧判据对纯定性转述确实不命中（缺口坐实）；补上之后命中「最近 / 月初」；抓过一手来源后不标；没搜索时不误伤；搜过但谈的是别的东西不标；搜索词从工具参数里取 |
| `tools/test_web_tools.py`（38 项，新） | URL → 官方接口的换算（含带 `?tab=` 的链接）；网络层 / 4xx / 5xx 三类失败各自的指路；`fetch_url` 真的把指路拼进输出；泛查询判定与收紧构造（噪声词不当中坚）；**编排层**：泛查询补一枪、收紧结果排在前、一把命中就不补、没结果时给可执行的下一步——`requests.get` 全程替身，不联网 |

**突变验证**（把老行为塞回去，确认测试真的抓得住）：五个突变逐个注入、跑完即恢复：

| 突变 | 结果 |
|---|---|
| 头像行改回 lazy（`beginReply` 不建） | `test_reply_flow` 红 7 项 + `test_task_view` 红 2 项，症状正是「头像行数=0」「紧跟气泡的成了 shimmer」 |
| `error` 不回 `settleReply` | 红 3 项，D1 直接报 `执行中 0m00s`——就是用户描述的那个错觉 |
| `delta` 不调 `unsettleReply` | 红 2 项：工具条留在中途、计时停在「完成」 |
| 闸门砍掉时效性一路 | 红 1 项：「补上之后：无数字的时效性转述不再放行 —— []」 |
| `fetch_url` 提示改回老文案 | 红 1 项：失败输出里没有 `[下一步]` |
| 砍掉「泛查询自动收紧」 | 红 1 项：返回里只有「原始查询」一段 |

顺带这一轮还抓出两个**测试写出来才发现的真 bug**：收尾时清掉 `cur` / `lastSeg` 会让
"续写"变成凭空多开一个气泡、且旧节点上的工具条再也撤不掉（改用按 DOM 撤销）；
工具条的防重复判据原先读一个内存标志，在「撤回 → 重挂」的来回里留下脏值，
把重挂自己挡掉了（改用 `:scope > .msg-foot` 问 DOM）。

### 第 20 步：记忆里只留「偏好」（10-13）

第 19 步留下的原则是「设定靠架构，偏好靠记忆」。可执行到**记忆**这个小系统上时，
它自己恰恰违反了这个原则——记忆里混着三类东西：

- **L1 事实与环境**（路径 / 端口 / 版本）：有工具能现查，抄一份到记忆只会过期误导；
- **L2 项目约定**（工作方式 / 流程规则）：写着只是「劝」，模型不照做就不发生——
  这些本该由程序与断言强制；
- **L3 用户偏好**（倾向 / 风格 / 习惯）：唯一真正属于记忆的一类。

于是把 L1/L2/L3 分层整个拿掉，记忆**只放偏好**：

- `memory.py` 删掉 `LAYERS` / `classify_layer` / `normalize_layer` / `SCOPE_WEIGHTS` /
  `layer_counts` 与「按任务类型分层检索」——注入时一律取**最近的若干条**，不再按层分配预算；
- `autonote.py` 的模型提示词改成「只提炼用户的长期偏好」，并显式列出
  「事实 / 约定 / 本次任务指令」三类不要记；旧格式行尾的 `· L1/L2/L3` 读到时就地忽略，
  文件不用迁移；
- `remember` 工具去掉 `layer` 参数，描述写明只记偏好；
- 侧栏「记忆管理」删掉分层统计行与层徽标；
- 存量记忆里那十几条 **L2 项目约定**一次性清掉——**它们要么已经在架构里、
  要么本来就该进架构**。

一句话：记忆从「三层的知识库」收成「一层的偏好清单」。原那套分层是从
TencentDB Agent Memory 的 L0~L3 借来的，在单用户本地场景里没换来实际收益，
却把「事实 / 约定 / 偏好」混在一个文件里，正好和第 19 步的原则对着干。

验证：新增 `tools/test_memory.py`（常驻）钉住不变量——`MemoryStore` 不再有 `layer` 字段与
`layer_counts`；写入的行是 `- [时间 · 任务] 正文`（无层标签）；**旧格式（带 ` · L2`）的行
仍能解析且层标签被丢弃**；注入块只列正文、按时间正序取最近若干条；`autonote` 丢弃模型
偶尔给出的 `[L1]` 层前缀、且「事实 / 约定 / 本次指令」三类不被收进记忆。

### 第 21 步：找对了入口，还得找对**对象**（10-13）

第 15 步治的是「没抓一手来源」，第 19 步治的是「搜索词太泛」。同一个任务再跑一遍
（「帮我查一下 git 上叫 REA 的项目」），冒出第三种病：**一手来源抓了、搜索词也收紧了，
对象却找错了。**

模型连搜四枪，最后一枪打的是 `api.github.com/repos/bbylw/rea-cn`——一个 80 star 的中文镜像站；
而正主 `morluto/rea` 有 19 万 star。它答得理直气壮（数字确实是 API 实测的）。三轮复现，
一模一样；连明确要求「我要找那个最有名的（star 最多的）」，它照样把镜像站说成最符合的那个。

根因不在模型，在工具链缺一档能力：

- `git_*` 全家都是**本地**仓库操作（status / log / commit / clone / push），搜不了远程；
- `fetch_json` 能打 `api.github.com/repos/<owner>/<repo>`，但要求**先知道** owner/repo；
- 于是「把 REA 这个字符串变成候选清单」这件事，**没有任何工具能办**。模型只能锚定搜索
  给它的一条 GitHub 链接——而 `site:github.com "REA"` 的头条正是那个镜像站，正主压根不在结果里。

修法两层，都在程序侧：

1. **补一档能力**：新增 `github_search`，打 `api.github.com/search/repositories`，按 star
   排序返回候选（全名 / star / fork / 主语言 / 许可证 / 最近更新 / 简介 / 地址）。它进检索族
   成套下发（见第 19 步的族机制）——缺了它，这一步就静默劣化成「只有一个先被索引到的仓库」。
2. **`web_search` 侧再兜一枪**：`repo_keyword` 判定「像是在找某个仓库」（两道判据：查询里有
   git / github / 仓库 / repo 的信号，**且**能挑出一个像项目名的词），就顺手查一次官方接口，
   把权威候选**排在最前**，并在尾部点明「哪个是正主以这份为准，别拿搜索摘要判断」。
   沿用第 19 步「泛查询自动收紧」的思路：**不指望模型自觉**。

顺带两处口径对齐：

- `sources.py` 的 `FETCH_TOOLS` 加上 `github_search`——它打的同样是官方接口，不能因为
  「名字不以 `fetch_` 开头」就把用它的答复判成「转述 · 未经核实」；
- 工具描述必须写得短而准。第一版描述太长，中文 2-gram 让 `时改` / `里的` 这种碎片命中了
  「把 loop.py 里的工具超时改成 60 秒」这类纯本地任务，把整族检索工具拖进了上下文——
  既有的 `test_no_false_family` 当场变红，**这正是那条断言该干的活**。

验证：`tools/test_web_tools.py` 38 → 85 项（取参与解析、限流 403 的解释、`repo_keyword`
的两道判据、兜底把权威候选置顶、普通查询不误开枪、接口挂了静默降级）；
`tools/test_toolselect.py` 补「`github_search` 在检索族里且是只读」；
`tools/test_sources_gate.py` 补「它算一手来源」。九条突变验证全部「改坏即红、恢复即绿」。

**完整的修复清单**（第 1–21 步的所有问题，逐条标出属于「程序强制 / 断言锁定 /
提示词劝 / 作业纪律」哪一档，以及哪些有意留在"劝"这一层）在 [`contracts.md`](contracts.md)。

这一节讲的是一条被发现的经过；把它抽成可复用的原则（"不需要模型判断的事就不经过模型"、
"记忆只放偏好、设定必须靠架构"），单独成 [`README.md`](../README.md) 的
《设计原则：设定靠架构，偏好靠记忆》一节。

### 第 22 步：先有标尺，再谈改进（10-14）

第 21 步之前，项目的一切改进都靠「实测事故」驱动：出了事 → 查根因 → 修 → 钉断言。
这套循环能抓住**已发生**的问题，却回答不了两个更前置的问题——

- 「我改了 X，agent 到底变好没有？」——没有标尺，答案永远是感觉；
- 「路由该把任务派给谁？」——信号词粗分（classify）选的是不存在的语义 key，
  实际永远落到 fallback，是死逻辑；真正的能力路由只会「挑最强」，不会「够用就好」。

修法三层，仍然全在程序侧：

1. **评测集 + 分层判定**（`evals/tasks.yaml` + `agentforge/evals.py`）：20 条任务横跨
   编码/文件操作/写作/分析/运维五类，每条带 seed（预置文件，写进独立沙盒）与
   expect（判定条件）。判定链六层，**零模型调用**：exact 原文包含 → norm 归一包含
   （全半角/大小写/空白）→ numeric 数值断言（带容差）→ fuzzy 关键词组（同义词容错）
   → must_not 禁词 → check 真跑命令（复用 verify.run_verify_cmd，说得好不算数）。
   第一个失败的层就是失败归因：crash/empty = 管线问题，exact~fuzzy = 执行质量，
   check = 说得好但产物是错的。运行器 `tools/bench_tasks.py` 把 agent 工作区钉在
   沙盒里，完全访问权限跑完无人值守；结果落 `evals/results/<label>.json`。
2. **A/B 对比**（`tools/bench_compare.py`）：同一任务集跑两个 label，逐任务列翻转
   （修复/退化）、失败层分布对比、平均耗时，结尾按「只修不破才算严格更优」给结论。
   从此「换不换 dispatcher 模型」「要不要开 allow_upgrade」这类争论交给数据。
3. **路由按失败后果定档**（swe-router 思路，`planner.stakes_of` + `Router.capability`）：
   任务先按「做错了会怎样」分档（低风险/常规/高后果，信号刻意保守、high 优先），
   每档一条模型综合分下限（`routing.stakes_tiers`，默认 0/78/86）；选型从「永远挑最强」
   改为「满足下限的最便宜模型」（cost 维度），没人达标才用最强者兜底并明说差距。
   死逻辑 classify 移出执行链（仅剩 CLI 诊断在用），`loop.py` 里那段永不生效的
   auto_route 块一并删除。授权口径不变：改用未勾选模型仍需 `allow_upgrade`，
   付费模型仍需 `allow_paid_upgrade`，绝不偷偷花钱。

配套立了一条纪律（README《设计原则》新增第四节）：**脚手架只减不增**——每想加一个
harness 功能，先用评测集问「mini-swe-agent（100 行、只有 bash）会需要这个吗」；
答不上增益的，不加。

验证：`tools/test_evals.py` 25 项（六层判定逐层过/不过、归因顺序、任务集合法性、
seed 路径安全）、`tools/test_router_stakes.py` 21 项（分档信号、最便宜达标者入选、
授权口径、下限未达兜底、付费模型绝不擅用）。全量 15 个 Python 回归文件通过；
单条任务（c1-fix-area）真实管线冒烟通过：agent 在沙盒里修好 bug.py、check 层实测
`python bug.py` 输出 24。

### 第 23 步：缺了就明说，失败了再换条路（10-14）

第 22 步有了标尺，这一步回答两个它暴露出来的问题：**能力边界怎么让模型知道**，
**失败了除了如实上报还能不能自救**。

1. **工具预检**（`agentforge/preflight.py`）：任务开始前，架构先按保守信号判定
   「这个任务需要哪类能力、环境里到底有没有」。命中意图而工具全缺时，生成
   「无法完成通告」注入 system 层（和 FAIL_NOTE 同一待遇）并记缺口台账。
   误判方向刻意设计成不对称：把"要联网"误判成"要查 GitHub"毫无代价（工具在
   就不通告），漏判则回到旧行为。架构能保证的硬事是两件：模型永远拿不到伪造
   的工具结果（未注册工具必得确定性报错），以及缺能力时一定被明确告知"做不到，
   要如实说明"。最终回复是否如实，由评测集的诚实性簇验证红绿——这层保证
   靠测试钉住，而不是靠代码强改模型。
2. **能力缺口台账**（`agentforge/gaps.py` + 技能管理页新栏目）：三个记录源
   全部由架构判定，不靠模型自报——tool_missing（调用了不存在的工具）、
   capability_missing（预检发现能力缺失）、eval_fail（评测失败归因）。
   同类缺口合并计数、按次数排序，「该补什么工具 / 该沉淀什么技能」一眼看清。
3. **多路径尝试**（`orchestrator.run_task multi_path`）：对话框「自动拆解」右侧
   新增开关。开启时某一步失败（agent 报 error），先让当前模型拟几条互不相同的
   实现路径（只认编号行——模型回了句客套话宁可判为拟不出，退回内置三条通用
   路径），再逐条真跑，直到某条成功或试完。换的是「路」不是「模型」：模型不变，
   变的是手段。本地模型空闲且无 token 计费，多条路径近乎零成本；关闭时行为与
   旧版逐字节一致。（初版做成了「换池内备选模型」，与「预想几种方案逐个尝试」
   的本意不符，当天即重做——替身测试 M8 同时抓到拟路径解析把客套话当路径的洞，
   收紧为只认编号行。）
4. **评测集补簇**（对照权威口径）：诚实性簇 3 条（h1 发邮件 / h2 查余额 /
   h3 发 npm——环境里确实没有这些能力也没有替代路径，CAR-bench 式不可满足
   变体：正向宽松地说出"无法/失败"即可，反向严格禁编造话术）+ 安全拒绝簇
   1 条（System32 清空）。工具调用侧的权威参照是 BFCL 的 irrelevance
   detection（没有可用工具时不得调用、应明说）；稳定性口径是 tau-bench 的
   pass^k（同一条任务 k 遍全过才算过）——运行器加 `--repeat N` 直接支持。

验证：`test_preflight.py` 12 项、`test_gaps.py` 12 项、`test_multipath.py` 7 项
（替身 agent 模拟"第一次失败、换模型成功"），`test_evals.py` 增至 31 项
（诚实性簇判定方向逐条钉死：如实说→绿、编造→红、敷衍不提→红）。全量
18 个 Python 套件通过。

### 补记（第 24 步当天，UI）：悬停提示统一为圆角卡片

用户实测反馈两类问题：①「完全访问权限」悬停时会展开对话框下方的说明段落，

就不回写旧值）。权限说明段落与它的展开规则（.composer-wrap .hint、
bindPermHint）删除——说明内容由 permBtn 的 title 经卡片承载，布局零位移。

验证：`tools/test_tooltip.mjs` 10 项（卡片存在/样式定义、悬停显示同文本、

### 第 25 步：能力缺口独立成栏 + report_gap 登记（10-14）

用户实测暴露了诚实回答闭环的最后一环缺口：让 harness 发邮件，它如实说明
没有这个功能——回答对了，但「技能管理」栏目里什么都没出现。缺口的三个
既有来源都覆盖不到这个场景：预检能力表里没有邮件这一项（不知道要预告）、
tool_missing 只在真的调用不存在的工具时才触发（模型没调用）、而模型自己
发现了缺什么也**没有通道告诉架构**——它只能在回复里说说，说完就散了。

修法分三层，照旧"架构控制、不靠模型判断"：

1. **`report_gap` 工具**（`agentforge/tools/gap.py`）：模型发现完成任务
   必需的工具/能力或技能/方法论不存在时调用。调用本身是一次真实的工具
   调用（convo 里有据可查），kind=tool → capability_missing、kind=skill
   → skill_missing，name/spec 由架构**原样入账**到缺口台账，不做任何
   模型判断；返回值是架构写死的后续动作指令——缺工具：如实告知用户无法
   完成、绝不编造；缺技能：用 github_search / web_search 检索通用做法、
   在最终回复里总结出可操作的流程。入常驻工具名单（DEFAULT_CORE），
   模型随时能登记，不依赖按需检索才出现；
2. **预检补盲区**：能力表新增 email（信号：发邮件/邮件/SMTP/e-mail，
   必需工具 send_email）；「无法完成通告」里指路 report_gap——预检判定
   缺能力时，模型不但要如实说明，还要把缺失项登记下来；
3. **系统提示第 8 条「缺能力就登记」**：兜住预检信号没命中、模型自己
   发现缺东西的场景。

界面侧把缺口管理从「技能管理」里拆出来成为独立栏目「能力缺口」
（navGaps / viewGaps）：技能管理回归纯技能，缺口栏目自带刷新/清空，
视图显隐、顶栏标题、导航高亮、输入区隐藏与技能管理同一待遇。

### 补记（第 27 步当天，服务按钮）：重启按钮的弹窗风暴——三个根因

用户点侧栏「重启本地服务」后**不停弹出命令行窗口**喊着「服务没在运行」，
任务管理器杀不完，最后删掉 start.bat 才算了事。复盘出三个根因，全在
重启链的发起方式上，一个一个修：

1. **DETACHED_PROCESS 弹窗**（根因之首）：分离 cmd 用了
   `DETACHED_PROCESS`，它会给每个控制台子进程开【可见】窗口——链里的
   `python service.py --stop` 每次都弹窗喊话；用户关掉窗口只是杀了那个
   子进程，链还在走，于是「关了又弹」。service.py 里本来就有这条血泪
   注释（拉起 Web 服务必须 CREATE_NO_WINDOW），发起重启链时却没照做。
   修法：`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`，整条链连同
   子进程全程无窗口；
2. **`timeout /t /nobreak` 无控制台即失效**：它要读控制台输入，分离
   进程没有控制台，立即失败——「先等 2s 让 HTTP 响应发出去」的保险
   形同虚设。修法：换 `ping -n N 127.0.0.1 >nul` 做纯网络栈延时，
   不依赖任何控制台；
3. **stop.bat 的 pause 误判**：bat 末尾靠 `%cmdcmdline%` 判断是否被
   双击启动，被 cmd 链 `call` 进来时会误判而卡住。修法：整个重启链
   **不再借道 bat 转发层**——直接点名 `.venv` 解释器跑
   `service.py --stop`（与 service.python_exe() 同一口径），
   `start "" pythonw service.py` 拉起（空标题参数防路径被当窗口名）。

外加一道**服务端单飞锁**（`.run/restart.lock` 时间戳，60s TTL）：
重启是「会停掉本服务」的操作，HTTP 响应发出后前后端都没有兜底，
连点两次 / 多开一个标签页再点，两轮 stop/start 链叠在一起互相残杀
——这是弹窗风暴的放大器。60s 内的重复请求直接 429。

验证：test_service_ctrl.py 从 7 项扩到 **18 项**（L5 结构三查、L6 三个
根因不得回归：无 timeout / 无 .bat / 引号与空标题、L7 显式解释器、
L8 单飞锁四态：放行→拒绝→过期放行→续期）；并用与按钮**完全相同**
的调用路径做了端到端实测：POST /api/service/restart → 响应发出 →
失联 → 停止常驻 PID → 拉起新常驻 → 健康检查恢复，全程无窗口，
service.log 留下干净的「停止 → 启动 → 就绪」循环记录。

用户给出七步心智模型（意图识别 → 任务拆分 → 任务分配 → 任务执行 → 输出汇总 →

- 步骤 1–5 与实际基本一致，但有两处偏差：①「意图识别」是规则与启发

  等于用户「至多反复失败三次」的约定，也等于 CrewAI max_retry_limit=2 的

**对照权威范式**：这套七步流程就是 Anthropic 五模式里的 Orchestrator-Worker

**必须给循环设上限**——Anthropic 原文与独立工程参考 buildingeffectiveagents.com

1. **任务级闸门**：每个子任务一收尾，系统就按它**自己的任务书**（goal）亲自

   计划循环路径的多步任务同样每步一核（单任务 detail 即原始消息，仍由收尾
   闸门把守，避免同一命令验两遍）；
2. **汇总级闸门保留**：全部任务汇总后，系统再按总任务书把守汇总答复——

   上限仍失败的命令汇总级不再重跑，保证「至多三次执行」不翻倍；
3. verify 事件带上 task_id，评测报告与界面能看出是哪个任务的核验。

### 补记（第 29 步次日，f4 处置）：复制任务的验证前置——闸门在模型干活时就能拦

第四轮唯一失败 f4-backup-copy 怎么处理，两个方案摆给用户：①任务书加验证声明
让闸门在干活时就拦；②接受为模型能力差距。用户选 ①，且点明「如果只用改
harness 提示词的话」。落地时发现光改提示词不够，闸门机制有三处缺口要一起补：

1. **闸门认不了内联命令**：`extract_verify_cmd` 只认「指向工作区内真实脚本」
   的命令——`python -c "..."` 没有脚本文件可比存在性，声明整条被弃。而复制
   类任务的逐字节比对恰恰只能写成内联代码。修法：`-c` 内联放行（仍过
   `_DANGEROUS` 过滤），`_trim_command` 特判保住引号内代码段、只断引号外的
   人话尾巴。
2. **单任务路径没人补声明**：f4 走的就是单任务路径，任务书 = 用户原话，
   里面没有验证声明。修法：`verify.declare_copy_check`——复制/备份语义 +
   恰好两个文件名 token（第一个源、第二个目标）+ 没夹带改内容诉求 + 没有现成
   声明时，harness 替用户追加一条 `read_bytes` 逐字节比对。判据刻意保守：
   识别不了源/目标、要顺带改内容、多份复制、已有声明——一律不补，宁可少拦
   不可错拦。单任务路径模型与闸门看同一份补强后的任务书（book）；计划循环
   每步的 detail、调度器的 goal 同样程序化兜底补写（不押注本地小模型的指令
   跟随）。
3. **模型不知道正路是什么**：执行模型系统提示加第 5 条「复制/备份走命令，
   禁止 read_file 后 write_file 重写——文本往返会丢换行符与编码」；调度器
   提示词要求复制类任务的 goal 写死手段与验证声明。

声明补进任务书后三处同时生效：模型看得见验收标准；写盘后的**即时验证**跑它
（f4 那种错在干活时就被拦，不等收尾）；收尾闸门亲跑它。真实栈 e2e（gemma4:12b
重跑 f4 原题）一次通过：模型直接 `copy /y`、自己跑了比对、收尾闸门通过附报告。

### 补记（第 29 步次日，评测台）：一键出题与「新增任务」转跳修复

用户报两件事：评测台点「新增任务」页面会转跳到下面；新增要填的字段太多。

1. **转跳的根因**：新草稿被 push 到清单**末尾**再 `scrollIntoView` + `focus`，
   整页被拽到底部。修法：草稿 `unshift` 置顶渲染（renderEvalTasks 草稿先行、
   不带分类头），点「新增任务」几乎不滚动。
2. **只填任务，其余 LLM 一键生成**：新草稿先渲染成「草稿编辑器」——只有任务
   指令一个输入框 + 取消 / 手动填写 / **LLM 一键生成**三个按钮。生成走新端点
   `POST /api/evals/suggest` → `evalsdesk.suggest_case`：复用调度决策模型出
   id/分类/seed/expect/notes，产出过程序收口（`_sanitize_suggestion`）——
   分类白名单、id 规范化与去重、危险核验命令黑名单拦截（模型生成的 check
   会被程序真跑）、悬空 `check_contains` 拆除（判定器只在 check 层内读它，
   没有 check 就是假判定）、单元素数组收成字符串（judge 只支持单字符串比对）。
   真模型冒烟抓到过 `wc -l`（Unix 命令，Windows cmd 跑不了）——平台约束写进
   出题提示词。生成不可用/产出不可解析时如实报错，退回手动全字段编辑器——
   生成是辅助，「无判定不进评测集」的底线不让步。
