## 1. P9：`if __name__ == "__main__"` 静默跳过（一行，影响最大）

**改法**（`agentforge/tools/ops.py`）：

```python
env = {"call": sdk_call, "tools": tools_mod, "print": _print,
       "__name__": "__main__",          # ← 新增
       "__builtins__": script_builtins}
```

**为什么必须是这一行**：`exec` 的环境里没有 `__name__` 时，名字查找会回落到
`builtins` 模块的字典，值是 `"builtins"`，于是守卫恒假——`main()` 一次都不调用，
脚本"成功"、零工具调用、**零报错**。这是模型最标准的 Python 写法，不该被环境坑。

**验证**：`test_ops_batch` 里加了带守卫的脚本，断言「真的执行了」且「不再退化成 0 次调用」。
本地另用独立脚本复现了「不加 → MAIN 不打印 / 加了 → 打印」，机理确定。

## 2. P5：脚本内禁直连网络

**改法**：`_guarded_import` 命中 `socket / ssl / requests / urllib / urllib3 / http /
httpx / aiohttp / ftplib / smtplib …` 时抛 `ImportError`，并直接告诉模型改用
`fetch_url / fetch_json / web_search / github_search`（走工具层的结果才带 `[实测]` 标记）。

**为什么禁而不是只警告**：绕过的数据没有来源标记，`false_provenance` 与引用核对
**全都看不见它**——证据链静默断裂，而表面上没有任何异常。只警告等于把"静默"变成
"有字但没人看"。

**验证**：`test_ops_batch` 断言出现 `[脚本拦截]` 且提示里有替代工具。

## 3. P11：「0 次工具调用」按成因分流

**改法**：三种形态各给一句话：

| 形态 | 输出开头 | 依据 |
|---|---|---|
| 脚本抛异常 | `0 次工具调用 · 脚本异常中断（NameError: …）` | 执行时捕获的异常 |
| 写了调用但没执行到 | `0 次工具调用 · 脚本里写了 read_file，但一次都没执行到` | `tooltrace.names_from_script` |
| 真没写调用 | 原文案（三引号/注释/分支/工具名错） | 源码里没有 call |

**为什么**：三者的处置完全不同（改环境 / 改一行 / 重试），混记成同一个
`tool_error` 指纹就没有诊断价值；本轮就是靠人工翻脚本才把它们分开的。

## 4. P10：把内层工具签名摊进系统提示

**改法**（`loop.py`）：PTC 常驻时，在「可编入脚本的工具」清单后追加一段

```
## 脚本内工具签名（照抄，别猜）
  - read_file(path)
  - write_file(path, content)
  - edit_file(path, old_text, new_text)
  - run_command(command, …)
  - github_search(query, sort=…, limit=…)
  …
```

签名从 `registry` 现取（必填原样、可选写 `x=…`），只列 10 个常用工具，不回到
"全量 schema 占 4000 token"的老路。

**为什么**：31 轮里 21 次参数名错，全部是猜的（`content` 是 `write_file` 的词、
`type` 是 GitHub REST 的词）；而报错里给了正确签名后模型下一轮就改对——
**看不见才是根因，不是学不会**。

**验证**：`test_ptc_resident` 断言 `edit_file(path, old_text, new_text)` 在块里、
`github_search` 那一行有 `sort` 没有 `type`、系统提示真的带上了、非 PTC 模式不重复下发。

## 5. P3：末次写盘失败时，自验不许背书

**改法**：
- `verify.write_outcomes(convo)`：只读 harness 自己印的【系统核对·写盘结果】，
  按产物路径取**末次**状态（一次失败后重试成功 = 自愈，不算失败；末次仍失败才算）。
- `verify.report_block(cmd, res, write_failed=…)`：有失败时不再写「以本结果为准」，
  改为「只证明**命令能跑通**，不证明改动发生过；本轮末次写盘仍失败：xxx。
  **不要据此声明任务已完成。**」
- `orchestrator` 在收尾自验处把 `write_outcomes` 传进去。

**为什么取"末次"**：soak02 的 c6 是「edit_file 传错参数 → 下一轮 write_file 写成」，
属于自愈；按"出现过失败"判会天天误伤，按"末次"判才既不误伤也不放过 rerun64 那种
「唯一一次写就失败、一个字没改却答已完成」。

**验证**：`test_verify_gate` 9 条，含「先失败后成功 → 成功」「先成功后失败 → 失败」
「没有权威块 → 不猜」。

**为什么不直接把闸门关掉**：w3 那类「文件写对了、答复把事实丢了」仍然要管；
所以保留"两边都没有 → 判缺"，只是把"产物里有"从误报里摘出去，并把措辞降级成
「答复里没复述（文件里已确认存在）」。

**验证**：`test_keyfacts` 7 条，含「只比答复会判缺（旧口径）→ 纳入产物后不判」

## 9. P8/P7：把"没响应"变成可见的失败

三层改动，从上游往下：

1. **请求级空闲超时**（`llm.py`）：`_post_chat` 用 `timeout=(10, idle_timeout)`；
   流式读取包一层 `_idle_lines`，把 `requests.Timeout` 翻成 `ModelIdleTimeout`
   （**刻意不继承 `requests.Timeout`**，否则会被 `chat_stream` 的重试分支吞掉、
   把等待翻倍），文案是「模型 180s 内没有返回任何新内容（端侧可能已卡住）…不是慢，
   是没有响应」。
2. **远端 provider 同样处理**（`providers.py`）：`_guarded_lines` → `ProviderError`。
3. **评测侧硬墙钟**（`bench_tasks.py`）：把 `deadline` 也交给 `run_task(stop_check=…)`，
   流式循环每收一行问一次，到点立刻中断生成并记 `超时（>N s，硬墙钟）`——
   修掉「判断写在事件循环体里、没有事件就走不到」的根因。

配置：`ollama.stream_idle_timeout: 180`（默认 180s；在线模型可调 60）。

**验证**：新套件 `test_model_timeout` 13 条（含"不是 Timeout 子类"这一条 —— 它保证
超时不会被重试逻辑吞掉、等待不会翻倍）。
