# 澄清弹窗判定规格（clarify policy）

> 本文回答一个问题：**什么情况下才允许弹窗问用户。**
> 不涉及"问了之后怎么办"——那部分（超时降级、无人值守、评测脚本答案、单轮预算）
> 已经在 `agentforge/interact.py` 里实现完整，且与 PTC 无关，**本次重规划不动它**。
>
> **阅读顺序**：§3 是目标形态（完整判据）；**§12 是当前要真正写进代码的试行版 v0**（只有两条
> 规则，因为本机是本地量化模型，凡依赖模型"想一下"的判据都不可靠）；§12.4 是全部参数的台账
> （**均为待实测，没有一个是实测值**）。其余章节是推导过程与外部对标。
>
> 现状代码在 `agentforge/loop.py`（`_lookup_signal` + 无条件早退分支），
> 测试在 `tools/test_ambiguity_gate.py`（已红，见 §9）。

## 1. 为什么要重写判据

### 1.1 表层原因：PTC 把输入掐断了

PTC 常驻后，模型不再直接调 `list_dir`，而是写脚本由 `ops_batch` 执行。harness 看到的
工具名统一变成 `ops_batch`，而判定函数的第一道闸是 `name not in _RETRIEVAL_TOOLS`。

```
PTC_SURFACE      = {ops_batch, ask_user, find_tools}
_RETRIEVAL_TOOLS = {list_dir, find_files, search_code, read_file,
                    github_search, web_search, fetch_url, fetch_json}
交集 = ∅  ⇒  信号永远记不上  ⇒  弹窗永远不触发
```

**PTC 必须常驻（省 89% 上下文），所以不能退回逐个暴露工具。** 只能把"哪次调用、产出了什么"
的配对补回来——这是事实采集问题，不是判据问题。

### 1.2 根本原因：判据口径本来就不对

即使把配对补回来，现有判据仍然是 **「检索动作没命中」**，而你要的是 **「缺了它就完全执行不下去」**。
两者差两道校验：

| 现有判据 | 反例（会误弹） |
|---|---|
| `list_dir` 空目录 | 任务是"在空工作区里新建一个文件"——空目录是**预期状态**，不是缺信息 |
| `web_search` 零命中 | 该信息本来就要从 GitHub API 取，只是渠道没选对 |
| 检索到多个候选 | 任务原文已经限定了范围（"star 最高的那个"），不必问 |
| 模型回复带问号 | 它只是礼貌性确认（"以下方案可以吗？"），不是缺信息 |

结论：**"未命中"是"缺信息"的必要条件，不是"执行不下去"的充分条件。** 重写判据比修管道更值。

## 2. 术语先把两类东西分开

混用这两个词，直接导致交接文档把真回退误判成"测试陈旧"。

| | **核查闸门**（`grounding.gate`） | **澄清触发器**（本文） |
|---|---|---|
| 职责 | 证伪答复：命令/包名/引用是否有据 | 决定要不要停下来问用户 |
| 输出 | 「这次一定错」+ 依据 | 「要不要问」+ 理由码 |
| 取数 | 工具结果全文（`role=='tool'`），**不看工具名** | 每次调用的「工具名 + 参数 + 产出」三元组 |
| PTC 影响 | 无 | 直接断供 |
| 名字 | `grounding_gate` | 建议由 `ambiguity_gate` 改为 **`clarify`** |

**用词约定**：以下一律称"澄清触发器 / clarify"，不再叫 gate。

## 3. 定义：什么叫「缺失某些信息就完全执行不下去」

> **任务要求了一个具体的东西（槽位），它在本次全部证据里一次都没出现过，
> 该找的通道已经找完，而且这次运行已经表现出走不下去的迹象。**

判定 = **C1 ∧ C2 ∧ C3 ∧（追问 ∨ 停滞）**。前三条件是证伪（这信息在本场拿不到），
第四个只决定"什么时候弹"。少任何一条都不弹（宁可少问，不可误伤）。

### C1 必需性：缺的是"槽位值"，不是"细节"

任务原文点名要求一个具体实体，且它在交付物里必须出现（不是可选修饰）。

判定的确定性做法（只用文字特征，不做语义猜测）：

- **专名标记** → 视为必需：全大写缩写（`REA`）、引号/书名号内（`"draft.md"`、`《三体》`）、
  CamelCase、含数字的标识（`gpt-4`）、带路径分隔符（`src/app.py`）。
- **动作宾语位** → 视为必需：紧跟在 找 / 查 / 打开 / 改 / 修 / 发给 / 基于 / 转到 / 对齐 之后的词。
- **泛指量词** → 视为**不必需**：`一个` / `某个` / `任意` / `某个开源` + 品类词。
  例：「找一个 Markdown 转 pptx 的工具」——品类词不是槽位值，缺了不算卡死。

### C2 不存在性：证据里**边界匹配**零命中

在本次全部证据（工作区清单、已抓网页/API 正文、全部工具输出）里做**边界匹配**
（`_bounded_in`：前后不能是 `[A-Za-z0-9._-]`，见 `pitfalls.md` 第 3 条）：

- 一次都没出现 → 不存在。
- 出现过但只是**前缀/后缀巧合**（`marp-team/marp` vs `marp-team/marp-cli`）→ 仍算不存在。
- 出现过且命中 → **不弹**（信息其实有，模型的病在别处，见 §5 的 redirect）。

注意：这里判的是**证伪**——"这个实体在本场证据里不可用"，不推测"用户心里想的是哪个"。

### C3 不可再查性：应走的通道已经走完

通道清单（按实体类型定，不按模型爱用什么定）：

| 实体类型 | 必走通道 |
|---|---|
| 代码/项目/包 | 工作区检索 → `github_search` / `exact_repo_lookup` / `npm` |
| 网页/文档/事实 | `web_search` → `fetch_url` |
| 本地文件 | `list_dir` / `find_files` / `read_file` / `search_code` |
| 模型/服务 | 本地模型清单接口 |

还有没试过的通道 → **不弹**，改为重定向（§5）。这条同时守住"检索不努力就甩锅用户"。

### C4 走不下去的行为证据：**追问** 或 **停滞**（二者其一即可）

C1∧C2∧C3 证明的是「这信息在本场拿不到」；C4 证明的是「这次运行已经走不动」。
两个可替代的**充分条件**，谁先出现用谁：

| 证据 | 判定 | 时效 |
|---|---|---|
| 模型在回复里追问，且问句指向 C1 抽出的槽位 | 立即满足 | **快**：省掉等它自己撞墙的那两轮 |
| 同 `(工具, 参数摘要)` 第 N 次出现；或连续 2 轮输出等价（长度 + 前 M 字指纹） | 满足 | 慢：模型不问也得等它真的原地打转才弹 |

> 这里的 N、M 以及"连续 2 轮"**均为待实测**，暂定值见 §12.4 参数台账。§3 是目标形态，
> 当前要落地的判定见 **§12 试行版 v0**。

**为什么不把"模型追问"直接降成纯日志字段**：那样会漏掉"实体真缺、模型压根不问、正准备瞎猜"
的情形——那正是幻觉的源头，也是这条触发器最该管的场景。
**为什么不把它当必要条件**：礼貌性确认（"以下方案可以吗？"）也带问号，C1/C2 不成立时它
自然不弹；所以它不是判据，是**加速器**——判据始终是 C1∧C2∧C3。

推论：模型没问 ≠ 不弹；模型问了 ≠ 一定弹。日志里记 `asked_by_model: true/false`
和 `trigger: "model_asked" | "stalled"`，复盘时才知道是哪条路径弹的。

## 4. 反例清单（不该问的，优先级最高）

判断顺序必须先跑完这五条，任何一条命中就**不弹**：

1. **答案已经在本次证据里**（模型没读）→ 不弹，指向"第 N 条工具输出里就有"。
   这是"上游没修好"，弹窗会把 harness 的失职转嫁成用户的负担。
2. **还有没试的通道** → 不弹，指明缺哪条通道。
3. **有唯一合理默认且动作可逆** → 不弹，带假设继续并在交付里注明。
   例：输出目录（`outputs/`）、文件命名、交付格式（按任务动词推）。
4. **缺的是偏好/风格**（篇幅、语言、排版）→ 不弹，按默认做，做完再说。
5. **泛指任务**（"找一个…的工具"）→ 不弹，品类词不构成槽位。

## 5. 判定输出不是一个布尔值，是三个动作

纯函数，不碰状态、不发事件，便于穷举测试：

```python
decide(task_text: str, facts: Facts) -> Decision
# Decision.action ∈ {"ask", "redirect", "proceed"}          # ask 还是唯一会弹的那个
# Decision.slot   ∈ {"entity", "location", "platform", "credential"}
# Decision.irreversible: bool     # 动作不可逆（删/覆盖/发布/发送），只是「提高阈值」的修饰
# Decision.reason ∈ {"MISSING_ENTITY", "CHANNELS_EXHAUSTED", "ANSWER_IN_EVIDENCE",
#                    "RECHECK_AVAILABLE", "DEFAULTABLE", "PREFERENCE", "GENERIC_TASK",
#                    "CREDENTIAL_MISSING", "IRREVERSIBLE_TARGET"}
# Decision.trigger ∈ {"model_asked", "stalled", "none"}      # 复盘用：走哪条路径弹的
# Decision.question_seed / options / evidence_refs
```

| action | 含义 | 谁在用 |
|---|---|---|
| `ask` | 弹窗 | C1∧C2∧C3∧(C4) 成立 |
| `redirect` | 不弹，回灌一句"往哪走" | 反例 1、2 命中（这就是今天 `results_look_generic` / 重试硬提示该待的位置） |
| `proceed` | 不弹，带假设继续并在交付里盖章 | 反例 3、4、5 命中 |

**本期范围（重要）**：`redirect` 只接管**反例 2（缺通道）**这一种。反例 1（答案在证据里）
以及现有的 `results_look_generic`、重试硬提示、`ask_budget` 降级提示**先留在原位不动**——
它们各自都有测试钉着，一次性收拢等于同时改四处的行为，回归面太大。
`decide()` 的签名按全集设计，实现分两步落地，不要求一次到位。

### 5.2 槽位类型决定走哪条通道（不是所有"缺"都该问）

弹窗只能解决**"用户脑子里有、系统里没有"**的信息。搞错通道，问了也是白问。

| 槽位 | 例子 | 走哪条通道 | 为什么 |
|---|---|---|---|
| `entity` 目标实体 | 哪个项目/仓库/客户 | **弹窗** | 只有用户知道 |
| `location` 目标位置 | 哪个文件/目录 | 先推默认（cwd / 唯一候选），推不出再弹 | 多数可从现场推出 |
| `platform` 格式/平台 | pptx 还是 pdf | **不弹**，`proceed` + 声明 | 有默认，且可逆（重生成） |
| `credential` 凭据/权限 | token、账号密码 | **不弹**，结构化报错 + 停下 | 用户答"我有"也继续不了，得去配置；弹了反而让人以为答完就行 |

**「不可逆」不是一个槽位，是一个修饰词。** 它不决定"缺的是什么"，只决定**同一个缺口在什么
把握度下才允许继续**：

| 缺口类型 | 动作可逆（查、读、生成草稿） | 动作不可逆（删、覆盖、发布、发送） |
|---|---|---|
| 零命中（C2 absent） | 若有默认 → `proceed` + 声明 | 必须 `ask` |
| 多候选（C2 multi） | 选最像的一个 → `proceed` + 声明 | 必须 `ask` |
| 唯一命中 | 直接做 | 直接做（对象已唯一，不弹） |

这张表是**唯一**的阈值差别。原来把它写成并列槽位（`target_of_irreversible`）是错的：
它让"不可逆"看起来像另一类信息缺口，实际上它只是把 `location`/`entity` 的容错从
"允许猜"收紧到"必须唯一"。

关键：**reason 必须能翻成一句人话给用户看**（"我问你是因为：任务点名要 REA，但工作区、
GitHub、网页三条通道都没有这个名字"）。看得到理由，误报才能被发现——这是"闸门必须可见"
的同一条纪律。

### 5.3 与「完全访问权限」的关系（两根不同的轴，不能互相顶替）

这是最容易做错的地方，必须写死：

| | **权限轴**（允不允许做） | **指代轴**（做哪一个） |
|---|---|---|
| 问的是 | "你能删这个文件吗" | "你说删旧的那个，是 10-19 版还是 10-20 版" |
| 现有实现 | `Guard.needs_approval()` + `config.require_approval`（8 个工具） | `decide()` + `ask_user` 弹窗 |
| 完全访问权限下 | **全部放行**（`auto_approve_all=True` → `needs_approval` 直接 `False`） | **照常判定，不受影响** |
| 本次是否改动 | **不动，一行都不改** | 重写判据 |

关键点：**用户给了完全访问权限，只是回答了"允不允许"，没有回答"是哪一个"。** 后者是信息
缺口，不是信任缺口——授权再高，也变不出"旧的那份"是哪份。

反过来说，这条也**不构成**执行层拦截（原设计里的"`Guard` 硬拦"已撤回，理由见下）：

1. **会跟完全访问权限打架**：`auto_approve_all` 是用户显式表达的"别一次次问我"，在 Guard
   里再插一条拒绝执行，等于绕过这个设置。
2. **Guard 判不了**：它运行时只看到 `(tool_name, {"path": "a.md"})`，没有任务上下文，
   无从知道"这个 path 是不是用户指的那个"。判"目标不明"必须有任务文本，那是 `decide()` 的活。
3. **硬失败的体验比弹窗差**：弹窗至少还能答一句继续，硬拦是直接停。

执行侧要保留的是**更便宜、且不需要问你**的那层：目标不唯一时先让模型自己核实
（`read_file` / `list_dir` 确认），核不出来再走 `ask`。这属于 C2/C3 的取证要求，
不需要新增权限代码。

**效果举例——「改代码」这一类几乎不可能触发弹窗**（这是用户最常干的活，必须保证）：

| 场景 | 判定 | 结果 |
|---|---|---|
| `edit_file("agentforge/loop.py", …)` | 对象唯一（模型点名 + 文件存在） | **不弹**，直接做 |
| `write_file("config.yaml", …)` 覆盖 | 对象唯一 | **不弹**，直接做 |
| "把这个模块重构一下"（没点名） | C1 不成立（无专名） | **不弹**，`proceed` + 在交付里声明假设 |
| "把 REA 那个仓库归档掉" | 实体零命中 + 不可逆 | **弹**（"REA 是哪个仓库"） |
| "覆盖掉上周那版报告" | 多候选 + 不可逆 | **弹**（列出候选让选） |
| "把这份报告发给老王" | 通讯录里两个"老王" + 不可逆 | **弹**（选人） |

也就是说：**弹窗只在"任务点了名 + 现场定不了唯一 + 猜错回不来"三件事同时成立时出现。**
正常改代码永远满足不了第三条。

### 5.1 选项从哪来（现状最粗糙的一环）

现在零命中时硬给 `["本地项目", "git上的项目", "其他"]`——这是**业务假设**，不是证据。
重规划后按来源分两类，且必须标明来源：

| 场景 | options 来源 | 标注 |
|---|---|---|
| 多候选未收敛（C2 的 multi 分支） | 检索命中的真实候选名（repo / 包名，≤3 个）+ `其他` | 有证据 |
| 零命中（C2 的 absent 分支） | 由**任务动词**推出所属类别（查找类→本地/代码托管/网页；凭据类→"我有/没有/换方案"） | **业务假设，前端要写"以下为推测选项"** |

不允许：把模型猜的名字塞进选项（那等于替用户作答）；选项超过 4 个；选项里出现本次证据中
不存在的具体值。

## 6. PTC 常驻下必须采集的事实（这是本次真正的上游）

判定要的输入不是"合并文本"，是**每次调用的三元组**。合并文本里同时可能有
`list_dir` 的空目录和 `write_file` 的"文件不存在"，扫文本必然把 A 的结论算到 B 头上
→ 那正是最忌讳的误伤。

采集规格（挂在 `ops_batch` 每次脚本内 `tools.call` 上）：

```json
{"tool": "list_dir", "args": {"path": "..."},
 "ok": true, "kind": "empty|multi|hit|error|denied",
 "candidates": ["owner/repo", "..."], "output_head": "前 2000 字"}
```

宿主要维护的运行级累加量：

- `channels_tried: set[str]`（工作区 / 代码托管 / 网页 / 服务）
- `repeat_counter: {(tool, args_digest): n}`
- `evidence_text: str`（全部工具输出，已有 `grounding.sources_from_history` 可直接复用）
- `task_slots: [{name, source, required}]`（C1 从任务原文抽）

**约束**：事实必须由采集层结构化上报（事件/属性），**不允许**从 ops_batch 的合并文本里
正则反解——那等于把管道问题变成解析问题，下一次改脚本输出格式就再断一次。

## 7. 兜底（沿用现状，只加两条）

`interact.py` 已经覆盖四层，本次不动：

| 场景 | 现状行为 |
|---|---|
| 交互模式，用户不理 | 180s 超时 → 降级"自行假设并注明"（180s **待实测**，本地无 API 成本，可放宽） |
| 后台/定时/派发（`no_user=True`） | 直接降级，不弹、不阻塞（rerun50 的根治） |
| 评测（`answers` 脚本） | 按 `ask_answers` 逐条答；无脚本则"无用户作答"提示 |
| 单轮预算 | 3 次用完自动降级（3 次 **待实测**） |

**新增两条**：

1. 弹窗事件必须携带 `reason` 与 `evidence_refs`，前端展示"为什么问"。
   理由码不明或证据为空时**禁止发弹窗**（程序侧断言）——防止哪天又退化成凭感觉弹的框。
2. **同一槽位只问一次**（`asked_slots: set`）：用户答过的槽位不再问，哪怕又出现未命中信号。
   现在的"单轮 3 次"只管次数、不管重复；同一件事问两遍比问三件不同的事更伤体验。

## 8. 上线分三步（先观察，再接管）

| 阶段 | 动作 | 行为变化 | 观测 |
|---|---|---|---|
| **P0 影子** | 采集事实 + 计算 `decide()`，只发 `clarify_decision` 事件 | **零变化**（不弹） | 每跑记录 `would_ask` / `reason`；连续 3 跑核对照例清单 |
| **P1 接管** | `ask` 分支真正弹窗，保留现有 ask_budget 兜底 | 弹窗恢复 | 每次跑记 `误伤数`（用户点"其他"或答"我没问这个"记为误伤） |
| **P2 收敛** | 依据 P1 数据删掉不成立的 reason | — | 误伤率 < 1/10 跑才允许长期开 |

P0 是必须的：**先看清它会说什么，再让它开口。** 直接上 P1 等于把一个新判据推到真实用户面前赌。

## 10. 明确不做

- **不用语义相似度判"缺什么"**：不可解释、不可穷举测试，误伤了也不知道为什么。
- **不让弹窗承担检索职责**：通道没走完就弹 = 把活儿丢给用户（现有 ask_budget 的初衷）。
- **不从合并文本反解事实**（§6 约束）。
- **不在弹窗里给答案**：只问"是哪一个/属于哪一类"，不猜"应该是 marp-cli"。

## 11. 已知抓不准的三处（写在这里，免得下次又误判成"功能坏了"）

1. **别名识别不了**：证据里写的是 `marp-cli`、任务里写「Marp 的转换工具」——边界匹配不同，
   C2 会判"不存在"从而**误弹**。反向也有：中文专名没有大小写标记（"帮我找三体那个项目"），
   抽不出槽位 → **漏报**（漏报是安全侧，可接受）。
2. **"空白但预期为空"分不清**：任务本身就是"新建/清空"，空目录是正常状态。靠任务动词
   （新建/创建/初始化）排除，动词表之外的情况会误弹。
3. **停滞阈值是经验值**：`同参数第 N 次` 对"确实需要重跑"的脚本会误判为停滞。
   P0 影子期先收数据，别先定死（全部参数见 §12.4，均为待实测）。

## 12. 试行版 v0（当前要落地的那一版）

> §3 那套 `C1∧C2∧C3∧C4` 是**目标形态**，不是第一版。本节是**实际要写进代码的**那一版：
> 规则更少、信号更硬、全部可穷举测试。

### 12.1 为什么不能照抄其他家

| 其他家做法 | 依赖什么 | 本地量化模型能不能用 |
|---|---|---|
| Claude Code / Cline：模型主动调提问工具 | 模型自己判断"我缺信息" | ❌ 弱模型不会主动承认缺信息，更常见的是一边缺一边瞎猜；反向也失效——它会把礼貌确认也当成"该问" |
| Windsurf：act, don't ask | 强模型猜得准 | ❌ 猜错就毁工作区（82 文件事故） |
| 置信度阈值路由 | 模型自评分数 | ❌ 小模型自评普遍过度自信，分数没有校准，等于拿噪声当阈值 |
| Vercel `needsApproval: (input) => ...` | **参数匹配规则** | ✅ 纯确定性，不碰模型 |
| LangGraph 在图节点插 `interrupt` | **插桩位置固定** | ✅ 位置可固定 |

**结论：只移植"确定性规则"和"固定插桩位置"这两样，凡是要模型"想一下"的一律砍掉。**
这也是本文档相对 §3 的最大让步：C1（抽槽位）、C3（通道是否走完）、置信度，v0 全部不做。

### 12.2 试行版只有两条规则

**R1 · 盲选不可逆目标（唯一"必问"规则）**

```
条件（全部为确定性信号，逐条可测）：
  ① 最近一次检索（list_dir / find_files / search_code）返回候选数 N ≥ 2
  ② 此后到不可逆调用之间，没有任何 read_file 命中其中任一候选
  ③ 紧接着调用不可逆工具：delete_file / write_file(目标已存在) / publish / send / run_command 含删除语义
→ 必问
```

为什么它是第一条：**模型在多候选里随手挑一个就删/覆盖，是弱模型最典型的破坏行为**。
Windsurf 那个"4 分钟改错 82 个文件"就是这条缺失的后果。三个信号全是解析工具返回 + 比对
工具名，不需要模型理解任何东西。

> **可实现性已核对**：`list_dir` 的输出是 `{path}\n共 {len(dirs)} 个目录 / {len(files)} 个文件`
> （`fs.py:423`），候选数可用正则稳定提取。**PTC 下这三个信号必须从脚本内的 per-call 记录取**
> （§6 的三元组），不能扫 `ops_batch` 的合并文本——合并后就分不清"哪次检索、几个候选"了。

**R2 · 模型自认不确定 + 检索零命中（"可问"规则）**

```
条件：
  ① 本轮有 ≥1 次检索且判定为零结果（复用 `_lookup_signal` 的 empty 分支，纯字符串匹配）
  ② 模型本轮回复的**末尾 M 字符内**出现 "？" 或 "?"（问号在前文正文里不算）
     —— M 暂定 200，**待实测**（见 §12.4）
→ 问
```

这是 v0 里**唯一借用模型**的地方，但借的是**标点位置**这个结构信号，不是语义判断。
弱模型打问号这个行为是稳定的，而它"想问什么"不可靠——所以问题由 harness 生成（见 12.3）。

> **实现避坑**：现有 `_EMPTY_MARKERS`（`loop.py:362`）里混了 `"文件不存在"`（属于 `read_file`），
> 那不是"检索零命中"而是"目标文件不存在"，**R2 不能直接复用它**。R2 的白名单应限定为
> `list_dir / find_files / search_code / github_search / web_search`，排除 `read_file` 与
> `fetch_*`，否则"读一个不存在的文件"也会触发提问。

> 保留 R2 的理由：它覆盖了 §1.2 里"实体真缺、模型正准备瞎猜"的场景，成本几乎为零
> （只看字符串）。但它**不是必问**：C1/C2 没做，所以 R2 命中不代表真的缺信息，可能只是
> 模型的礼貌确认。因此 R2 触发后仍要过 §4 的反例过滤（尤其"答案已在证据里"）。

**R3 · 其余全部放行。** 具体包括不做：

| 不做 | 原因 |
|---|---|
| C1 抽槽位（专名/动作宾语位） | 中文任务 + 弱模型，抽不准；误抽比不抽更糟 |
| C3 判断"通道是否走完" | 判"走完了"最容易被误判，而它正是"少问"的守门人，判错就变成甩锅用户 |
| 停滞检测（同参数第 N 次） | 现有重试硬提示已覆盖；再叠一层容易和它打架 |
| 影响面统计 | 需要跨调用聚合，P1 再加（见 12.5） |

### 12.3 问题由 harness 生成，不由模型生成

弱模型写的问题经常跑偏（问得太宽、夹带错误候选、把答案写进问句）。所以 v0 用**固定模板 +
真实证据填充**：

| 触发 | 模板 | 选项来源 |
|---|---|---|
| R1 | 「我要{删除/覆盖} `{path}`，候选有 N 个：{A}、{B}…，是哪个？」 | **本次检索的真实结果**，最多 3 个 + `其他` |
| R2 | 「没在{工作区/GitHub/网页}找到「{X}」，你要的是？」 | 由检索用过的通道推类别 + `其他` |

约束对齐 Claude Code 的硬限制：每题 **2–4 个选项**；`其他` 由前端自动提供且**不出现在选项
列表里**；用户输入的自定义文本**直接作为答案值**返回（而不是返回"其他"）；header ≤ 12 字。
**禁止**把模型猜的值塞进选项——那等于替用户作答。

### 12.4 参数台账（全部「待实测」）

以下是本文档出现过的所有数字。**没有一个是实测来的**，全部是拍的，一律按待实测对待，
代码里集中定义成一组的常量，方便影子期后统一改：

| 参数 | 暂定值 | 状态 | 怎么测出来 |
|---|---|---|---|
| `ask_budget` 单轮上限 | 3 | **待实测** | 影子期统计每任务实际需要问几次的分布，取 P90 |
| R1 候选数门槛 | N ≥ 2 | **待实测** | 统计正常任务里"检索返回 ≥2 项后紧接着不可逆调用"的出现频率 |
| R2 问号窗口 | 末尾 200 字 | **待实测** | 试 100 / 200 / 500，看判定结果是否稳定，取最稳的 |
| 停滞：同参数第 N 次 | 2 | **待实测** | 统计同参数重复的分布，区分"重跑"与"打转" |
| 输出等价：指纹前缀 | 200 字 | **待实测** | 同上 |
| 交互超时 | 180s | **待实测** | 本地无 API 成本，可放宽；按实际响应时间分布定 |
| 影响面阈值（P1） | 3 个文件 | **待实测** | 统计改代码任务触及文件数的分布 |
| 误报合格线 | < 1/10 | **待实测** | 影子期人工核对「问了但本不该问」的比例 |

> **关于"预算"的更正**：本机是本地 agent，除了电费没有按次计费。所以这里的"预算"**不是钱**，
> 是两个东西——**打扰次数**（用户被中断几次）和**等待时间**（每轮本地推理的耗时）。
> 后者对本地模型更贵：多问一轮 = 多一次完整推理。因此 v0 的原则仍是"宁少问不多问"，
> 只是理由从"省 token"换成了"省用户的时间和耐心"。审批与澄清仍然共享同一份注意力，
> 这条不因为免费而失效。

### 12.5 怎么迭代（加规则/删规则都要有门槛）

| 动作 | 门槛 |
|---|---|
| **加一条规则** | 必须同时给出两条用例：一条它该弹、一条它不该弹。缺一条不许进。 |
| **删一条规则** | 连续 10 次跑里触发 0 次，且没有对应的失败案例 → 要么信号坏了，要么场景不存在，删。 |
| **调一个参数** | 必须来自影子期数据，不许再拍第二个数。 |
| **升级到 §3 完整判据** | 仅当 R1/R2 的影子期误报率 < 1/10 且漏报有明确案例时，才逐条加 C1/C3。 |

P1 才加的两项：**影响面统计**（跨调用聚合改了几个文件）和 **`proceed` 拆两档**
（静默 / 带可撤销声明）。这两项都需要改交付文案与执行层，不放进 v0。

### 12.6 落地位置（2026-10-21 已实现）

| 职责 | 文件 | 说明 |
|---|---|---|
| 判定状态机 R1/R2、候选提取、问题模板、参数台账 | `agentforge/clarify.py` | 新增。原 `loop.py` 里的信号识别常量整套迁入，`loop.py` 只做重新导出 |
| 单次调用的「工具名 + 输出」喂进判定器 | `loop.py` `Agent._execute` | **唯一咽喉点**：直连调用与 PTC 脚本内层调用都经过它，所以不需要（也禁止）扫 `ops_batch` 合并文本 |
| R1 执行前拦截 | `loop.py` `_execute` → `_clarify_precheck` | 在 `claim_write` / `tool.run` **之前**，返回非 None 即不执行 |
| R1 弹窗补发 + 答复回灌 | `loop.py` `run()` 工具结果之后 | 见下方「线程坑」 |
| R2 收尾弹窗 | `loop.py` `run()` 无工具调用的收尾分支 | 先翻记忆，再弹窗，再问是否存记忆（流程不变） |
| 开关与模式 | `config.py` `clarify_mode` | `on` / `shadow` / `off`，默认 `on` |

**必须记住的线程坑**：`interact.py` 的会话上下文（脚本答案 / `interactive` 标志 /
预算）是 **thread-local**。R1 的拦截发生在 `ops_batch` 的脚本线程里，在那里直接
`interact.ask()` 会**静默退化成「无用户作答」**——用户永远看不到弹窗，日志里也像
正常降级。所以拦截与提问必须拆开：脚本线程只负责「拦下 + 登记」，弹窗由 `run()`
在主线程补发。这条已写进 `docs/pitfalls.md` 第 11 条。

由此带来一个可见的行为差异：**R1 的弹窗出现在工具结果之后**（先 `ops_batch`
返回「本次未执行」，紧接着才是 `ask_user` 事件，答复以 user 消息回灌）。事件顺序
看着别扭，但它换来的是「拦得住」+「问得出去」两件事同时成立。

测试：`tools/test_clarify_v0.py`（R1 该弹 3 条 / 不该弹 6 条、R2 该弹 1 条 / 不该弹
5 条、合并文本安全 5 条、端到端 3 条）、`tools/test_ambiguity_gate.py`（已改成
PTC 真实形态）、`tools/test_clarify_v0.py::test_e2e_shadow_mode`（影子模式）。

> 目的：避免"自己想"漏维度。取材以一手材料为准（Cline 系统提示原文、Claude Code / Vercel AI SDK /

### A.1 四条主流路线，哲学完全不同

| 谁 | 什么时候问 | 判据在哪 | 代价 |
|---|---|---|---|
| Claude Code | 模型主动调 `AskUserQuestion` | 提示词 + 模型判断 | auto 模式下模型会**倾向不问** |
| Cline | 模型主动调 `ask_followup_question`，并自报 `requires_approval` | 提示词 + 模型判断 | 模型自评不可审计 |
| LangGraph / OpenAI / Vercel | 工具上标 `needsApproval`，**可以是函数**按参数判 | **代码/配置** | 只认参数，不懂任务意图 |
| Cursor / Windsurf | 产品哲学两极 | 产品默认值 | 见 A.4 |

**关键事实：上面没有一家在 harness 里做"这个实体是否存在"的判定。** 它们只有两类判据——
①模型自己说要问；②按工具参数匹配规则（`input.command.includes("rm -rf")`）。
本文设计的 `C1∧C2∧C3` 属于**第三类**：用证据状态反推信息缺口。这条路没人趟过，
好处是不赌模型自觉，代价是没有现成数据可参照（见 A.5 最后一条）。

### A.2 本规格漏掉的四个维度

**① 「影响面」是独立于「可逆性」的第二根轴**

Uvik 的四象限（影响 × 可逆）比本文的二元判定细一档：

| 做错了多糟 / 多难撤销 | 易撤销 | 难撤销 |
|---|---|---|
| 影响低（局部、常规） | 静默执行 + 日志 | 批量确认 |
| 影响高（大范围、外发） | 单次确认 | 逐条确认 + 二次确认 |

本文只有"可逆/不可逆"，缺"影响几个文件/几个人"。现实反例：Windsurf Cascade 在 monorepo
里 4 分钟改错 82 个文件、把 tsconfig 全局关掉 strict——每一步都"可逆"，合起来不可逆。

**② 「置信度」是第三个旋钮，不是布尔**

外部实践普遍用置信度阈值路由（低于阈值转人工）。本文明确写了"不做语义猜测"，
等于放弃这个旋钮。折中：不用模型自评分数当判据（不可解释），改用**可观测的代理**——
检索命中数、候选数、同参数重试次数、模型是否改过方案。这些都进得了日志。

**③ 缺第三种处置：「先做，留否决窗口」（human on the loop）**

本文只有 `ask / redirect / proceed`。对**可逆但影响面大**的动作，最优解是第三种：
先做，同时明确告知"我改了 N 个文件，这是备份/回滚方式"。比问省一次打断，比闷头做安全。
`proceed` 应再分两档：静默 proceed / proceed + 显式可撤销声明。

**④ 澄清与权限审批共用同一份「注意力配额」（最要紧的一条）**

外部实践的原话是「审批预算是共享池，滥用一处，透支全部」。**注意：本机是本地 agent，
这笔"预算"不是钱**（除电费外无按次计费），而是**打扰次数 + 等待时间**两样。

这仍然成立，而且对本地更贵：多问一轮 = 多一次完整的本地推理等待。它同时解释了用户为什么
关心"完全访问权限下还弹吗"——他关掉权限审批就是在省这份配额。如果澄清弹窗独立计费，
总支出没降，等于白关。**因此 `ask_budget` 必须与权限审批合并计量**，不能让两个计数器
各自为政。

### A.3 别人踩过的坑（都有数字）

| 系统 | 数字 | 含义 |
|---|---|---|
| Windows UAC | 89% 批准率；仅 13% 能解释为什么弹 | 弹多了就变成按回车 |
| Android 权限 | 17% 安装时看权限；<3% 既看又懂 | 提示语本身失效 |
| Chrome SSL 警告 | 70% 点穿，一半在 2 秒内 | 底率决定行为：99% 没问题 → 当作 100% 没问题 |
| 医疗警报 | 85–99% 无需干预；某儿童医院单日 5300 条、95% 误报 | 误报率高会死人 |
| Claude Code（Anthropic 内部） | 93% 用户批准所有请求 | 连最好的产品也逃不掉 |

两条由此得出的硬结论：
- Vercel 文档原话：*"A blanket true trains users to click approve without reading — the
  security value evaporates."* ⇒ **全量确认等于没有确认。**
- 误判成本不对称：把高风险误判成低风险是安全事故（5–8%），把低风险误判成高风险是
  打扰疲劳（3–5%）。所以**判据要往"少问"偏**，但不可逆动作那格不能偏。

### A.4 两极化反例：该问不问 / 问得太多

| | 表现 | 后果 |
|---|---|---|
| Windsurf Cascade | "act, don't ask"；遇 TypeScript 类型不匹配**不问**，直接改 tsconfig 全局关掉 `strict null checks`，然后进重试死循环 | 4 分钟改错 82 个文件，最后 `git reset --hard` |
| Cursor Composer | 倾向 surface 决策，"我要装 X，是吗？" | 安全，但熟练用户嫌烦 |

**这就是本文要的中间态**：不问的代价是毁工作区，乱问的代价是用户关掉弹窗。
判据存在的意义就是在这个夹缝里找位置。
