# 踩过的坑

> 只记**花了时间才想明白**的那种坑：症状看起来像 A，实际是 B，而且 B 往往在更上游。
> 每条固定三段：**症状 → 真因 → 以后怎么做**。按「先怀疑自己，再怀疑 harness，最后才怀疑模型」排序。
>
> 相关：[`eval-findings.md`](eval-findings.md)（每一跑的问题与修法）、
> [`contracts.md`](contracts.md)（哪些是硬约束）。

---

## 0. 评测脚本自身也会制造幻觉

**症状**：rerun58/59 的 `reply.txt` 里同一份答复连着出现三遍，第一份以「Marp（及其 CLI 工具 marp-cli）」
开头，后两份以「marp-cli」开头。我据此判定「模型生成退化」，还专门写了 `dedupe.py` 去修。

**真因**：模型没有连刷三遍。核对事件流：`assistant` 事件 **0 条**，而 `delta` 按 `step` 切开是
`[1203, 1179, 537]` 三段——正是**两次被打回的草稿 + 最后一次交付**。
`dispatch_task.py` 把所有轮次的 delta 累加进一个字符串，于是「三轮」看起来就是「三连刷」。

**以后怎么做**

- 下结论前，先把事件流按 `step` 切开看每一轮的长度，再看答复。
- 采集器只留**最后一轮**的 delta（`step` 事件上 `deltas.clear()`），并把它写进注释：
  「重写轮会把整段答案重发一遍，全轮次累加等于给自己造一个假故障」。
- 一条元规则：**评测脚本和被测系统一样需要证据**。它给的数字是证词，不是事实。
  这也是为什么 `.run/<tag>.meta.json` 里连「工具序列、是否声明未核实」都要落盘——
  复盘靠文件，不靠我上一轮的印象。

## 1. 闸门判了，但用户看不见（同一个坑踩了两次）

**症状**：rerun58 日志里明明打了两次回灌（history 里有两段「答复核查未通过」），
但事件流里 `grounding_gate` **0 条**，前端也一片安静。

**真因**：`loop.py` 老老实实 `yield {"type": "grounding_gate", ...}`，而 `webui.py` 的
`if/elif` 链里**没有这个分支**——事件被静默丢弃。rerun16 的同款事故（闸门判了、日志里有、
界面没有）当时也是这么来的。

**以后怎么做**

- 新增事件类型时，三处一起改：`loop.py`（发）、`webui.py`（前端分支）、
  `scripts/dispatch_task.py`（时间线识别）。少一处就等于没发。
- 事件的「可见」要能被测出来：现在 `tools/test_grounding_gate.py` 里有断言盯着
  「闸门开口时事件必须存在」。

## 2. 「它抓到了，是 harness 把它扔了」

**症状**：rerun61 最终答「该仓库只有一句描述，没有安装命令」。看起来是模型没找到/没看，
而事实是它**抓到了** marp-cli 的完整 README，包含 `npm install -g @marp-team/marp-cli`。

**真因**：抓到 README 的下一轮，上下文压缩把 63,703 字摘成 9,177 字，命令全被摘要吃掉。
模型看到的是「仓库简介」，它当然说「没有安装命令」——它没有说谎，是 harness 把依据扔了。
更糟的是闸门这时只能判「命令无据」，等于**判 harness 自己造成的损失**。

**以后怎么做**

- 压缩必须保护一手来源：`[实测 · 网页]/[实测 · API]` 抬头的消息留抬头 + 前段 + **全部命令行**；
  摘要块后面再补一份命令行清单。
- 压缩链要**世代继承**：摘要块本身也是消息，下一轮会再被摘要一遍。任务原文与命令行都要
  显式从上一代摘要里捞回来，否则「钉住」只活一轮。
- 判读口诀：先看 `tool_result`（拿到了什么），再看压缩记录（剩下的还是不是它拿到的），
  最后才看答复。

## 3. 子串匹配让错误答案蒙混过关

**症状**：答复写 `npm install -g @marp-team/marp`（这个包在 npm 上是 404），
而源里只有 `-marp-cli`，闸门却放行了。

**真因**：判据写的是 `n in src`。`@marp-team/marp` 是 `@marp-team/marp-cli` 的前缀子串，
于是「源里有没有」变成了「能不能当子串」。

**以后怎么做**

- 一切「某个 token 在不在源里」都改成**边界匹配**（`_bounded_in`：前后不能是
  `[A-Za-z0-9._-]`），前缀/后缀都不算命中。
- 命令的主体要用 `_cmd_subject` 取（跳过 `install/i/add` 这类包管理器子命令，取包名），
  否则 `npm install X` 只会核对到 `install`——那个词永远在源里。

## 4. 提词器挑中泛词，整轮检索白跑

**症状**：`web_search("markdown to pptx command line tool open source")` 被「自动收紧」成
`site:github.com "command"`，搜回来一堆叫 Command Code 的项目。

**真因**：`_key_word` 的优先级把「长度」排在最后之前，`presentation`(12 字符) 压过了
`Marp`(4 字符)；而全领域泛词（presentation/markdown/cli/components…）没有被排除。

**以后怎么做**

- 提词优先级：全大写缩写 > 首字母大写专有名词 > 非泛词 > 带数字 > **长度（最后）**。
- 全是泛词时**不要假装收紧**——如实说「这句话里没有可精确匹配的名字」，并给下一步
  （走 `github_search` / `npm_package_search` / `exact_repo_lookup`）。
- 相关性闸门兜底：结果与查询零词面交集就丢弃，并明说「不是没搜到，是搜回来的不是这个词」。

## 5. 白名单是幻觉的逃生通道

**症状**：错误包名、错误命令一度能过闸门，因为判据里有一句「纯通用动作就放过」。

**真因**：白名单本意是放过 `cd`、`ls` 这类无主命令，实际却把「主体核对失败」的情况
一律兜成通过——**兜底逻辑长在判据最下游，就等于给幻觉开了后门**。

**以后怎么做**

- 白名单只兜「纯通用动作」（`cd`、`mkdir`、`ls`），且必须**没有**包名/仓库名参数；
- 兜底要写在注释里说明「为什么这条不会放过具体包名」，并配一条反向测试
  （错包名必须被拦）。

## 6. 「0 次工具调用」曾被当成正常收工

**症状**：rerun57 里 19 次 `ops_batch` 全部 0 次调用，任务看起来在推进，实际一步没走。

**真因**：模型把整段脚本包进了 `"""..."""`——语法完全合法，运行时就是「一个字符串字面量」，
什么都不执行。零调用被当成「脚本跑完了」。

**以后怎么做**

- 零调用是**错误**，不是结果：明确回一句「本轮没有拿到任何数据」，并列出常见原因
  （三引号/围栏包裹、只有注释、未执行分支、工具名写错）。
- 顺手解包三引号再执行（`_unwrap_triple_quoted`）；YAML 行（`marp: true`）不算命令。

## 7. 「扫描到的」不等于「这个任务产出的」

**症状**：一次「克隆仓库」的任务跑完，清空弹窗里几十个文件被归成「中间文件」，
默认勾选——一键就把用户克隆进来的整个仓库删了。

**真因**：早期判据是「via=scan 即中间文件」。而扫描相减只能看出「这段时间它出现了」，
看不出源头；克隆、下载、解压都会整批以 scan 落进台账。

**以后怎么做**

- 中间文件只按**名字/路径模式**判（tmp/draft/cache/草稿 + `.log/.bak/.tmp` +
  `__pycache__/node_modules/.pyc` 这类依赖与解释器产物）；
- 真成果（README.md、src/、tests/）落到「最终产出」，默认**不**勾；
- 版本库（`.git`）任何情况下都不删，`_purge_files` 里有独立的一道闸。

## 8. 重启窗口期派发，撞的是瞬断

**症状**：改完代码写 `restart.flag`，紧接着派发任务，连接被拒（`Connection refused`）。

**真因**：看门狗消费 flag 需要几秒，旧实例已经退了、新实例还没监听。

**以后怎么做**

- 派发前**连续 3 次** `health=200`，中间隔 2–3 秒；只看到一次 200 不够。
- 重启本身要落日志（`.run/service.log`），失败时先看它，别猜。

## 9. 用裸解释器跑测试，缺依赖报 ModuleNotFoundError

**症状**：`python tools/test_xxx.py` 报 `No module named yaml`。

**真因**：`C:\Users\admin\.workbuddy\binaries\python\...` 是干净解释器，项目依赖装在 `.venv`。

**以后怎么做**：测试一律 `.venv/Scripts/python.exe`；派发脚本可以用干净解释器（它只用标准库）。

## 10. 诊断越界：闸门差点变成答案生成器

**症状**：第一版诊断写了「query 直接写 Marp」「候选里这几个像 `marp-team/marp-cli`」，
模型照抄就过了。

**真因**：想「让下一轮有方向」时，很容易滑到「替模型把答案想好」。而闸门的职责是**证伪**：
说清「这次为什么一定错」，不是「怎样才对」。

**以后怎么做**

- 诊断固定三段：**犯了什么错**（mistake）/ **确定性依据**（哪个 token 在源里找不到）/
  **下一步往哪走**（方向，不给值）。
- 测试里钉死一条反向断言：诊断文本**不得**包含正确答案（包名、仓库全名、命令）。

## 附：一条判据优先级的经验

同一个现象，先问「能不能用程序判」：能 → 写在 A 层（确定性判据）；不能 → 才写进提示词。
反过来（先写提示词，再补程序）通常意味着提示词里已经长了一堆补丁，模型开始互相冲突地遵守。
