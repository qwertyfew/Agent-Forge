# First-Party Source（结论必须来自一手来源）

「拿没查过的东西当查过的写出来」有两种表现，**判据是同一条**：

| | 转述（不可引用） | 一手来源（可引用） |
|---|---|---|
| **外部事实** | 搜索引擎摘要、第三方博客、聚合站点 | 官方站点页面、官方文档、官方 API 字段 |
| **本机事实** | 记忆、印象、同类项目的惯例 | 工作区本身——`list_dir` 看目录、`read_file` 看内容 |

真实事故两起：

- **外部**（REA 检索实测）：任务要求查 GitHub 上的项目 REA，agent 只调了一次 `web_search`，
  就把摘要里的「Star 数已达 **1w+**」写进结论——GitHub API 实测是 **17 万**，差一个数量级；
  「最近更新」写成「**2026 年 7 月**」，实际是**当天**。定性描述大致没错，**定量与时效全错**。
- **本机**（端到端实测）：任务要求「列出工作区根目录下的文件」，25 秒、**0 次工具调用**，
  答复里凭空列着 `agent-forge.json` / `core/` / `ui/` / `venv/`——这些在工作区里**都不存在**。

两次工具都没坏。坏在**来源性质**：「转述」和「实测」在它眼里没有区别。

## 一、一条判据

> **这句话，是我自己从一手来源读到的，还是别人转述 / 我自己想出来的？**

**实测**可以直接引用；**转述**只能用来找入口。结论里两者不得混用；只有转述可写时
必须写明「未经核实」——含糊其辞比写错更糟。

工具输出已经替你标好了来源性质，照标签走就不会错：

| 输出头 | 意思 | 能不能引用 |
|---|---|---|
| `[搜索摘要 · 转述 · 未核实]` | `web_search` 的摘要 | 只能找入口 |
| `[实测 · 网页]` | `fetch_url` 抓到的正文 | 可以 |
| `[实测 · API]` | `fetch_json` 抓到的官方接口字段 | 可以 |
| （无标签的本地工具结果） | `list_dir` / `read_file` / `find_files` 等读到的现场 | 可以 |

## 二、动手顺序（三步，别省第二步）

1. **搜**：`web_search` 找到候选 URL。**目标是某个具体项目 / 库 / 产品时，优先挑官方域名**
   （官网、`github.com/...`、官方文档），而不是第三方博客——技术博客里的数字往往过期，
   而且经常互相抄。
2. **抓**：`fetch_json`（接口）或 `fetch_url`（网页）**至少抓一个一手来源**。这一步不能跳：
   搜到 URL 不等于核实过。抓 JSON 接口通常比抓网页更省事，字段是干净的。
3. **写**：数字与日期从抓回来的内容里取。抓不到就如实说「未能核实」，**不要退回引用搜索摘要**。

**本机事实只有两步，但第二步同样不能省**：先 `list_dir` / `find_files` / `read_file`
看一眼现场，再写结论。**「先列出来」这类要求，问的就是现场，不是让你回忆。**
任务里没提过的文件名 / 目录名，一个字都不许出现在结论里。

## 三、常用官方 API 地图（`fetch_json` 一次调用就够）

| 想查什么 | 打哪里 | 取哪些字段（`keys`） |
|---|---|---|
| GitHub 仓库 | `https://api.github.com/repos/<owner>/<repo>` | `full_name,stargazers_count,forks_count,open_issues_count,pushed_at,updated_at,language,license.spdx_id,topics` |
| 最新 Release | `https://api.github.com/repos/<owner>/<repo>/releases/latest` | `tag_name,published_at,name` |
| 贡献者数 | `https://api.github.com/repos/<owner>/<repo>/contributors?per_page=1` | （看 `Link` 头的 last 页号，或直接读数组长度） |
| npm 包 | `https://registry.npmjs.org/<pkg>` | `dist-tags.latest`、`time.<版本>` |
| PyPI 包 | `https://pypi.org/pypi/<pkg>/json` | `info.version,info.summary,info.author` |
| 其他 | 官方文档里写的 API / 数据端点 | 按其字段名取 |

**时效性认 `pushed_at` / `updated_at`，不认搜索摘要里的日期。** 日期格式是 ISO（`2026-10-13T05:58:58Z`），
引用时换算成「年月日」即可。

## 四、两个容易踩的点

1. **本地跑通 ≠ 在线也对**。本地 Ollama 走 ndjson、在线 provider 走 SSE，抓取路径也不同；
   一次搜索成功不代表下一次抓取成功。抓取失败要如实报，别默默改用摘要。
2. **别把「搜到的第一个结果」当官方**。`github.com/<别人>/<同名仓库>`、镜像站、fork、
   内容农场都排在前面过。看域名、看 owner，对不对得上再抓。

## 五、系统会核查（两道，都是硬约束）

这不是「希望你能做到」，是**系统会替读者核一遍**（`agentforge/sources.py`，与收尾验证闸门
同一思路：模型只有解读权，没有裁定权）：

1. **外部事实**：只用过搜索、没抓过任何一手来源，而总结里又出现数字 / 版本 / 日期时，
   答复末尾会被追加一段「转述 · 未经核实」声明。
2. **本机事实**：任务要的就是工作区现状（列目录 / 有哪些文件 / 看现状），却全程一次读取类
   工具都没调，而答复里列着具体文件名 / 目录名时——**先给你一轮修正机会**去真看一眼；
   仍然没看，答复末尾会被追加「未经核实」声明，并在界面上标出是哪几项。

看到这两种声明，说明这一步漏了。下一次同类任务，先去看 / 先去抓，再写结论。
**「技能加载了」不等于「规矩生效了」——真正兜底的是这道系统侧核查。**
