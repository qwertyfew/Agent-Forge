# Self-Verification（自证与沉淀纪律）

改的是**自己的子系统**（记忆、技能注册、编排调度、工具层）时，「跑起来没报错」什么也证明不了。
本 skill 管两件事：改完怎么自证，收尾怎么沉淀才不污染自己。

## 一、自证的三条硬要求

1. **脚本必须可移植——禁止写死本机绝对路径。**
   用 `Path(__file__).resolve().parent.parent` 定位仓库根，或读配置项。
   写死 `D:\...\somewhere` 的那一刻，这个脚本就只在那台机器上成立；换机器是一堆
   `FileNotFoundError`，而「在我这儿是过的」会让下一个读它的人误以为结论仍然有效。
   一次性评测脚本尤其容易死在这儿。
2. **回放真实脏数据，不要构造 happy path。**
   会出错的从来不是理想输入，而是历史里那条已经写错的记忆、那段混了本次任务文件名的方法论。
   拿真正出过问题的输入回放，断言才对得上现实。
3. **契约先行：先写「必须成立的断言」，再动代码。**
   断言写的是**不变量**——「任务书句式绝不进长期记忆」「`WHEN_NOT` 命中时必须让位」
   「不存在的符号必须给出无引用结论」。若照着当前实现反推断言，改完代码顺手把断言也改成现状，
   验证就纯属摆设。

## 二、验证脚本摆哪儿

本项目按**寿命**分两处，别混（判据是「这条断言三个月后还要不要跑」）：

| 位置 | 寿命 | 用途 |
|---|---|---|
| `tools/verify_*.py` | 一次性 | 只为某一批改动写的批次验证；跑完留证即可，时过境迁可退休 |
| `tools/test_*.py` | 常驻 | 跨批次的回归；以后每次动这些子系统都该重跑 |

退休一份 `verify_*` 之前，先确认它守的**契约**已经落进 README「能力的契约」一节——
断言可以退，规矩不能丢。

## 三、沉淀时的防污染三条

自动沉淀最容易犯的错是把「这次怎么做」当成「以后都这样」：

1. **任务书句式不进长期记忆**——「必须先用 read_file 读完」「产出：写入 docs/x.md」是*这一单的指令*；
   凡「任务：/步骤：/验收」结构一律过滤。例外：用户明说「记住…」「以后…」的强信号照收。
2. **本任务的结论不进长期记忆**——带本机绝对路径的、提「本次任务/本次产出」的都是一次性的。
3. **事实与项目约定也不进记忆**——记忆里**只放用户偏好**。事实（路径 / 端口 / 版本）有工具能现查，
   约定（工作方式 / 流程规则）由程序与常驻断言保证；这两类写进记忆只是「劝」，模型不照做就不发生。
   判据是「**删掉这条记忆，测试会不会红**」——会红，说明它本来就该待在架构里。分层（L1/L2/L3）
   已经取消，别再给记忆打层标签。
4. **讲方法论的 skill 不得混入本次任务的专有内容**——正文里出现本次任务的文件名或绝对路径，整条作废。

## 四、端到端怎么「看得见」

不要靠猜模型为什么这么答。`POST /api/chat` 返回的是 **SSE 事件流**，把 `route`（这轮交给谁）、
`dispatch`（拆成几个子任务）、`assign`（各派给谁）、`conflict`（谁和谁要写同一个文件）、
`task_done`、`stats`（tokens/tps/花费）依次读完，编排的每一步都有据可查。
事件全表与两个实操要点（`POST /api/models {"action":"auto_config"}` 切路由、评测另起端口
别碰常驻的 8787）见 README「能力的契约：可观测、可验证、不自我污染」。
