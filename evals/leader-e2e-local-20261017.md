## 端到端抓出并已修复的 bug（单元测试抓不到的那种）

1. **`run_leader` 缺 `read_cache` 参数**（`UnboundLocalError`，0.1s 即崩）——旧 `run_multi_agent` 有此参数，重构时丢失；修复：补参数 + `run_task` 提前创建共享缓存传入。
2. **`"dispatcher": dispatcher.name` 漏括号**（dispatch 事件负载带方法对象 → JSON 序列化崩）——修复为 `dispatcher.name()`。
3. **环境隐患**：多次重启堆出多个监听 8787 的服务实例，请求被旧代码进程接管，造成「修了没生效」的假象。排查手段：对比进程启动时间与代码 mtime。教训：重启服务后必须核实监听进程唯一。
4. 顺带：webui 异常处理补 `traceback.print_exc`（此前只透出 `str(e)`，排障定位不到行号）。

## 架构级改进建议（按影响排序，未动手）

1. **给员工内环加完成契约**：小步骤提示词强制要求「最后一步必须 write_file 产出结果文件」或提供 `submit` 收尾工具——消灭「读到步数上限」这种最贵的失败方式（本次 5 步 × ~10 分钟全部死于此）。
2. **步骤级步数上限独立于全局 100**：员工单步建议 25-30 步；撞限即快速失败，把决策权交回 Leader（它已证明会换招）。
3. **失败重试去重**：Leader 对「同类步骤连续失败」应换策略（拆更小/换维度/降范围），而不是重发几乎相同的批次——R2→R5 有 3 批高度相似，浪费 ~30 分钟。
4. **`leader_round` 事件透传**：webui 补分支，让滚动规划在界面上可见（前端胶囊已就绪）。
5. **台账 summary 提取修正**：本任务 summary 落了一条原始工具结果 JSON 而非助手结论（回看页会显示一段 JSON 串）。

## 结论

**七步架构的骨架经实测成立**：闭环滚动规划、按能力指派、子任务隔离、失败不拖垮批次、并行/串行闸门、停止路径全部按设计工作，且 Leader 表现出设计预期的「看结果、改批次」行为。当前最大的合理性缺口不在七步骨架，而在**员工内环的步粒度失控**（无完成契约 + 上限太宽）与**失败重试的收敛策略**——两者都属于可配置/可加约束的修补，不动架构。
