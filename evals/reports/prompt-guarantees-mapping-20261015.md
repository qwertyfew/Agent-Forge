## 〇、先把「提示词」在这个 harness 里的三种角色分清

映射前必须区分——不是所有写在代码里的文本都是"保证"：

| 角色 | 含义 | 该不该信任 |
|---|---|---|
| **软保证** | 靠模型自觉遵守的纪律（"必须查证""禁止编造"） | 不可信。本地小模型会飘，正是本轮审计对象 |
| **架构的执行器** | 架构已做出裁决，提示词只是把裁决结果送达模型的通道（闸门修正轮、诚实守卫逼供） | 可信。决定权在代码，模型只有"照办或再被拦" |
| **信息注入** | 环境事实 / 记忆 / 任务笔记 / 工具索引，是数据不是要求 | 与信任无关，缺了它模型只能猜 |

**闸门修正轮的四个 PROMPT（`verify.py` 的 `CORRECTIVE_PROMPT` / `ARTIFACT_CORRECTIVE_PROMPT` /
`UNFINISHED_CORRECTIVE_PROMPT`、`sources.py` 的两个、`honesty_guard.FORCE_CONFESS_PROMPT`）
全部属于第二类**——它们看似是提示词，实为架构裁决后的"补救指令"，不在审计范围内，且必须保留。

## 一、七步流程的代码落点与各步的提示词 / 架构清单

**① 意图识别 → ② 任务拆分 → ③ 任务分配 → ④ 任务执行 → ⑤ 输出汇总 → ⑥ 闸门核验 → ⑦ 输出**

| 步 | 代码落点 | 该步的提示词 | 该步的架构层 |
|---|---|---|---|
| ① 意图识别 | `dispatcher._worth_dispatch` + 简单对话判定 | 无专门提示词（SYSTEM_TEMPLATE 兜住单任务对话） | 确定性规则：`_TOOL_HINTS` 信号表、`SIMPLE_CHAT_HARD_CHARS`（只否决"太长"）、`NOT_SIMPLE_KINDS` |
| ② 任务拆分 | `dispatcher.DISPATCH_SYSTEM` | 拆解原则全文（语义独立 / 宁可少拆 / **绝不缩小范围** / 依赖判定 / 验证命令原样保留） | JSON 强 schema 输出；`MODEL_CHOICE_GAP` 防自派；**拆分质量本身无架构校验** |
| ③ 任务分配 | `DISPATCH_SYSTEM` 的 model 字段 + `scores.py` | "只在明显更合适时才填 model；不要都派给自己" | 能力分自动挑选 + `MODEL_CHOICE_GAP=8` 否决退化指派；`needs_chinese` → 翻译桥接（`BRIDGE_NOTE`，架构触发） |
| ④ 任务执行 | `loop.py` SYSTEM_TEMPLATE（工作方式 8 步 + 输出要求 + 安全约束） | 见 §2 主表 | 权限 Guard 硬拦截、未注册工具确定性报错、写盘后即时验证、`FAIL_NOTE` 程序化注入、任务笔记跨压缩持久、修正轮 |
| ⑤ 输出汇总 | `dispatcher.SYNTH_SYSTEM` | 5 条整合规则（含本轮新增【读产出文件】【对上文件名】） | **方案 B 已落地**：artifacts（文件名+内容）随 summary 一起喂给协调者——信息契约已架构化 |
| ⑥ 闸门核验 | `orchestrator._verify_gate`（六道） | （修正轮 PROMPT，属架构执行器） | ①验证命令分支亲跑 ②产物核查 missing/stale/ghost ③未完成自弃 ④外部事实一手来源 ⑤本机事实来源 ⑥通用诚实守卫（honesty_gate） |
| ⑦ 输出 | 最终答复 + 闸门 notes 拼接 | SYSTEM_TEMPLATE「输出要求」大半条目、`LANG_REMINDER` | `LANG_REMINDER` 程序化贴消息末尾；闸门权威声明不可被模型推翻；artifacts 事件 → 前端文件卡片（汇总↔文件对齐） |

## 三、直接回答你的两个问题

### Q1：这些提示词起了什么作用？

- **②③的调度提示词**决定"活怎么拆、给谁干"——拆错的范围缩水是唯一会产生错误交付的条款，其余拆错只是费钱。
- **④的执行纪律**是给小模型的操作守则——其中真正"错不得"的（复制走命令、缺能力坦白、现状须查证）逐条核下来，前两者已有或刚有架构兜底，只有"现状须查证"仍半裸。
- **⑦的输出要求**是给最终答复的诚实/风格守则——诚实条款要么已被闸门覆盖（外部事实、未完成坦白、缺能力坦白），要么是你拍板移出闸门职责的（假装已验证），风格条款无需兜底。
- **⑤的汇总规则**决定答案是否完整送达——方案 B 落地后信息源问题已解决，剩"写了没"的措辞风险。

### Q2：有无架构替代它们做兜底？

**已完全兜住（提示词可删可留，共 6 条）**：中文回复（LANG_REMINDER 双保险）、外部事实一手来源（sources_gate）、复制备份走命令（三重验证）、禁删工作区外（权限 Guard）、缺能力/未达成坦白（本轮 honesty_guard 接管，原 preflight 的职责已架构化）、文件产物中文（翻译桥接 BRIDGE_NOTE，架构触发）。

**属架构执行器、必须保留（7 个修正轮 PROMPT）**：闸门四类 + 本机事实 + 诚实守卫逼供——它们不是保证，是裁决的送达通道。

**仍无兜底、需要你决策的（3 条 B 候选）**：
1. **② goal 保真**（调度器不得缩小任务范围）——拆错即交付错，全链路唯一在这步产生错误而非浪费的条款；
2. **④⑦ 项目现状须查证**——local_facts_gate 只覆盖"列文件却零读取"窄场景，一般"答代码事实"仍靠自觉；
3. **⑤ 关键结果必须进答复**——方案 B 保证了信息在场，但没保证模型写出来；w3 类 norm 失败的残余风险全在这条。

**已拍板的取舍（不算缺口）**：⑦"没验证说未验证"——你已决定闸门不查过程；harness 层零兜底是设计结果，判定退到评测层。

## 四、三条 B 候选的收口（2026-10-15 第二轮，已落地）

三条均已实现为「程序比对 + 一轮修正」的现有模式，无过程检查，与「闸门判产物」原则兼容：

1. **② goal 保真**（`config.goal_fidelity_gate`，实现在 `dispatcher.py`）：拆分后程序比对——
   原文点名的交付物（文件名 / 路径 / 引号内容，`deliverable_tokens`）是否都出现在某个
   goal 里（`missing_deliverables`）；缺了先点名重拆一次（两版取缺得少的），仍缺则把
   交付物程序化补进最相关任务的 goal（`【系统侧范围保全】`声明，同 `_augment_copy_checks`
   既有模式）并记台账 `gaps.record("goal_fidelity", …)`。规则拆解路径同样过检（无 LLM
   可重拆，直接补写）。
2. **④⑦ 项目现状须查证**（复用 `config.local_facts_gate`，实现在 `sources.py`）：
   `needs_local_note` 从窄场景扩成两路——窄场景（任务书问现状）不变；新增一般场景：
   项目/代码类任务书（`_PROJECT_WORK_RX`）+ 全程零读取 + 总结断言工作区现状
   （≥2 项，或单项 + 存在性断言 `_ASSERT_RX`）→ 同样出手。`produced` 参数排除本轮
   程序确认的产出文件；`_DESIGN_RX` 排除「设计/规划」类任务书（交付物本身就是清单，
   枚举的名字是方案不是现状陈述）。命中走既有修正轮 + 声明拼接。
3. **⑤ 关键结果必须进答复**（`config.facts_gate`，实现在 `verify.py` 新增第七道核查）：
   `required_fact_tokens` 从任务书的要求句（保留/写明/确保/包含…）提取硬 token
   （引号内容 / 时间 / 日期 / 数字），`missing_required_facts` 归一比对最终答复
   （NFKC 全半角统一、千分位等价、中文数字不猜）；缺了给一轮修正
   （`FACTS_CORRECTIVE_PROMPT`），仍缺附 `missing_facts_block` 声明并播报
   `missing_facts` 事件。三处防误报：验证行整行排除；时间/日期/引号先取后掩码
   （防「14:00」拆出 14/00）；路径段与反引号代码先掩码（防 `reports/2026` 里的
   2026 被当事实）。

**顺带修复的两处遗留问题**：
- `honesty_guard._FILE_INTENT_RE` 收紧——旧正则把「列出工作区的文件（不要读内**内**容）」
  和答复里的文件清单（agent-forge.json / start.bat…）都误判成「要产出文件」，触发
  假逼供；改为生产动词锚定的扩展名 / 动词+文件 / 交付物名词+写入动词三类信号。
  同时 `assess()` 在 `files` 为空时不再判「文件没写出来」（文件存在性归产物核查管）。
- `test_verify_gate.py` 两处断言还在锁已删除的旧行为（C 谎报「未经系统确认」注脚、
  R18 同类），改为锁定新契约（闸门不做过程检查）；`StubAgent` 的修正提示断言放宽为
  「系统侧」前缀。

**测试**：新增 `tools/test_keyfacts.py`（关键事实，19 项）、`tools/test_goal_fidelity.py`
（goal 保真，23 项）；`test_local_facts.py` 增一般场景 8 项；全套 11 个测试文件通过。

## 五、若要继续收口（历史备查，三条 B 候选已按 §四 落地）

1. **goal 保真**：拆分完成后程序比对——用户原文里的交付物名词（文件名、路径、"写入/回复里给出"）是否都出现在某个 goal 里；缺了 → 拒收该次拆分、重试一次。判定纯词面比对，无模型参与，符合"调用即证据"。
2. **现状查证扩展**：`local_facts_gate` 的命中规则从"列文件类请求"扩展为"回复断言了工作区文件/代码事实，而轨迹无对应 read/list/search"（复用轨迹扫描，与 honesty_guard 同源）。
3. **关键结果回显**：任务书含"保留 X / 答案是 Y / 必须包含 Z"字样时，汇总后程序检查回复是否含 X/Y/Z（字面/数字比对，复用评测 expect 的 contains_norm 逻辑）；缺失 → 追加一轮修正。这条同时把 c3/c4 的"数字无来源"问题顺带收进（数字必须能在文件或命令输出中找到）。

三条都是"程序比对 + 一轮修正"的现有模式，不引入新的过程检查，与"闸门判产物"原则兼容。
