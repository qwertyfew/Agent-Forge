## 一、rerun10：守卫修复上线，但调度链路复发 → 按计划转入定因

守卫修复（61a5881：带行号圆括号引用 + 全角括号）随服务重启生效。但 rerun10 的
r1 评估就解析失败——比 rerun9（r4 才坏）更早。果断停止，执行既定计划：
给 `_chat` 补失败观测（done_reason 落盘）再复现。

### 诊断过程的三块拼图

1. **失败样本落盘基建**（LLMResult 补 `done_reason`；`_chat` 失败样本写
   `.run/dispatcher_failures/`）。首版落盘全 0 字节——模型名 `gpt-oss:20b`
   里的冒号在 Windows 被当 ADS 备用数据流，内容全写进了流里。消毒后拿到关键数据：
   `done_reason=length, eval_count=2046, content_len=0`。
2. **排除法**：np=8192/16384 都在 2046 截断（看似钳制）；但中等提示词
   np=3000 能跑到 2539 自然收尾——不是钳制。同一长提示词流式重发又成功——是随机的。
3. **定因**：Ollama 对 gpt-oss harmony 的 **analysis（思考）段有 ~2048 token
   隐形预算**。上下文越长思考越容易跑飞，撞墙后 final 通道永不输出
   （content 空、reasoning 字段也空、done_reason=length）。
   这完整解释了三轮实验的共同现象：「短上下文全好、长上下文必坏、
   num_predict 加到多大都没用」。

### 修复（commit 611734d）

- 系统提示追加 gpt-oss 官方档位 **`Reasoning: low`**：分析收敛。同一失败
  提示词连测 4/4 全 stop，耗时 26-47s → 4-11s（调度 JSON 不需要深推理）。
  对 gemma 无效无害。
- `_chat` 加 **validator 参数**：输出非 JSON 视同失败当场重试（原只对空响应
  重试），重试 2→3 次。Reasoning: low 下仍偶发超短非 JSON 回答（实测 38 字符）。
- orchestrator 三处调用点删 `num_predict=2048/4096/1024` 覆盖——它们会压掉
  8192 默认值，等于把预算又压回 rerun8 时代的水平。

## 二、rerun11：全链路健康度显著改善

- **调度成功率**：r1-r6 大部分规划/评估一次通过；2 次规划截断走兜底后，
  下一轮自愈（评估照常成功、重新规划出补查步骤）。全程 9 份失败样本落盘
  （7 空 + 2 截断），validator 重试救回大多数。
- **评估环有牙齿**：r1「判定未完成：继续」→ r2 具体指出「差距清单文件未确认
  存在」→ r3 规划专项补查。不再是无意义重试。
- **语义验收严格且诚实**：两次重试打回均给出具体缺口（四列格式 / 文件路径+行号
  证据 / 对比点覆盖度）；重试上限用尽后**如实附上未通过原因**而非谎报完成。
  这是诚实纪律的正确表现——语义验收判的是「答复是否自含证据」，本次答复
  只引用了文件没贴内容，被判未通过属正确行为，交付物本身可人工复核。
- **残余问题**：gpt-oss 在 Reasoning: low 下偶发仍深度思考（2 次截断样本
  thinking 1.2 万字符）——模型自认任务复杂时不完全服从档位。兜底机制能
  接住，暂不需进一步动作；若后续频率上升，可探测 Ollama 原生 think 档位
  （`think: "low"` 字符串参数）。
