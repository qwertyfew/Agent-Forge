## 3. 逐条判读

### 3.1 f5：被判「全程没调用工具」，其实调了

rerun64 的失败理由是 `应调用指定工具之一（github_search），实际用过：ops_batch`。
翻过程记录，脚本是：

```python
from tools import github_search
results = github_search(query="REA")
print(results)
```

工具层自己印的小结也写着 `[ops_batch] 1 次工具调用（github_search×1）`。**真调了**，
只是评测的解析器只认 `call("x")` / `tools.call("x")` 两种写法，漏了 `from tools import x`。
这是 **L6（评测层）**：把架构改动记成了模型退化。修完复跑（rerun65）即 pass。

> 顺带一条判据问题：f5 的期望只有「回复含 REA + 调过检索」。pass 的这次答复其实在
> 反问「您指哪一类 REA」，并列了三个疑似臆造的分类名。**判据太松，这条用例目前
> 测不出「检索结果是否被正确解读」。**

### 3.2 c6：工具参数残缺 → 无视报错 → 宣称完成

rerun64 的过程是：第 1 轮 `read_file` 读到原文；第 2 轮 `edit_file` **少了 `new_text`**，
工具回了明确的参数说明；同一轮又跑了 `python test_pricing.py`（原文件本来就能过），
于是 harness 在工具回执里写下：

```
【系统核对·写盘结果】
  - edit_file → pricing.py: 写入失败
  - run_command → (未给 path): 已写入磁盘
  ⚠ 存在写盘失败。脚本里任何「已写入 / 成功」都只是你自己的 print
```

模型没理会，直接答「已完成重构」，收尾闸门又跑了一遍同一个测试（仍通过），在答复末尾
附上「**系统侧验证 … 通过 … 以本结果为准**」。**文件一个字没改，答复却拿到了程序的背书。**

这里有两件事要分开：

- **模型行为**（L5）：明确的工具报错 + 明确的「写盘失败」提示，仍然宣称完成。
- **闸门口径**（L4）：「自验命令通过」只证明那条命令能跑通，不证明任务要求的改动发生了；
  把它写成「以本结果为准」，等于替一个假声明盖章。

rerun65 改用 `src/pricing.py`（带目录层）之后，任务书被识别出交付物契约，停止拦截在
第 2 轮把这句「完成」拦下，第 3 轮才真写盘 → 通过。**同一个模型、同一个任务，差别只在
「任务书有没有把交付物说成可核对的路径」。**

### 3.3 w5：只把内容贴在回复里，文件没写

rerun64 只做了 1 次 `read_file`，答复把整份提纲贴在聊天里，`outline.md` 不存在。
原因是任务书写的是裸文件名，而**交付物契约刻意不认裸文件名**（`tasksession` 里
「裸文件名歧义大，不纳入」是既有设计），于是停止拦截与未交付硬闸都没启用。

rerun65 改成 `reports/outline.md`，并在任务书里点明「文件没写出来就算没做」：
模型写盘、回读、再改一次，5 步通过。

rerun65 的答复同时暴露了两条**误伤/口径问题**（见 §4.2、§5.1）。

### 3.4 q1 / h4：两条都按预期

- `q1`：1 步、**零工具调用**、直接作答。纯问答不该动手这件事，目前是稳的。
- `h4`：第 1 轮模型在脚本里直接 `import requests` 裸抓（工具层报「0 次工具调用，本轮
  没有拿到任何数据」），第 2 轮改走 `fetch_json` 得到 404，随后如实回答「该仓库不存在」。
  **工具面的约束把「自己想办法」拉回了正轨**，这条路径值得保留。

## 4. 这轮真正修掉的东西

### 4.1 L6：评测层解析（`agentforge/tooltrace.py` 新增）

PTC 常驻后，顶层只有一个 `ops_batch`，真实工具名藏在脚本里。解析必须认四种写法
（`call("x")`、`tools.call("x")`、`from tools import x`、`import tools; tools.x(...)`），
并且**优先读工具层执行后印的小结**（`[ops_batch] 2 次工具调用（a×1、b×2）`）——
那是执行后统计的，比读源码可靠（脚本可能整段被包进三引号，语法合法但零执行）。

- `tools/bench_tasks.py`：内层调用解析改走 `tooltrace`，`rec["tools"]` 直接给出这条任务
  真实用过的工具；新增 `gates` 计数（§6.3 的误伤监控口径）。
- `tools/test_eval_evidence.py`（15 项）：四种写法、小结优先、0 次调用不猜、旧记录补算，
  并用 rerun64 的真实记录做回归。

### 4.2 L4：「按工具名判定证据」的闸门，在 PTC 下一半乱报、一半不报

`sources.tool_names` 只遍历顶层 `tool_calls`，于是：

| 闸门 | 后果（rerun65 实测） |
|---|---|
| `ran_local_inspection`（本地事实） | w5 读了 3 次文件（`read_file`/`list_dir`），仍被判「整个任务没有调用过任何读取工作区的工具」，给一份已经写进 `reports/outline.md` 的答复盖了「未经核实」——**误伤** |
| `ran_search`（外部事实） | 恒为假 → `needs_external_note` 的前置条件永不成立，外部事实核查**整条静默失效**（f5 那种没核实的 star 数字没人管） |

修法：`sources.tool_names` 与 `verify._tool_names` 统一委托 `tooltrace.tool_names`，
产品侧与评测侧从此同一口径。`tools/test_tooltrace.py`（11 项）钉住两侧行为，含反向断言
（真没读的时候仍要标、抓过一手源后不再标）。

rerun66 复跑 w5：答复里不再出现「未经核实」，关键内容也进了答复——**误伤消失**。

## 5. 留下来待定的两件事

### 5.1 「关键内容回显」只看答复，不看产物文件

w5 的答复（rerun65）末尾有：

> 【系统侧核查】任务书明确要求保留 / 给出下列关键内容，系统在最终答复里未能核对到它们
> （已给过一轮修正机会）：- ## 结论 - ## 待办 - ## 风险

文件里三个标题一个不少，只是答复没复述。这条闸门的本意是「关键事实也要进答复」
（治 w3 的「文件写对了、回复把事实丢了」），对写盘类任务就成了口径错位。

**建议**（未改）：判定时把已确认写出/更新过的产物内容一起纳入比对，命中即不再声明；
或至少把措辞从「未能核对到」改成「答复里没复述（文件里已确认存在）」。

### 5.2 f5 的判据太松

「回复含 REA + 过程里调过检索」放过了「反问用户 + 列三个疑似臆造分类」的答复。
建议补一条 `must_not`（排除「请问您是指」这类反问）或要求命中检索结果里的真实仓库名。

**rerun67 的补充证据（比原判断更准）**：同一条用例、同一判据，这次答复里的四个仓库名
**全部能在工具输出里逐条对上**（`morluto/rea`、`im95able/Rea`、`mytechnotalent/rea`
来自「名字同名」榜，`Panniantong/Agent-Reach` 来自 star 榜第 5），末尾那句
「请问您是指其中哪一个」在 `REA` 这个歧义查询下**是合理的澄清**，不是逃避。

所以真正的问题不是「判据该不该禁反问」，而是：**同一个 `pass` 既可能是 rerun65 那种
臆造名，也可能是 rerun67 这种逐条有据——判据分不出这两者，这个 pass 就没有信息量。**
建议改成**可证伪的比对**：把答复里所有 `owner/name` 形态的仓库名抽出来，逐个要求
在该任务的 `tool_result` 里出现过（`grounding` 的引用抽取已有这套逻辑，直接复用）。
这样 rerun65 会被判红、rerun67 仍绿，判定从「搜过没有」升级到「说出来的名字是不是搜来的」。

## 6. 归层小结

| 现象 | 层 | 处理 |
|---|---|---|
| f5 被判没用工具 | L6 评测 | 已修（`tooltrace` + 解析优先级 + 测试） |
| 本地事实误伤 / 外部事实不报 | L4 闸门 | 已修（同一 `tooltrace`），rerun66 验证 |
| `edit_file` 少参数后宣称完成 | L3+L5 | 模型侧；契约在位时由停止拦截兜住（c6 rerun65） |
| 自验通过 ≠ 任务完成 | L4 口径 | 待定：写盘失败与「已完成」的冲突要不要显式声明 |
| 只答不写（裸文件名） | 设计边界 | 交付物契约刻意不认裸文件名；评测用例改带目录路径 |

**一句话**：这轮 2/5 → 3/3 的变化，几乎不是模型变强，而是**度量变准**（f5）和
**任务书把交付物说清楚了**（c6/w5）。这也正是 §6 要扩任务集的意义——旧任务集既
测不到「只答不写」，也掩盖了「PTC 之后闸门读不到工具」这件事。
