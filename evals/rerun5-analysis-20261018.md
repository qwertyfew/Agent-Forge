- 所以：step52 的回归点（闸门误判）已稳住；但这轮没走到「交付物落盘→闸门验收通过→

## 1. 后台执行 / 不消耗 token（不改，仅说明实现方式）

- 后台任务是 **Bash 工具的 `run_in_background` 派生出的 OS 子进程**，脱离对话回合独立存活。
- 「不消耗 token」指**对话侧 LLM 推理 token**：后台进程跑的是 harness 脚本，它调的是
  **本机 Ollama 模型**（gpt-oss:20b / gemma4:12b）→ 本地 GPU 推理，**没有按量计费的
  API token**；且对话回合在我给出上一条回复时已经结束，后台运行期间**没有新的对话 LLM
  调用**。所以后台工作与对话 token 账单解耦。
- 注意两层「分解」别混：① AgentForge harness 内部的 leader/员工分解（rerun5 跑的就是它）；
  ② 我（外层 agent）自己的任务拆解。后台执行是运行时能力，与 harness 内部逻辑无关。

  是员工模型连续 3 轮既无工具调用也无正文时的兜底报错。leader 规划走的是 `plan`/`assign`/
  `leader_round` 事件，根本不经过这段。
- rerun5 共 8 条 `subtask_error`：
  - 7 条是 `模型调用失败：500 Server Error ... localhost:11434` —— Ollama（员工模型
    gpt-oss:20b）返回 500，属**员工/基础设施层**崩溃。
  - 仅 1 条（l4，587s）是「连续 3 轮没有输出」，也是员工模型空输出。

## 3. 处理流程是否合理 + 术语对齐（先整理，待确认再改）

你的流程（一句话 → 分解成任务 → 对每个任务 leader 规划「小步骤」→ 员工执行并返回 →
leader 重规划小步骤或生成收尾「预回复」→ 闸门核验 → 产出「正式回复」）**结构合理**，
与 harness 实际的 leader 双环架构基本一致，按此流程走没问题。

但有两处需要和你对齐（以下「现状」是代码/UI 实际出现的文案）：

| 你的术语 | harness 现状 | 不一致点 | 建议 |
|---|---|---|---|
| 小步骤 | UI/事件写「**子任务**」（如 `子任务失败…`、`plan` 里的 l1…lN）；skill 名 `small-steps-iteration` | 你叫「小步骤」，界面叫「子任务」 | 二选一统一（倾向保留你的「小步骤」，或明确「子任务=小步骤」） |
| 员工 | eval 备注里用了「员工」（如「员工将文件写入到了…」），代码/skill 用 `worker` | 角色名一致，但「失败的单元」界面叫「子任务」而非「员工的小步骤」 | 明确「子任务 = 员工要执行的小步骤」 |
| 预回复 | 代码里叫「**拟回答**」（`orchestrator.py:324` 收尾闸门 convo 只有 `[任务原文, 拟回答]`） | 你叫「预回复」，代码叫「拟回答」 | 统一为你的「预回复」 |
| 闸门核验 | 有两套被统称的东西：① leader 的 `leader_round` `判定未完成` 自复盘；② 真正的收尾验证闸门 `_verify_gate`/`verify.py` | 你的流程里「闸门核验」是**一步**，实际是「leader 自复盘 + 系统收尾闸门」两层 | 建议区分命名：leader 那步叫「评估/复盘」，系统那步叫「闸门核验」，避免混用 |
| 正式回复 | UI/事件基本只说「回复 / 输出」，没有「正式回复」这个词 | 缺统一叫法 | 可用你的「正式回复」作为终态文案 |
| 一句话 / 任务 / 分解成任务 | UI「发一句话自动登记成一条任务」；leader 拆解成 plan | 基本对齐 | 无需改 |

**另外两条行为文案也建议对齐你的口径（先列，不改）：**
- `子任务失败：模型连续 3 轮没有输出任何内容（既无工具调用也无正文），任务未完成。（其它任务不受影响，继续执行）` —— 其中「子任务」按上表统一为「小步骤/员工」口径。
- leader 轮里那 12 条 `判定未完成：…` —— 这是**leader 自复盘**的结论，不是闸门结论，建议在 UI 上和「闸门核验」区分开（例如标成「复盘：…」），否则你会误以为「判定未完成」就是闸门在拦。

## 4. 「mini-swe-agent 分析文件路径是否正确？」这类简单问题不该问

- 这是 `ask_user` 弹窗（本轮 2 次），由 `loop.py` 的**确定性澄清触发**（amb_signals /
  `asked_once`，每场至多一次）发起：工具返回空/多候选时，harness 会向用户澄清。
- 问题：对「路径对不对」这种**员工自己能判断**的事也弹窗，违反你的原则
  「只有在『没有这个信息就执行不下去』时才发问」。
- 方向（待你确认是否改）：① 把澄清门槛提高到「确属阻塞」才问；② 给员工默认口径
  「能自己判断的就自己定，只有真卡住才问」；③ ambiguity gate 对「路径确认」这类低风险
  澄清直接内部裁决，不弹用户。

## 5. 为什么这么多工具调用（777 次），是员工还是 leader，去重生效没？

- **777 次全部是员工模型（worker）调用**（leader 只发 `plan`/`assign`/`dispatch` 事件，
  不下 `tool_start`）。分布：search_code 314、read_file 230、list_dir 180、find_files 18、
  write_file 12、task_notes 11、run_command 4、ask_user 2、其余零星。
- **「已查过的不重复查」逻辑确实实现了**：`agentforge/readcache.py` 的 `ReadCache`，
  按「工具+参数」签名缓存，同签名第二次起直接回放（`loop.py:790-810`，编排层 per 任务
  传同一个 `read_cache` 跨子任务/批次共享）。
- **但它没完全压住冗余**，原因有二：
  1. 缓存是**签名精确**的——同一个文件用不同行范围读（如 `context.py` 读 `1-332` 与
     `1-200` 是两次不同签名）会漏缓存；rerun5 里 `context.py` 被读了 3 次就是这种近重复。
  2. 真正的大头 `search_code` 314 次大多是**不同的搜索词**（逆向两个仓库本就要大量
     异质搜索），这部分是合理探索，不是纯冗余。
- 结论：去重逻辑**生效但粒度太严**（只挡完全相同签名）。要进一步压，可考虑对
  read_file 做「同文件忽略行范围去重」、对 search_code 做「同目录同意图归并」。

## 6. 为什么执行这么久、收敛逻辑不明确？

- 主因是**员工模型不稳定**：deep 代码分析子任务反复触发 Ollama `gpt-oss:20b` 的 500，
  learn-claude-code 分析（round 1-3）和 mini-swe-agent 证据提取（round 9-12）整批失败。
- 次因：**leader 每批重新派发，不累积部分进度**。round 4 之后员工其实已把部分分析写到了
  `20261018-144157/analysis.md` 等文件，但 leader 下一轮又从零派「重新提取证据」，
  已写好的中间产物没被当作输入复用 → 空转。
- 边界：`leader_max_rounds = 12`（`config.py:198`）是硬上限，到第 12 批还没收敛就停，
  与记录的 `用户停止（生成中断）`一致（被帽或手动停）。
- 收敛逻辑本身是清楚的（评估→未达成就重派→达成就收尾），**卡住不是逻辑不清，是员工
  交不出合格产物 + 批次间不继承中间结果**。
