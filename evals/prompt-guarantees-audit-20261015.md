## 一、点 1：`_CAPABILITIES` 为何存在 + 通用诚实守卫设计

### 1.1 模型明明能看到工具列表，为何还要这张 5 类表？

- 模型**确实**能看到工具列表：`loop.py` 的 `TOOL_INDEX_HEADER`（行 147、230）把可用工具**名字**注入系统提示；完整 schema 按需下发。所以这张表**不是**用来告诉模型「你有哪些工具」——模型已经知道了。
- 这张表的真实作用：**执行前的确定性预检**。它把 5 类历史出过编造事故的外置能力
  （github / web / shell / git / email）做成「信号词 → 必需工具」映射，`assess()` 在
  任务开始前判定「意图需要某能力且其工具缺失」时，**由架构向 system 层注入一条硬指令
  「你做不到、必须如实说明」**（`preflight.note_for` → `messages_with_system` 注入）。
- 为什么需要这个硬指令，而不靠模型「看到自己没工具就自觉承认」？设计说明写得很清楚
  （`preflight.py` 文件头）：小本地模型（gemma4:12b 之类）即使看到了工具列表，被问
  「搜下 GitHub 项目」时仍会凭训练记忆编一份结果——它**不会可靠地 self-admit**。
  所以这是一层「可靠性拐杖」，不是信息源。

### 1.2 你的担忧是对的：这种硬编码表不具扩展性

- `_CAPABILITIES` 只覆盖 5 类、**刻意「宁漏勿误」**（信号命中才认，漏判回到旧行为）。
  任务一多一复杂，必然出现「该坦白却没被识别」的覆盖盲区——h3（发布到 npm）就是活例：
  它连 5 个信号都没命中，且发布走的是存在的 `run_command`，所以 preflight **无论如何都触发不了**，
  与「表是否扩列」无关。硬编码表这条路天然走不通。
- 更糟的是：表越扩越脆弱，信号词要为每个能力手写正则，维护成本随任务数线性甚至超线性增长，
  且永远滞后于真实任务分布。

### 1.3 通用诚实守卫：用「证据比对」替代「能力枚举」（建议方向）

不要把诚实寄托在「枚举所有能力 + 写信号词」，而是做成**基于执行轨迹的证据比对**——
harness 本来就握有完整证据，不需要预先知道任务要什么能力：

- **证据源（架构已具备）**：`_verify_gate` 收到的 `convo` 是完整对话轨迹（所有工具调用与返回），
  加上 `summary`（最终回复）、`message`（任务书）、以及沙盒里真实存在的文件。
- **通用判定，不再枚举能力**：
  1. **产物 / 答案真实性**：声明「已写入 X / 产出 X」→ 查文件是否真存在且本轮写过（现有
     artifact 核查的 missing/stale/ghost，已架构化，保留）；声明「答案是 N / 跑出结果 N」→
     比对沙盒产物或执行轨迹里的真实值（现有 `check` 层 + `apply_expect`，保留）。
  2. **未完成 / 不可行的诚实性**：模型若自承「下一步 / 做不了」（现有 `unfinished_claim`，保留），
     或产物缺失且未坦白 → 判为「未达成」，而非「成功」。
  3. **缺能力的坦白**：不再靠预枚举。若任务目标显然需要某动作、而轨迹里既无对应工具调用、
     又无「我无法完成」的坦白，则视为「未达成 / 需坦白」——**通用**，不依赖能力白名单。
- **h3 由此自然覆盖**：发布到 npm 的目标未达成（沙盒里没有发布成功的证据 / 包根本没发上去），
  而模型回复是「请把文件放进来」式的甩锅、没有「我无法完成」的坦白 → 守卫判「未达成」并逼其坦白。
  这与 preflight 扩列无关，纯粹是「目标没达成 + 没坦白 = 诚实缺失」。
- **这条守卫的本质**：从「预先告诉模型你缺什么」转向「事后核模型说的与做的/产的是否一致」。
  前者必然漏，后者只看证据、与任务复杂度无关，可扩展。

> 注意：证据比对守卫替代的是 preflight 的「能力坦白」职责，但 **`ran_verification` 式的过程检查
> 不应回归**（你已明确反对）。守卫只看「产物对不对 + 没做成时有没有坦白」，不看「你调了哪个工具」。

## 三、点 2：闸门重建原则（架构级）

### 3.1 当前闸门（`_verify_gate`）实际在做什么

按 `orchestrator.py` 顺序，闸门对每条 summary 跑五道核查：
1. **验证命令分支**（有 `cmd` 时）：程序亲跑任务书声明的验证命令，失败则拦住修正；无论模型说什么都附权威报告。✅ 这就是「判产物对不对」，保留。
2. **产物核查**（missing/stale/ghost）：声明/声称的文件是否真存在且本轮写过。✅ 判产物真实性，保留。
3. **未完成/不可行自承**（`unfinished_claim`）：模型自认「下一步/做不了」且零改动 → 判未达成。✅ 保留。
4. **外部事实一手来源**（`sources_gate`）：用了搜索却没抓一手来源、还写了外部数字 → 附「转述未核实」。✅ 保留。
5. **本机事实来源**（`local_facts_gate`）：列工作区文件却零读取 → 附声明。✅ 窄但保留。

### 3.2 已删的分支（你要求的）

原 `elif claimed_verified and not ran_verification → UNVERIFIED_NOTE`。这条**检查的是过程**
（有没有调 `run_command`），不是产物。删后闸门不再因「模型声称验证通过但没调命令」而加注。
若成果已由第 1 道验证命令分支验收为正确，模型的「验证通过」陈述即为真，无需再质疑过程。

### 3.3 仍残留的一处 `ran_verification`（待你裁定）

- `orchestrator.py` 产物核查里：`produced = verify_gate.ran_writes(convo) or verify_gate.ran_verification(convo)`
  （约现第 317 行），用于区分 ghost（全程零写操作+零命令 → 文件不可能是本轮产出）。
- 这里 `ran_verification` 的语义是「有没有命令可能产出过文件」，服务于**产物真实性**
  （判文件是不是本轮写的），不是「你有没有验证」。这与你反对的「过程检查」性质不同。
- **建议**：保留。它回答的是「声称的文件是否真实存在」，属于产物判定，符合你的闸门原则。
  若你坚持「任何 run_command 检查都不要」，可改为「零写操作即视为 ghost 候选」——
  但会牺牲「命令产出的文件」这类合法场景的精度，需权衡。

### 3.4 闸门的目标形态（建议，供讨论）

把闸门输出从「追加声明」升级为**明确的执行状态判定**（你描述的原则）：
- `SUCCESS`：产物经第 1 道验证命令 / 第 2 道产物核查确认正确。
- `CANNOT_EXECUTE`：缺工具/技能或当前状态不可行，且模型已坦白（或守卫逼其坦白）。
- `MODEL_LIMIT`：模型智力/能力上限导致未达成（轨迹显示它尝试过但做不对）。
- `ROUNDS_EXCEEDED`：轮次耗尽未收敛。
- 然后**交接给第七步输出**收尾，闸门本身不做与任务无关的事（不查过程、不查它调了哪个工具）。
- 当前代码是「能追加声明就追加」，尚未显式输出状态枚举；是否要做成枚举由你定，
  但删掉 run_command 检查这步已符合你的核心原则。

## 四、点 3：第七步「简单汇总各任务结果并输出」设计是否合理（客观分析）

### 4.1 代码里第七步到底是什么

- **多任务**（≥2 子任务且 `dispatcher_synthesis` 开）：`dispatcher.synthesize()` 由决策模型
  把各子任务的 `summary` 整合成一份中文答复（输入仅为 `[标题] 摘要` 列表，见 `dispatcher.py:558/562`），
  然后过 `_verify_gate`。**这就是你说的「汇总各个任务结果并输出」**——设计在代码里是落地了的。
- **单任务**（或关掉 synthesis）：没有独立汇总步骤，agent 自己的最后一条回复即最终输出，仍过闸门。

### 4.2 这个设计本身合不合理

**合理的一面**（标准 Orchestrator-Worker 模式，Anthropic 也推荐）：
- 多 agent 各自产出结果后，必须有一个聚合层把 N 份结果压成一份给用户，不能简单拼接（冗长、重复）。
- 用一个轻量「协调者」模型做聚合是通行做法，比让某个 worker 自己收尾更稳。

**不合理 / 有漏洞的一面**（正是 w3 失败的根）：
- **汇总契约是漏的**：`synthesize()` 喂给协调者的**只有每个 worker 的 `summary` 文本**
  （`dispatcher.py:562` 的 `listing`），**不包含 worker 写出的文件内容、也不含 worker 的完整轨迹**。
- 于是当某子任务的答案/关键事实**写在文件里**（如 w3 的 `short.txt` 含 14:00），而 worker 的
  `summary` 没把 14:00 复述出来时，协调者**根本没有信息源**去把 14:00 带进最终回复 → 系统性丢事实。
- 换句话说：第七步「汇总」在架构上是存在的、方向也对，但**输入契约缺了一块**——
  文件型交付的「答案」没回流到汇总层。

### 4.3 怎么修（设计层，非提示词）

不是「第七步该不该汇总」的问题，而是「汇总层拿什么汇总」的问题：
- **方案 A（契约补全）**：worker 收尾时，其 `summary` 必须携带「用户要的答案/关键事实」，
  不能只写「已创建 X」。由架构在 worker 收尾处强制（而非靠提示词）把答案要点回填进 summary。
- **方案 B（汇总层读产物）**：`synthesize()` 的输入除 `summary` 外，附带各子任务产出的文件内容
  （或关键片段），让协调者基于真实产物而非一句回执来汇总。
- **方案 C（判定看文件）**：对「答案在文件里」的任务，评测 `judge` 的 norm/keywords 改判文件而非回复。
  但这会削弱「答案必须进回复」的体验，且偏离你「判产物」的原则，仅作备选。

> 我的客观结论：**第七步「汇总」的设计合理、应予保留**；真正要改的是「worker→汇总」的
> 信息契约（A 或 B），而不是否定汇总这一步。这与你「闸门判产物、输出步汇总」的分工是一致的——
> 只是产物里的「答案文本」目前没被汇总步看见。
