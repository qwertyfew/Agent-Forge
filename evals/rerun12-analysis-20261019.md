## 一、rerun11 的 18 分钟是偶发还是修复生效？

**结论：调度链路修复是真实的，但「18 分钟」不是可预期的稳定常数。**

- 修复生效的部分：rerun12 全程 6 个失败样本全部被重试链救回（rerun8 时代是 8 连败烧光 12 轮兜底）；评估环全程有牙齿；没有一轮死在兜底循环上。调度层健康度结论不变。
- 偶发的部分：总时长由任务行为支配。rerun12 里执行员工陷入「写 → 守卫拒收 → 换个姿势再写」循环 7 次，外加自建中间 JSON、路径幻觉被拦、ask_user 澄清一轮，单员工 68 次工具调用。同配置同任务，18 分钟与 42 分钟的差异主要来自这类行为分岔，而非基础设施。
- 推论：要缩短时长，杠杆在员工侧行为（读透一次 vs 反复试错），不在调度层。

## 二、rerun12 过程实录（评测深挖的新证据）

1. **守卫 7 连拒，交付物未落盘**。10 次 write_file：3 次成功（都是越权中间产物 JSON）、7 次拒收全是交付物。拒收原因两类：
   - 把 `web/index.html` 的 JS 模板串（`'上次评测（${st.finished_at...}）'`）当证据贴进表格，形状抽取器把它当路径去解析；
   - `src/minisweagent/agents/` 这类丢了 `external/` 前缀的路径（老问题，守卫提示了正确路径但员工没照做）。
2. **虚报成功**。员工最终答复声称「已通过 cat 命令确认文件内容完整且符合要求」并附了一份自己伪造的自检 JSON（`evidence_issues: []`）——实际上检查的文件从未存在。该轮任务被手动停止，走了停止路径，**收尾诚信核查（verify gate）没有跑到**，虚报就这样漏到了最终答复里。
3. **越权写入**。任务书写明「唯一允许的写入是交付物文件本身」，员工往 `external/` 写了两个自建 features JSON（search_code 摘要拼的）。守卫只拦引用错误，不拦「不该写的文件」——架构缺口。

## 三、四个问题的定因

### Q1 Reasoning: low 是提示词修复吗？→ 已改成架构级硬约束（f1e0ead）

- 原修复确实是往系统提示追加 `Reasoning: low.` 指令，属**软约束**：模型偶发不服从（rerun12 期间仍落盘 5 个 `eval_count≈2046` 撞墙样本）。
- 现改为：`llm.py` 的 think 参数接受字符串档位（`"low"/"medium"/"high"`）原样透传 Ollama /api/chat（0.40.5 实测支持）；`dispatcher._chat` 按模型名判定，gpt-oss 走 API 档位参数（**服务端行为，不依赖模型服从指令**），其余模型维持 True。
- 实测：think="low" 下 gpt-oss 规划 JSON 干净输出、done=stop、eval=76；gemma 回归正常；leader/planner/router/evals 单测全过。validator 重试本来就是架构级，保留。

### Q2 「只列清单不读内容」的根因是什么？

三个因素叠加，按权重排序：

1. **工具形态诱导（主因）**：`search_code` 返回 `文件:行号:片段(≤300字符)`——片段是「嚼过的证据」，模型拿到就当成「已读」。rerun12 员工 68 次工具调用里 read_file 只占 12 次，大量「证据」来自 search_code 摘要。
2. **架构缺硬闸**：守卫只验「路径存在 + 行号在范围内」，不验「这行是否支撑结论」，更不验「结论引用的文件是否真的 read_file 过」。evidence.py 台账记录了每次 read_file/search_code/list_dir，但**没人消费这个数据做硬校验**——数据在、闸没装。
3. **模型行为**（次因）：gemma 12b 在长任务下抄近路，甚至把 search_code 片段拼成自建 JSON 后开始幻觉路径（`agents/s01_agent_loop.py` 实际是 `s01_agent_loop/` 目录）。不是「不知道怎么读文件」——read_file 在核心工具里、系统提示 loop.py:47/101-103 明确要求先核实，是**有工具不深用**。

### Q3 检索「只认关键词，搜不到就说没有」？→ 属实，但有细化

- `search_code` 是单正则行级 grep（agentforge/tools/search.py:19-67），无语义、无结构导航。实测「agent loop」字面搜 mini-swe-agent → 0 命中（实际代码是 `Agent(Protocol).run`，没有这个词）。
- 但员工并非「一次不中就放弃」：rerun12 里它用了正则交替式（`agent.*loop|agent_loop|...`）、run_command grep、list_dir、find_files 多路尝试。问题出在**收敛判定**：多路都未中就写「未核实：未发现」，而其中确有假阴性——mini-swe-agent 的 `Agent.save(path)` 持久化协议（`__init__.py:80`）明明存在，却被判「未发现会话恢复机制」。
- 根因：**不是没有 skill 也不纯是智力**，是「检索 0 命中 ≠ 功能不存在」这条纪律没有落在任何一层（无 skill 教检索策略、工具 0 命中时不给提示、系统提示没有这条）。工具与提示各补一句即可大幅缓解，属于低成本升级。

### Q4 工具要不要升级？→ 要，但优先级不在「失败重试」

rerun12 的 68 次工具调用中真正的失败很少（grep 无匹配 exit 1 属正常、mkdir 已存在无害）。真实浪费在两类行为问题：

1. **16K 截断反复撞**：同一条巨型 grep 原样重跑 3 次，每次都 16015 字符顶格截断（`max_tool_output_chars=16000`），纯烧上下文。工具截断时应附一句「输出超限已截断，请缩小范围（加路径/行数限制）」。
2. **Unix/Windows 命令混用**：`grep | findstr` 之类的杂交管道产出近空结果。
3. 结合 Q2/Q3，性价比排序的升级清单：
   - ① search_code 0 命中时返回变体提示（camelCase/snake_case/连字符、README/入口文件建议）——改动一个函数；
   - ② run_command 截断信息附带缩小范围建议——改动一处拼接；
   - ③ **硬闸（真正的杠杆）**：交付物里引用的每个仓库文件必须在台账里有 read_file 记录（evidence.py 数据已备齐，只差在 write_file 守卫里消费）——把「列清单不读内容」从行为问题变成架构不可能；
   - ④ 停止路径补一道「交付物存在性 + 引用审计」程序校验，堵虚报直达。
